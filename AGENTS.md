# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- The design spec is `docs/design-v3.html`. Its M0 badges (Pi included) were resolved by the spikes; `docs/m0-verdicts.md` is the record of what each platform behavior actually does and which design text changed. Read it before building on any harness, Pi, Herdr or tasks-axi behavior.
- Anything that drives Herdr (spikes, contract tests) must go through Firstmate's `fm-herdr-lab.sh` via `spikes/lib/lab.sh`, never the default session. Scrub inherited `CLAUDECODE`/`CLAUDE_CODE_*` env before provisioning (`lab_scrub_env`), or launched harnesses run as child sessions of yours.
- Run the spikes with `spikes/run-all.sh [group]` (README "Running the M0 spikes"). Herdr needs socket access, so run them outside a command sandbox.
- Pi contract tests use the offline scripted model in `spikes/pi/lib/scripted-provider.ts` and a scratch `PI_CODING_AGENT_DIR`, never a paid model or `~/.pi`; `spikes/pi/NOTES.md` has the script syntax and the opt-in real-model pass.
- The cleanup guard must pass both fixture sets before any change to it lands: `fixtures/cleanup-guard/run.sh --impl "bun $PWD/scripts/guard/landed-impl.ts"` (landed-work verdicts) and `fixtures/cleanup-order/run.sh --impl "bun $PWD/scripts/guard/cleanup-impl.ts"` (locks, parked runs, reaping, order). CI runs both.
- Product code is TypeScript on Bun; dev commands are in README "Development". `bun test` starts real daemons on Unix sockets, relies on FSEvents and runs the real tasks-axi 0.2.5, so run it outside a command sandbox. Inside one, `bun install` also needs `BUN_TMPDIR` and `BUN_INSTALL_CACHE_DIR` pointed at a writable temp directory.
- `docs/m1-notes.md` to `docs/m4-notes.md` record the choices each milestone made where the design leaves room, and the live results (Herdr's typed-command limits, Claude trust and sandbox, the steer channels, the reconciler's rules, leader sessions and the lease, presentations and offers, the named-head and merge gates, the approval channels, cleanup). Extend the latest one, or add the next milestone's, rather than rediscovering them.
- `bun test` never reaches a real Herdr or harness: test homes point `[herdr] socket` at a missing path, and runtime tests use `test/helpers/fake-herdr.ts` with a fake worker that goes through the real CLI. Leader tests use fakes that run the real bridge artifacts (the leader settings file's hooks, the Pi leader extension). Live Herdr, Claude and Pi runs are `flowryn doctor --contracts` and `scripts/lab/m2-live.sh` to `m4-live.sh`, all in a lab session; they own a `flowryn/contract-<runid>-` branch prefix and clean up by exact name in code.
- Leader and worker hooks share the `flowryn hook` verbs; the caller's token decides (a run token is a worker, a leader session's token a leader or read-only reader, by the lease). Leader bridges decide nothing: put any rule in `src/leader/` or `src/attention/`, never in `src/bridges/`.
- A worker's `$FLOWRYN_BIN` calls run inside the user's Claude Bash sandbox (hooks do not). The per-run settings allow the daemon socket, the run's spool and report directories and, for a ship, only what a commit in its linked worktree writes of the git common dir (`objects`, `refs`, `logs`, `packed-refs` and its lock, its `worktrees/<name>`), with `hooks` and `config` denied, so a worker never writes git config (no `push -u`). A new path a worker must write needs adding there (`src/harness/git-access.ts`, `src/harness/claude/adapter.ts`, `src/lifecycle/launcher.ts`).
- Nothing in tests, fixtures or the lab reaches GitHub or the shared no-mistakes daemon: GitHub goes through `src/forge` at `[github] api_url`, served by the fake forge (`test/helpers/fake-github.ts`), and test homes get a stand-in `no-mistakes`. A GitHub token is only ever sent to GitHub's own API host. A real-GitHub run needs a sandbox repo the user provides.
- `flowryn approve` and the live board need a real terminal; tests drive them through `script(1)`, which refuses a socket on its stdin (Bun's pipe, and a macOS FIFO, are sockets), so `test/helpers/pty.ts` feeds keys through a FIFO that `cat` copies onto a real pipe.
- Every tasks-axi mutation goes through `recordIntent` in the same transaction as its runtime change, and every mutation of `flowryn.db` appends an event in its transaction (`src/db/events.ts`). Never call tasks-axi or write the database from anywhere else.

## Maintaining this file

Keep this file for knowledge useful to almost every future agent session in this project.
Do not repeat what the codebase already shows; point to the authoritative file or command instead.
Prefer rewriting or pruning existing entries over appending new ones.
When updating this file, preserve this bar for all agents and keep entries concise.
