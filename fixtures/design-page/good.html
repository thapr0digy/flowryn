Design pages you can judge in two minutes

Design for the task “design review pages” · plain rules in code, no model grades the writing.

In short

Design pages open with code names and file lists today, so you rebuild the idea yourself. Every design page will now follow one fixed outline in plain words, readable in about two minutes, with files and code names folded at the bottom. Flowryn checks the outline, length and code names before the page reaches you, and sends a failing page back to the worker with the reasons. QA summary cards get the same check.

What I need from you

Approve, or send changes. No questions; the rest is decided (folded section). Worth a look:

  • 500 visible words at most, about two minutes. Diagrams don’t count.
  • Code names are caught by shape: underscores, mixed case, file paths, flags. Plain-English jargon has no shape, so the instructions forbid it and you judge it.
  • Designs in progress are checked too: their next hand-in is refused once, naming the template.

Goals and non-goals

Goals. The page alone tells you what changes, why, and what could go wrong. Every page has the same shape. The check is plain code with one answer.

Not goals. Grading the writing: that stays with you. Chat replies and status reports, which stay terse.

How it works

  1. The design instructions ship a page template with the seven parts marked. The outline borrows from Google design docs, Rust RFCs, Oxide RFDs and decision records (sources folded below).
  2. At hand-in Flowryn checks: every part present and in order, a short summary, the visible budget, a diagram here, no code names above the fold, the detail folded last.
  3. Failures go back as a list of fixes. The worker’s “be terse” rule now covers replies and reports, not review pages.

Other ways we could do it

  • New instructions, no check. Cheapest, but the old ones asked for clear pages and drifted anyway.
  • A model grades readability. Catches jargon, but varies between runs, costs money, and the task rules it out.
  • Flowryn generates the page from data. Tightest shape, but loses free-form diagrams and tables.
  • Do nothing. Pages stay hard to judge.

Risks, and how we’d know it’s wrong

  • Pages pass the check but still read badly. You send changes; the rules tighten.
  • 500 words is too tight for a big design. Repeated length refusals. Change one number, or split into phases.
  • Product names trip the code-name rule (like macOS). A refusal names it; a short allow-list covers common ones, and a page can define any term.

The rules the check applies

RuleHow it is checked
Template filledNo {{SLOT}} placeholder left.
Seven parts, in order, then the detail<section data-section=…> for tldr, ask, change, goals, how, alternatives, risks, each with words, in that order; then <details data-section="detail">, not open, after the last section. Nothing but the title and one subtitle line before tldr.
Short summarytldr ≤ 80 words.
Visible budgetWords outside <details>, <svg>, <style>, <script> and comments ≤ 500. The message gives the count and says to fold detail.
A diagramThe how section holds a <figure> (inline SVG, an image or a drawn <pre>).
No code names above the foldIn visible text (SVG labels included): words with an inner underscore, lower-then-upper case (allow-list: macOS, iOS, iPadOS, iPhone, iPad), a slash plus a file extension, a leading --, a trailing (); and any <code> or <pre> element outside the figure. A term the page defines with <dfn> is allowed everywhere. <kbd> marks what the user types and is allowed. Each offending term is named, up to 10.

Plain-English jargon (“digest”, “follow-up batch”) cannot be caught by shape. The skill forbids undefined internal terms; the reviewer judges. No model is used anywhere.

Tests

  • test/unit/design-template.test.ts: the bare template fails (placeholders); this page, copied to fixtures/design-page/good.html, passes; each rule fails on its own crafted page with its own message; a page shaped like the old ones (file table first, LEADER_WAKE_KINDS above the fold, 660 words) fails on order, budget and code names.
  • test/unit/qa-template.test.ts: card code-name and card-budget cases.
  • test/unit/review-page.test.ts: visibleText drops folded parts and nested tags; the shape rules on a word list, including the allow-list and <dfn>.
  • Integration (test/integration/workflows.test.ts or a new file): design-stage stage done refuses a bad page with every problem listed, accepts the good one, refuses a --page that names another file, refuses a symlink.
  • Every existing test that hands in a design page gets the good fixture through the fake harness’s page helper.

Assumptions the build tests

  • Existing tests hand in design pages through few enough places that swapping in a valid page is small (guess; not counted yet).
  • Lavish serves the page as written, so <details> stays folded (true for QA pages today).
  • The question widget still mounts and works inside the ask section.
  • The offline contract fakes do not match on the “Be terse” line (if they do, the build updates them and decides the bump).

Choices made, and why

  • “What I need from you” is second, right after the summary: decision-first is the user’s standing preference for review pages, and Squarespace puts the approver’s ask up front.
  • 500 visible words: about two minutes at 250 words a minute; existing pages run 544 to 899. Google allows a 1–3 page “mini design doc” for incremental work; 500 words is the short end of that.
  • A fixed path (design/design.html): the skill already names it, and the QA check works the same way.
  • A fill-in template, not generated HTML: keeps free-form diagrams and tables.
  • A diagram is required: the task asks for it; any <figure> counts, so a tiny design can draw a two-box sketch.
  • Code names by shape, not a word list: deterministic and project-independent; <dfn> is the escape hatch, as plain-language guidance says to define terms on first use.
  • In-flight design runs are checked: their error names the template, which the daemon writes beside the skill at start, so one revision fixes it.
  • Leader pages get guidance, not a check: there is no hand-in point to check them at.
  • QA keeps its card, already plain-language, and gains only the code-name rule and a 200-word card budget.
  • No phase plan: one change.
  • No scout finding: the scout report has none for this; the evidence is the user’s complaint and the pages under ~/.flowryn/data/*/design/ (measured above).

Where the outline comes from

PartSource
In shortRust RFC “Summary: one paragraph”; Amazon narrative memos open with the conclusion.
What I need from youSquarespace RFC status line tells reviewers what feedback is wanted; approvers answer “yes”, “not yet” or “yes, if”.
What changes for youRust RFC “guide-level explanation”: describe it as if it already existed, by its effect on the user.
Goals and non-goalsGoogle design docs: a non-goal is something that could reasonably be a goal but is chosen not to be.
How it works, with a diagramGoogle: overview first, system-context diagram, then detail.
Other waysGoogle “alternatives considered” (“one of the most important”); Rust “rationale and alternatives” incl. the cost of doing nothing; PEP “rejected ideas”.
Risks and how we’d knowRust “drawbacks”; Nygard ADR “consequences”, negative ones included; Monzo’s required risks section (via Orosz).
Detail folded, lastGoogle: no pasted code or schemas, “focus on the parts relevant to the design and its trade-offs”; Diátaxis: keep reference apart from explanation; Rust “reference-level explanation” comes after the guide-level one.
Plain words, defined termsUS Federal Plain Language Guidelines: short sentences, main idea first, define terms, one term per thing.
Keep it short and minimalWill Larson: “start from the problem”, prefer minimal templates; Oxide RFD 1: timely over polished.
