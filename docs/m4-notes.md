# M4 notes

M4 builds section 17's "M4 · Delivery and policy" of [`design-v3.html`](design-v3.html) on top of [M1](m1-notes.md), [M2](m2-notes.md) and [M3](m3-notes.md): the no-mistakes, direct-PR and local-only delivery modes; the GitHub watcher; the named-head gate; the approval channel from all four channels; the merge gate with red refusal, a single-check human waiver and proof; the cleanup guard with both fixture sets; and the board's approve key. This file records where the design left room, what M4 chose, and what the live runs showed. Each item names the code that holds it.

## The forge

- Flowryn talks to GitHub's REST API itself (`src/forge/github.ts`): read a PR, list a branch's PRs, read a head's check runs and commit statuses, and merge at an exact head (`PUT .../merge` with `sha`, which GitHub refuses with 409 when the head moved). Reads are conditional (ETag / If-None-Match), so an unchanged poll is a 304 that costs no rate limit; a mutation drops the cached reads of its repository.
- `[github]` (`src/config/delivery.ts`): `api_url`, `web_url`, `token_env`, `poll_ms` (default 60 s), `timeout_ms`, `merge_method` (default `squash`). Canonical PR URLs are `<web_url>/<owner>/<repo>/pull/<n>`; a project's repository comes from its `repo_url` (https, `git@` and `ssh://` forms).
- **A token goes only to GitHub's own API**: the first set variable in `token_env`, else `gh auth token --hostname <web host>`, and only when `api_url` is `api.github.com` or the web host (Enterprise). Any other `api_url` (the fake forge of the tests, the fixtures and the lab) gets no token at all.
- A check run is green when completed with success, neutral or skipped, pending while it runs, red otherwise; a commit status is green on success, pending on pending, red otherwise. No checks at all is `none`, which is not red.
- `test/helpers/fake-github.ts` is the fake forge: the same REST calls from memory, with ETags. A repository can be backed by a local bare git repo, so a PR's head follows the pushed branch and a merge lands a real squash (or merge) commit on the bare repo's base branch, deleting the head branch as GitHub's auto-delete would. Knobs make it unreachable, rate limited, refuse merges, or accept a merge it never reports until `prove()` (the unproven case). Tests, the first fixture set's implementation and the lab all use it; nothing in them reaches GitHub.

## Delivery

- The worker contract's "finished" lines follow the task kind and the project's delivery mode (`src/harness/contract-text.ts`): a scout delivers `--report`; a local-only ship commits, never pushes and delivers `--local`; a direct-PR ship pushes, opens a PR into the default branch and delivers `--pr`; a no-mistakes ship runs its pipeline (which pushes and opens the PR), asks through `$FLOWRYN_BIN ask` for an ask-user finding, pulls so its HEAD is the PR head, then delivers `--pr`.
- **The named-head gate** (`src/lifecycle/delivery.ts`): `deliver --pr <url>` is accepted only if the URL names a PR in the project's repository; the PR exists, is not closed unmerged and not a draft; it is the run's branch into the project's default branch; its head is what the remote has for that branch (`git ls-remote origin`); and it equals the worktree's HEAD, read by the daemon. A draft or a head that is not on the remote is also a divergence (P1), as section 6's example says; a later delivery that passes resolves it. A HEAD that is not the PR head is refused with `head_mismatch` and a help line (`git pull --ff-only`), without a divergence: it is the worker's own state.
- `deliver --local` (local-only) is accepted when the worktree is on the run's branch, clean, and has commits the default branch lacks. The artifact is the branch head (artifacts gained the kind `local`).
- A delivery records the artifact (URL or branch, and the head), moves the run to `ready`, links the PR in the backlog, and opens `pr_ready` (P1) or, for sensitive work, `sensitive_action_waiting` (P0). A second delivery at a new head voids every standing approval of the task.
- **`deliver` waits up to 60 s for its reply**, not the 2 s section 12 gives worker verbs before they spool: the gate asks GitHub and the remote, and a spool would turn a refusal the worker must see into "spooled" (`replyMs` on the verb spec). The 300 ms connect timeout is unchanged, so a daemon that is down still spools at once.
- A ship worker's Claude sandbox settings allow writes to what a commit in its linked worktree needs, and no more of the project's git common dir: `objects`, `refs`, `logs`, `packed-refs` (and its `.lock`, which creating a ref takes) and the worktree's own `worktrees/<name>` (`src/harness/git-access.ts`). The common dir's `hooks` and `config` are denied explicitly (`sandbox.filesystem.denyWrite`), not left to Claude's built-in protected paths: flowrynd later runs git unsandboxed in the primary checkout, where a planted hook or `core.fsmonitor` would run. So the direct-PR contract says `git push origin HEAD`, not `-u` (tracking config is a config write). `test/unit/harness.test.ts` applies the generated lists to a real commit and push under macOS `sandbox-exec`.

## The watchers

- The delivery watcher (`src/watch/delivery.ts`) polls every delivered PR (ship runs `ready` or `merging` in a PR mode) every `poll_ms`, and what it sees is applied by `src/reconcile/delivery.ts`: a PR that reads merged with a merge commit lands the run (a merge Flowryn asked for and could not prove at once, or one you made on GitHub); a PR closed unmerged is a P1 `pr_closed`; a head that moved after delivery, or a PR turned draft, is a divergence; red checks at the delivered head are a P1 `checks_red` until they turn green. A failing forge backs off (doubling up to 10 min, or until the rate limit's reset) and is never retried in a tight loop.
- It also proves local-only merges a restart interrupted, marks a merge still `requested` after a restart as unproven (the daemon stopped before it knew), and runs the cleanup of a landed run whose cleanup never ran.
- The no-mistakes watcher reads `no-mistakes axi status` in each no-mistakes ship's worktree, read-only: a live run for the run's branch makes the Flowryn run `validating`, and its end makes it `running` again. Three failed reads in a row open one P1 (`nomistakes_down`); flowrynd never restarts no-mistakes (section 16).

## Approvals

- Four channels create an approval (`src/policy/approvals.ts`):
  - **claude-ask**: the Claude leader's PreToolUse hook sees `flowryn merge <task>` (or `flowryn cleanup <task> --discard`) in a Bash call, records an attempt (session, tool use id, the arguments' hash, permission mode, and the PR and head its prompt names), and answers `ask` with a reason that names the PR, the head and the checks; the ask rule `Bash(flowryn merge *)` is the second layer. The merge that follows matches the newest unmatched attempt of the same session and arguments under five minutes old; an attempt made under `bypassPermissions` never matches. A newer attempt supersedes older ones.
  - **pi-confirm**: the Pi leader extension registers a `flowryn_merge` tool (plain JSON-schema parameters, which Pi 0.87.1 validates without TypeBox). It reads what would land (`hook merge-summary`, fresh from GitHub), shows the title, PR, head and checks with `ctx.ui.confirm()`, and on yes runs `flowryn merge <task> --head <sha> --key-file -` with the approval key on stdin. The key comes from `session-start` when the session claims the lease; a session that took the lease later gets one from `hook approval-key`, which mints a new key (so only the newest one works). The extension blocks shell calls to `flowryn merge`, `approve` and `hook`.
  - **cli-tty**: `flowryn approve <task> [--allow-red <check>] [--discard]` (`src/cli/commands/approve.ts`) refuses in an agent pane or without a terminal on stdin and stdout, asks the daemon for a challenge (`approve.begin`, which reads the PR, head and checks fresh), shows them, and reads a random four-letter code back from `/dev/tty`. `approve.confirm` records the approval bound to exactly the head it showed. Challenges live in the daemon's memory for two minutes and are used once, right or wrong; a restart forgets them.
  - **board**: the live board's `a` key lists the ships waiting for a merge approval and runs the same two steps from the board's own raw terminal keys.
- **Which approval allows a merge** (`chooseApproval` in `src/policy/merge.ts`): a standing human record (cli-tty or board) for the current head first, because it can carry a waiver; then the harness channel the caller brought; then the yolo posture. A head the caller confirmed (`--head`, or the head a Claude prompt named) is a precondition: if the head moved, the merge is refused even under yolo.
- The challenge is confused-agent-grade, like the human role itself (M1): it stops piped input and keystrokes forged through Herdr, because the code is read from `/dev/tty` and must be read off the screen. It does not stop a process that speaks the socket as your terminal, which is section 7's accepted residual ("an agent using another interpreter to call the binary"); the leader's deny rule and the Pi extension's shell gate keep an agent from running `flowryn approve` itself.
- An approval is single use and expires after 24 hours; a record for another head never matches, and the refusal says whose head it was for. `--allow-red` must name a check that is failing now, and only when exactly one is.
- `--gate` (review gates) arrives with workflows in M5; `approve --gate` says so.

## The merge gate

- `flowryn merge <task>` (`src/policy/verbs.ts`, `src/policy/merge.ts`) checks, in the design's order: the canonical PR at the delivered head (`pr_closed`, `head_moved`); not a draft and the head on the remote (`pr_draft`, `head_not_on_remote`); every check green, or exactly one red check waived by a human record (`red_checks`), and none still running (`checks_pending`); an approval or yolo (`approval_required`); sensitive work only with a human record (`approval_required`). All are exit 2.
- The approval is used up and the merge recorded (`merges` row `requested`, run `merging`) in one transaction; then GitHub is asked to merge at exactly that head, and the PR is read back. **Merged with a merge commit is the only proof**: the run is landed and its cleanup starts. Accepted but not reading merged, or no answer, is `unproven`: the command exits 2 `not_landed`, the run stays `merging` with its worktree, a P1 `unproven_merge` says so, and the watcher keeps looking. A refusal from GitHub (409 head moved, 405 not mergeable) is `merge_refused`, and the run is ready again.
- **yolo only removes the need for a human record; flowrynd never merges by itself.** Section 6 lists the only automatic actions, and a merge is not one; the leader still runs `flowryn merge`, and a yolo merge opens an informational `yolo_merged`.
- A local-only merge is a fast-forward of the project's default branch in its primary checkout, which must be on that branch with no changes to tracked files; a diverged branch is `not_fast_forward` (the worker rebases and delivers again). The proof is the head on the local default branch.
- `flowryn decline <task> --body-file -` sends a delivered ship back: the run is `running` again, its approvals are void, and the worker gets your words as a steer.

## Cleanup

- `src/policy/landed.ts` is the landed-work verdict, a port of Firstmate's rules at a09090d1: dirty always refuses; work on a remote-tracking branch (a fork counts) is landed; local-only work on the local default branch is landed; otherwise a merged PR (recorded, or found by the branch) whose head contains HEAD or every unpushed patch, or content already in a freshly fetched default branch; an unreachable forge with the content absent refuses. A human discard approval turns a refusal into a discard. A scout's clean worktree is allowed (its deliverable is its report). When a ship's worktree is already gone (removed by hand), its branch may hold the only copy of the work, so the guard judges `refs/heads/<branch>` from the primary checkout by the same rules; only a branch that is gone too is `worktree_absent`. The fixture sets have no case for it (the first set has no primary checkout, and the second's refusal check needs the worktree present); `test/unit/policy.test.ts` covers it.
- `src/policy/cleanup.ts` is the cleanup order: the verdict; an `index.lock` in the worktree waited for, removed only when provably stale (`lsof` proves no holder and it is at least `lock_age_ms` old), with the verdict taken again; the task's own parked no-mistakes run aborted and confirmed (`src/policy/nomistakes.ts`); the worker stopped by its recorded identity; leaked processes reaped (`src/policy/reap.ts`); the lock checked again; then `git worktree remove` (with `--force` only for an approved discard) and the task branch deleted. Flowryn removes worktrees with git, as M2 creates them; a plain `git worktree remove` deletes the lock with the worktree's admin directory without a word, so the guard checks the lock itself first. A step that cannot run at all (a tool that will not start, as `ps` inside a command sandbox) refuses with `guard_error` rather than throwing, so an automatic cleanup still leaves its record and its P1.
- After a proven merge the daemon cleans up by itself (section 6); a refusal then is a P1 `cleanup_refused` naming `flowryn cleanup <task>`. A landed run that is cleaned becomes `cleaned`, and its task is done in the backlog (`--pr <url>`, or a note naming the local merge).
- `flowryn cleanup <task> [--discard]` (leader or you) cleans a landed, cancelled or failed run's worktree. `--discard` needs a human discard approval bound to the worktree's HEAD (the branch tip once the worktree is gone): `flowryn approve <task> --discard` in your shell or a Claude prompt (the ask rule `Bash(flowryn cleanup * --discard*)`). The approval is used up only when the cleanup removes the worktree; a refusal (a lock, an unconfirmed no-mistakes abort, survivors) leaves it for a retry at the same head, and a matched Claude prompt is recorded as a claude-ask approval only then. The Pi leader has no discard tool; you approve in your shell.
- `[cleanup]`: `lock_age_ms` (30 s), `lock_wait_ms`, `lock_retries`, `reap_grace_ms`, `reap_passes`, `nomistakes_timeout_ms`, for tests and the lab.

## The fixture sets

- `fixtures/cleanup-guard` (21 cases, the first set): `scripts/guard/landed-impl.ts` serves each case's `forge.json` from the fake forge and runs Flowryn's verdict through the same REST client the daemon uses. 21/21 pass.
- `fixtures/cleanup-order` (23 cases, the second set): Firstmate's index-lock, parked-run-abort, process-reap and ordering cases, with fake `no-mistakes`, `lsof`, `ps` and `git` per case and real processes to reap. `scripts/guard/cleanup-impl.ts` runs the whole cleanup procedure against each scenario. 23/23 pass; a naive implementation that always force-removes fails 17. Its README lists what was deliberately not ported (the runs-ledger fallback, a non-linked checkout, tmux pane groups) and why.
- CI runs both sets against Flowryn's implementation.

## Protocol and version

- `PROTO` is 2 (verb arguments changed: `deliver --local`, `merge --head/--key-file`, new verbs), so an older CLI in a running worker gets exit 76 instead of talking past the daemon. The version is 0.3.0.

## Tests

- `test/integration/delivery.test.ts`: the named-head gate and the merge gate against the fake forge (green, head mismatch, draft, head not on the remote, red, waiver, two reds, pending, head moved after delivery, unproven then proven, refused, merged on GitHub, closed, yolo, sensitive), no-mistakes `validating`, local-only merges and a diverged main, decline, and cleanup with and without a discard approval.
- `test/integration/m4-exit.test.ts` is the M4 exit: one ship per leader and channel, dispatch to cleaned. The leaders are the M3 fakes, extended: the fake Claude runs Bash calls through the settings file's permission rules and the PreToolUse hook's decision; the fake Pi runs the extension's registered tools and answers `ctx.ui.confirm`. `flowryn approve` and the board run in a real pty: macOS `script(1)` refuses a socket on its stdin, and Bun's stdin pipe is a socketpair (as is a FIFO on macOS), so the keys go through a FIFO that `cat` copies onto a real pipe (`test/helpers/pty.ts`).
- Test homes get a fake `no-mistakes` and no `gh`, and a GitHub address that answers nothing unless a test serves the fake forge (`test/helpers/harness.ts`).

## Live runs

`scripts/lab/m4-live.sh [--claude-project <checkout>] [--seed-contracts] [flow ...]` runs the exit on real leaders started with `flowryn lead` in panes of a Firstmate lab session (`fm-herdr-lab.sh`), with real workers. Claude leads from a linked worktree of the trusted checkout; its local-only project is another linked worktree on a `flowryn/contract-<runid>-main` branch that the ships merge into, and every branch and worktree the run made is removed by exact name on exit. Pi leads and works in scratch repositories with a scratch agent dir and the offline scripted provider. The direct-PR and no-mistakes ships push to bare origins behind a fake GitHub served by the run on 127.0.0.1. The run answers two kinds of prompt only, because they are what is under test: Claude's permission prompt for `flowryn merge` and Pi's merge confirm (both with Enter, the first choice, Yes). It never answers a trust dialog, and never writes `~/.claude.json` or `~/.pi`.

Result on 2026-09-24 (Herdr 0.7.5, Claude Code 2.1.281 on haiku, Pi 0.87.1 on the scripted provider, lab session `fm-lab-flowryn-m4-77370-22949`): **17/17 passed**, every ship from dispatch to merged and cleaned.

Do you want to proceed?") and not the PreToolUse hook's reason, so the PR, head and checks are on screen only when the hook alone asks. The approval is still bound to the head the hook recorded. The earlier run whose screen check looked for the hook's reason failed that one check and nothing else.
