# M5 notes

M5 builds section 17's "M5 · Workflows, capacity, autonomy" of [`design-v3.html`](design-v3.html) on top of [M1](m1-notes.md) to [M4](m4-notes.md): workflow stages and review gates, capacity pools with the host check and Docker label evidence, plans and auto-dispatch on landing, the terse style block, and the three stage skills. This file records where the design left room, what M5 chose, and what the exit runs showed. Each item names the code that holds it. [`v1-status.md`](v1-status.md) lists every v1 item and where it landed.

## Workflows and stages

- **Workflows are data** (`src/config/workflows.ts`): `[workflows.<id>] stages = [{ id, skill, gate, pools, fresh }]`, where `gate` is `none`, `review` or `merge`. The defaults are the design's `feature`, `fix` and `scout`; a table with the same id replaces one. The checks: at least one stage, unique ids, a merge gate only on the last stage, no review gate on the last stage (it ends in a delivery), and only pools `[capacity]` defines (every run holds `worker` already, so a stage may not list it). A ship's workflow must end in the merge gate and a scout's must not.
- **A run's workflow is frozen at dispatch**: the definition goes into the `run.dispatched` event, so editing `config.toml` never reshapes a running run (`runWorkflow` in `src/lifecycle/stages.ts`). `dispatch --workflow <id>` picks one; the default is the project's (`project add|set --workflow`, which must be a ship workflow), and `scout` for scouts.
- **A stage's state** is `runs.stage_state` (migration 5): `waiting` for its capacity grant, `active`, `review` while its review gate is open, `done` once the last stage delivered. `runs.pending_launch` is the launch a grant must start (`fresh`, `resume`, or `stage` for a fresh stage worker), and `runs.stage_note` the words the stage start carries (a verdict, your changes).
- **The worker's side** (`src/harness/contract-text.ts`, `src/lifecycle/stages.ts`): the task file now starts with the current stage in one paragraph (where it sits in the workflow, the skill and its `SKILL.md` path, the pools it holds, what ends it), and the contract says: stage finished, run `$FLOWRYN_BIN stage done [--review <lavish url>]`, end your turn, and wait for a steer. `stage done` releases the stage's pools and either opens the review gate or requests the next stage; the scheduler starts it and a steer carries its instructions. A Claude worker usually gets that steer at once as its Stop continuation, a Pi worker mid-turn or as a follow-up. `stage show` prints the same instructions on demand.
- **Delivery ends the last stage.** `deliver` from an earlier stage is accepted only when no review gate stands between (the `fix` workflow's `build` stage, say): the delivery finishes the ungated stages at once and holds nothing, since nothing of them is left to run. That keeps every M4 flow working; the contract still tells a worker to run `stage done` first, so a no-mistakes ship holds its `validation` slot while the pipeline runs. A review gate ahead is `wrong_stage` (exit 2), and so is a delivery while the stage waits for capacity.
- **fresh = true** stages start a new worker: the scheduler stops the old harness by its identity, the run gets a new session id, and the launcher (mode `stage`) starts a new session in the same worktree with the stage in its task file. The reconciler leaves a run alone while `pending_launch` is set.
- **Decline** (`src/policy/verbs.ts`) now restarts the last stage through the scheduler: its pools are granted again, the merge gate row records the changes, and a worker that died meanwhile is resumed with your words as its steer.

## Review gates

- **Human-bound, like merges** (`src/policy/gates.ts`). A gate passes only with an approval record (action `gate`, bound to `gate:<id>` and the worktree's HEAD, used once) from a human channel:
  - `flowryn approve <task> --gate <stage>` in your terminal, behind the `/dev/tty` code (cli-tty), and the board's approve key, which now lists open reviews too (board). Both pass the gate as they record it: section 11 names them as the way you pass a gate.
  - The Claude leader's `flowryn gate pass <task>`: its PreToolUse hook records an attempt (action `gate`) and asks, and the ask rule `Bash(flowryn gate pass *)` M3 already wrote is the second layer (claude-ask).
  - The Pi leader's `flowryn_gate_pass` tool: it shows the stage and the review page with `ctx.ui.confirm()` and passes the gate with the approval key on stdin (pi-confirm). The extension blocks `flowryn gate pass` in the shell.
  - Nothing else: a token-less call without the code, a worker, or yolo never passes a review gate (`approval_required`).
- **Every gate prompt shows the plan it would approve** (`pendingPlanLine`): approving the design approves its plan, so `approve --gate`, the board, Claude's prompt and Pi's confirm each name the plan and its phases ("it also approves plan p1, 1 phase that start by themselves once this task lands: …") next to the review page.
- `stage done --review` needs an http(s) or file:// URL; the gate opens a P1 `gate_ready` with the link. `flowryn gate changes <task> --body-file - [--to <stage>]` sends the run back with your words: by default to the nearest earlier stage without a review gate (QA back to build), else to the gated stage itself (the design back to design). It needs no approval, since it only holds work back.
- The merge gate (section 7) is recorded as a `gates` row too: opened at the delivery, passed with the merge's approval when the run lands, sent back by a decline. The merge itself still goes through M4's merge gate.
- `gate pass`, `gate changes` and `approve --gate` wait for one scheduler pass before they answer, so the reply says whether the next stage started or waits for capacity.

## Plans and autonomy

- **A plan is a phased feature** (`src/lifecycle/plans.ts`): an optional `# title`, then one `## <phase>` section per phase, each a ship task. A section may start with `workflow: <id>`, `harness: claude|pi` and `after: <n>[, <n>]`; each phase waits for the one before it unless `after` says otherwise. At most 20 phases.
- **Approving the design approves the plan.** A design worker hands its plan in with `stage done --review <url> --plan-file <path>`; the plan waits, `pending`, on that gate, and its phases are not in the backlog. Passing the gate approves it: each phase becomes a Queued ship in tasks-axi (`add … --blocked-by`), phase 2 blocked by the design's own task. Changes on the gate discard it. `flowryn plan <project> --body-file -` files a plan the leader writes, approved as filed, like a dispatch.
- **Landed** means a run of the task is `cleaned` (merge proven, then cleanup done); a task Flowryn never ran has landed when the backlog shows it done. The blockers come from the backlog's `blocked-by:` dependencies, so a hand edit to them wins (section 8); a phase you hold or park in the backlog waits.
- **Auto-dispatch** (`Scheduler.autoDispatch` in `src/sched/scheduler.ts`): every pass, and at once when a cleanup finishes, each Queued phase of an approved plan whose blockers have all landed starts, in code, when its project's autonomy is `plan`: the run is created waiting for its first grant, the task goes In flight, and an informational P1 says "Phase 2 of 2 in "…" started by itself". A phase that is ready but cannot start (no contract record for the harness version, Herdr down, a tangled checkout) opens one P1 `phase_blocked` until it starts. The same checks as a dispatch apply; a phase never starts on an open PR.
- **Autonomy `manual`** (per project; `[autonomy] default` sets it for new projects) files the phases and starts none: `flowryn dispatch <project> --task <id>` starts one, and refuses with `blockers_not_landed` (exit 2) until its blockers landed.
- **Ad hoc tasks stay manual unless you pass `--auto`**: `dispatch --blocked-by <task> [--auto]` files a one-phase plan, Queued behind those tasks; with `--auto` it starts by itself once they land.
- `flowryn show <plan id>` shows each phase and where it is (`queued, waits for …`, `running · build active`, `cleaned · ship done`).

## Capacity pools and the host check

- **Slots are rows** (`src/sched/pools.ts`): `pool_leases` is rebuilt with its own id (a stage granted again after a release gets a new row) and one live lease per pool and run. A grant re-counts inside its own immediate transaction and refuses rather than overfill, so live leases never exceed a cap.
- **Who holds what**: every run holds a `worker` slot from its first grant until its worker is gone (the run ends, or the reconciler finds its process dead with no resume coming). A stage holds its own pools from its start to its end: `stage done`, or the delivery for the last stage (after that the ship waits for your merge holding only its worker slot). A decline and a resume ask for them again. The migration gives every run that is open at the upgrade its worker lease.
- **The scheduler** (`src/sched/scheduler.ts`) grants in "drain before fill" order: fewest stages left first, then project priority, then how long it waited. A run it cannot grant is skipped, so work that needs a free pool is never held up by work waiting for a full one; nothing reserves a slot for the head of the queue. A pass runs after every change that frees or needs capacity (dispatch, stage done, a gate verdict, delivery, cancel, cleanup, a dead worker, a launch that failed) and every `[sched] pass_ms` (30 s).
- **The host check** (`src/sched/host.ts`) runs before any grant that takes a new slot; a stage that needs none (build after the design) starts regardless. Available memory is free + inactive + speculative pages from `vm_stat`, because macOS keeps free memory as inactive file cache and `os.freemem()` reads a few hundred MB on a healthy machine; load is the 1-minute load average per core. `[capacity.host] probe = <command>` replaces both with a command that prints `{"free_mem_gb": n, "load_per_core": n}` (the tests' and the lab's seam). A result is reused for `host_cache_ms` (5 s); the check is recorded, with an event, only when it flips. While it fails nothing new is granted and running work carries on; work waiting longer than `[sched] wait_alert_ms` (30 min) opens one P1 `capacity_wait`, closed once nothing waits that long.
- `flowryn capacity` shows each pool's live leases over its cap, the host check, the usage-limit pause and the waiting runs in grant order with why each waits; `fleet` has a capacity line and a stage column (`qa review`, `ship waiting`); `show` adds the workflow, the gates and the leases.
- A dispatch answers after one scheduler pass: `launching`, or `waiting for capacity`.

## Docker label evidence

- The visual QA skill tells a worker to label every container `flowryn.run=$FLOWRYN_RUN`, one compose project per environment. The reconciler runs `docker ps --filter label=flowryn.run` on its steady pass (`src/reconcile/docker.ts`; `docker` joins `[tools]`) and records rank-2 evidence per run. An environment is one compose project; a container outside compose counts on its own.
- A live run running more environments than its `docker_env` leases is a divergence. Containers of a run that ended, died or holds no environment lease (a worker that left its QA containers up after `stage done`) are listed in one P1 `docker_leftover` with the `docker rm -f` line; nothing is removed automatically (section 16). Containers labelled for a run this home does not know are not judged. No Docker, or a daemon that does not answer, is skipped.

## The Claude usage limit

- The signals come from Claude Code's hooks reference (checked for this milestone): a turn that ends in `StopFailure` with `error: "rate_limit"` is a claude.ai usage limit (or an API rate limit), and `Notification` with `notification_type: "quota_auto_resume_fired"` (Claude Code 2.1.234 and later) means Claude continued after the reset. No hook input carries the reset time.
- Any Claude session, worker or leader, reporting the limit pauses every Claude launch and stage grant, and every Claude phase's auto-dispatch (`src/sched/usage.ts`), with one P1 `usage_limit`. The pause lifts on `quota_auto_resume_fired`, or on any Claude turn that later ends normally (`Stop`), which proves usage is available again; Pi work carries on throughout. Worker settings gain a `Notification` hook for the three `quota_auto_resume_*` types, and the leader's `Notification` matcher adds them to `idle_prompt`.

## The style block and the stage skills

- `[style]` (`styleBlock`): `terse = false` turns it off; `text = "…"` or `file = "<path>"` replaces the design's text (at most 2,000 characters, since it leads every prompt). The block now leads the worker contract (section 11: "the same block leads every worker's instructions") and is the leader's appended system prompt, as in M3.
- `src/skills/stages.ts` holds `flowryn-design`, `flowryn-build-test` and `flowryn-visual-qa`: descriptions of about 30 words, bodies under 2,000 characters (well inside 60 tokens and 1.5k tokens). The launcher writes them to `<state_dir>/skills/` and loads them into a Claude worker as a plugin (`--plugin-dir`); every stage start names the `SKILL.md` path, so a Pi worker reads the same file (a Pi `--skill` per skill would cost the typed launch line three long paths; M2's 960-byte limit). The design and QA pages live in `$FLOWRYN_REPORT_DIR`, outside the worktree, so a local-only delivery's clean-worktree check is not tripped by review artifacts. QA uses a `chrome-devtools-axi` session named after the run, so five browsers never share one.
- The leader's skill names `plan`, the review gates and `capacity`.

## Protocol and version

`PROTO` is 3 (new verbs and arguments: `stage done`, `gate pass|changes`, `plan`, `capacity`, `dispatch --workflow --blocked-by --auto --task`, `approve --gate`, `hook gate-summary`, and `hook notify` now also taken from workers), so an older CLI in a running worker gets exit 76. The version is 0.4.0.

## Tests

- `test/unit/workflows.test.ts`: the workflow, capacity, autonomy, `[sched]` and style config; plan parsing; the host check's `vm_stat` reading and verdict; Docker line parsing; pool grants never overfilling; stage instructions.
- `test/integration/workflows.test.ts`: a feature through design, review (Claude's prompt), build, visual QA (the Docker and browser slots held, the container counted), review (your terminal) and ship, with every gate row and lease checked; changes at the QA review sent back to build with your words; a delivery refused before a review gate; a fresh-worker stage; the usage-limit pause and its lift, with Pi work unaffected; a manual-autonomy plan and `blockers_not_landed`.
- `test/integration/capacity.test.ts` is the scaled capacity exit (b): 24 ships (half Claude, half Pi fake workers, each a real process through the real CLI, no model calls) against the design's caps on the fake Herdr, with a sampler reading the leases every 50 ms. The host check (fed by a probe file) blocks the first three, the view says why, and the P1 opens after the alert time; once the host recovers they start and the P1 closes. 24 ships then give 20 live workers and 4 waiting for a worker; the 20 builds finish and only 5 get QA (Docker environment and browser); QA drains in waves of 5 into 5 validating ships; two runs end and the two oldest waiting start. Over about 200 samples no pool ever exceeded its cap, and each reached it (worker 20, validation 5, docker_env 5, browser 5). Two smaller tests prove drain before fill (a ship stage takes a freed slot before older build work) and the Docker divergence and leftover P1.
- `test/integration/m5-exit.test.ts` is the M5 exit with fake leaders: a two-phase feature on a Claude leader (the design through Claude's prompt, QA through `flowryn approve --gate qa` in a real pty, merges through Claude's prompt) where phase 2 starts by itself only after phase 1 is cleaned, and on a Pi leader (the shell refused, `flowryn_gate_pass` declined then confirmed, QA passed on the board).
- The fake worker gained `stage-done`, `plan-phase`, `docker-up`, `docker-down` and `usage-limit` steps; after a stage done it ends its turn and carries on when the next steer arrives, which can be the one beside the `stage done` tool result itself. A spooled `stage done` (exit 75, a daemon slower than the CLI's 2 s under the full suite's load) is treated the same way, as the contract says; an earlier version counted it a failure and the capacity test flaked once. The fake Claude leader now matches hook matchers as regular expressions, as Claude does. Test homes get a fake `docker` and a host check that always passes unless a test sets one.

## Live runs

`scripts/lab/m5-live.sh [--claude-project <checkout>] [--seed-contracts] [--keep] [pi] [claude]` runs the exit on real leaders started with `flowryn lead` in panes of a Firstmate lab session (`fm-herdr-lab.sh`), with real workers, one live at a time.

The `pi` flow: a Pi leader and scripted Pi workers in a scratch local-only repository; the design passes through the `flowryn_gate_pass` confirm and QA on the board. The `claude` flow: a Claude leader, phase 1 on a scripted Pi worker and phase 2 on a real Claude worker, in linked worktrees of a checkout Claude trusts (`--claude-project`, with `pretrust = "check"`); the design passes through Claude's permission prompt and QA through `flowryn approve --gate qa` typed in a lab pane. In both, phase 1's design hands in a page and a one-phase plan; visual QA is real (an `nginx:alpine` container labelled with the run, a curl of the page and a `chrome-devtools-axi` screenshot on a session named after the run, while the reconciler counts the container against the run's `docker_env` lease); ship is a local-only delivery; the leader merges; and phase 2 must start by itself. The run answers only the review and merge prompts under test, never a trust dialog, and removes every branch, worktree and container it made. The contract record was seeded (`--seed-contracts`) for the versions M4's live run had verified, Claude Code 2.1.281 and Pi 0.87.1.

Latest run, 2026-09-24, both flows in one daemon, **16/16 passed**: Herdr 0.7.5 (protocol 17), Claude Code 2.1.281 with Haiku as the leader and the phase 2 worker, Pi 0.87.1 with the offline scripted provider, Docker 29.2.1, the host check at `min_free_mem_gb = 4` (the machine had 8.7 GB available and a load of 0.24 per core), in lab session `fm-lab-flowryn-m5-82585-904`, which the helper tore down, checking the default session unchanged. Each flow took about a minute and a half.
