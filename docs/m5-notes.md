# M5 notes

M5 builds section 17's "M5 · Workflows, capacity, autonomy" of [`design-v3.html`](design-v3.html) on top of [M1](m1-notes.md) to [M4](m4-notes.md): workflow stages and review gates, capacity pools with the host check and Docker label evidence, plans and auto-dispatch on landing, the terse style block, and the three stage skills. This file records where the design left room, what M5 chose, and what the exit runs showed. Each item names the code that holds it. [`v1-status.md`](v1-status.md) lists every v1 item and where it landed.

## Workflows and stages

- **Workflows are data** (`src/config/workflows.ts`): `[workflows.<id>] stages = [{ id, skill, gate, pools, fresh }]`, where `gate` is `none`, `review` or `merge`. The built-ins are `feature` (design, build, ship), `feature-ui` (design, build, visual QA, ship: the one that carries visual QA, for work with screens), `fix` and `scout`; a table with the same id replaces one. `feature` had the QA stage until 2026-10-05 (see the last section). The checks: at least one stage, unique ids, a merge gate only on the last stage, no review gate on the last stage (it ends in a delivery), and only pools `[capacity]` defines (every run holds `worker` already, so a stage may not list it). A ship's workflow must end in the merge gate and a scout's must not.
- **A run's workflow is frozen at dispatch**: the definition goes into the `run.dispatched` event, so editing `config.toml` never reshapes a running run (`runWorkflow` in `src/lifecycle/stages.ts`). `dispatch --workflow <id>` picks one; the default is the project's (`project add|set --workflow`, which must be a ship workflow), and `scout` for scouts.
- **A stage's state** is `runs.stage_state` (migration 5): `waiting` for its capacity grant, `active`, `review` while its review gate is open, `done` once the last stage delivered. `runs.pending_launch` is the launch a grant must start (`fresh`, `resume`, or `stage` for a fresh stage worker), and `runs.stage_note` the words the stage start carries (a verdict, your changes).
- **The worker's side** (`src/harness/contract-text.ts`, `src/lifecycle/stages.ts`): the task file now starts with the current stage in one paragraph (where it sits in the workflow, the skill and its `SKILL.md` path, the pools it holds, what ends it), and the contract says: stage finished, run `$FLOWRYN_BIN stage done [--review <lavish url>]`, end your turn, and wait for a steer. `stage done` releases the stage's pools and either opens the review gate or requests the next stage; the scheduler starts it and a steer carries its instructions. A Claude worker usually gets that steer at once as its Stop continuation, a Pi worker mid-turn or as a follow-up. `stage show` prints the same instructions on demand.
- **Delivery ends the last stage, and the caps are the contract.** `deliver` from an earlier stage is accepted only when no review gate stands between (the `fix` workflow's `build` stage, say). A stage it would skip that holds pools is never finished for free. How that works depends on the delivery mode:
  - **no-mistakes**: the pipeline runs before `deliver --pr` (the PR comes from it), so the pipeline must run under the ship stage's `validation` slot. The worker starts that stage first with `flowryn stage begin <last stage>` (`beginLastStage` in `src/lifecycle/stages.ts`). It ends the current stage and requests the last one, which the scheduler grants for this run only. It returns once the stage has started, or refuses with `stage_waiting` (exit 2) while the pool is full. The worker then ends its turn, and the steer that starts the stage says so. The contract names the workflow's actual last stage and says whether it holds a slot. `deliver --pr` is refused with `stage_waiting` unless that stage was already active before the call; it is never granted at delivery time. The pipeline start itself is observed and flagged, but not blocked. When the delivery watcher sees no-mistakes go active on the run's branch while its last stage is not active and it holds no `validation` slot, it opens one P1, `validation_outside_cap` (`flagOutsideCap` in `src/reconcile/delivery.ts`). The refusal is the backstop: a pipeline run outside the cap cannot deliver until the worker holds the slot.
  - **Runs open across the upgrade** are exempt from both. Migration 5 marks the workflow it freezes for them `legacy_m4`, since their workers were given M4's contract (pipeline, then `deliver`, no `stage begin`). Such a ship's slot is granted at delivery time, as for local-only and direct-PR, and its pipeline is not flagged.
  - **local-only and direct-PR**: nothing runs under the slot before the delivery, so the skipped pooled stage is requested and granted at once for this run (`startPooledStages`), on the same pools and host check as any grant, with no steer. If it cannot be granted at once, `deliver` is refused with `stage_waiting`, and the steer that starts the stage tells the worker to deliver again. M4's flows work unchanged while the pools are free.
  - Either way, `deliver` checks its flags before changing any stage, so a malformed call changes nothing. A single-run grant (`Scheduler.grantNow`) never runs a full pass: no auto-dispatch, no other run's launch. Work nearer shipping, or older work, that needs the same pool keeps its turn. Stages without pools are still finished at once. A review gate ahead is `wrong_stage` (exit 2), and so is a delivery while the stage waits for capacity.
- **Runs open before M5** keep the contract their worker was given: migration 5 freezes `runs.workflow_def` for every open run (a ship: `build` then `ship`, the ship stage holding `validation` and ending at the merge gate; a scout: `investigate`; both marked `legacy_m4`), and `runWorkflow` reads it before the dispatch event. Without it, an M4 run of a `feature` project would sit at `build`, 2 of 4, and its delivery would be refused for the `qa` review it was never told about.
- **fresh = true** stages start a new worker: the scheduler stops the old harness by its identity, the run gets a new session id, and the launcher (mode `stage`) starts a new session in the same worktree with the stage in its task file. The reconciler leaves a run alone while `pending_launch` is set.
- **Decline** (`src/policy/verbs.ts`) now restarts the last stage through the scheduler: its pools are granted again, the merge gate row records the changes, and a worker that died meanwhile is resumed with your words as its steer.

## Review gates

- **Human-bound, like merges** (`src/policy/gates.ts`). A gate passes only with an approval record (action `gate`, bound to `gate:<id>` and the worktree's HEAD, used once) from a human channel:
  - `flowryn approve <task> --gate <stage>` in your terminal, behind the `/dev/tty` code (cli-tty), and the board's approve key, which now lists open reviews too (board). Both pass the gate as they record it: section 11 names them as the way you pass a gate.
  - The Claude leader's `flowryn gate pass <task>`: its PreToolUse hook records an attempt (action `gate`) and asks, and the ask rule `Bash(flowryn gate pass *)` M3 already wrote is the second layer (claude-ask). The attempt records the gate the prompt showed (`gate:<id>`), and the pass is refused when another gate is open by then (sent back and reopened).
  - The Pi leader's `flowryn_gate_pass` tool: it shows the stage and the review page with `ctx.ui.confirm()` and passes the gate with the approval key on stdin (pi-confirm), naming the gate it showed (`--gate-id g<n>`). `gate pass` refuses a `--gate-id` that is no longer the open gate. The extension blocks `flowryn gate pass` in the shell.
  - Nothing else: a token-less call without the code, a worker, or yolo never passes a review gate (`approval_required`).
- **Every gate prompt shows the plan it would approve** (`pendingPlanLine`): approving the design approves its plan, so `approve --gate`, the board, Claude's prompt and Pi's confirm each name the plan and its phases ("it also approves plan p1, 1 phase that start by themselves once this task lands: …") next to the review page.
- `stage done --review` needs an http(s) or file:// URL; the gate opens a P1 `gate_ready` with the link. `flowryn gate changes <task> --body-file - [--to <stage>]` sends the run back with your words: by default to the nearest earlier stage without a review gate (QA back to build), else to the gated stage itself (the design back to design). It needs no approval, since it only holds work back.
- The merge gate (section 7) is recorded as a `gates` row too: opened at the delivery, passed with the merge's approval when the run lands, sent back by a decline. The merge itself still goes through M4's merge gate.
- `gate pass`, `gate changes` and `approve --gate` wait for one scheduler pass before they answer, so the reply says whether the next stage started or waits for capacity.

## Plans and autonomy

- **A plan is a phased feature** (`src/lifecycle/plans.ts`): an optional `# title`, then one `## <phase>` section per phase, each a ship task. A section may start with `workflow: <id>`, `harness: claude|pi` and `after: <n>[, <n>]`; each phase waits for the one before it unless `after` says otherwise. At most 20 phases.
- **Approving the design approves the plan.** A design worker hands its plan in with `stage done --review <url> --plan-file <path>`; the plan waits, `pending`, on that gate, and its phases are not in the backlog. Passing the gate approves it: each phase becomes a Queued ship in tasks-axi (`add … --blocked-by`), phase 2 blocked by the design's own task. Changes on the gate discard it. `flowryn plan <project> --body-file -` files a plan the leader writes, approved as filed, like a dispatch.
- **Landed** means the task's latest run is `cleaned` (merge proven, then cleanup done); a task Flowryn never ran has landed when the backlog shows it done. Only the latest run counts: a scout promoted to a ship keeps its cleaned scout run, but the promotion starts the ship run in the same transaction, so the task lands only when the ship does (a dependent started on the scout's landed report before 2026-10-05). The blockers come from the backlog's `blocked-by:` dependencies, so a hand edit to them wins (section 8); a phase you hold or park in the backlog waits.
- **Auto-dispatch** (`Scheduler.autoDispatch` in `src/sched/scheduler.ts`): every pass, and at once when a cleanup finishes, each Queued phase of an approved plan whose blockers have all landed starts, in code, when its project's autonomy is `plan`: the run is created waiting for its first grant, the task goes In flight, and an informational P1 says "Phase 2 of 2 in "…" started by itself". A phase that is ready but cannot start (no contract record for the harness version, Herdr down, a tangled checkout) opens one P1 `phase_blocked` until it starts. The same checks as a dispatch apply; a phase never starts on an open PR.
- **Autonomy `manual`** (per project; `[autonomy] default` sets it for new projects) files the phases and starts none: `flowryn dispatch <project> --task <id>` starts one, and refuses with `blockers_not_landed` (exit 2) until its blockers landed.
- **Ad hoc tasks stay manual unless you pass `--auto`**: `dispatch --blocked-by <task> [--auto]` files a one-phase plan, Queued behind those tasks; with `--auto` it starts by itself once they land. A blocker must be a ship: a scout never lands, so a task behind one would wait forever, and dispatch refuses it (`bad_args`). `dispatch <project> --task <id> --sensitive` starting a Queued task marks it sensitive; a start never clears the mark.
- `flowryn show <plan id>` shows each phase and where it is (`queued, waits for …`, `running · build active`, `cleaned · ship done`).

## Capacity pools and the host check

- **Slots are rows** (`src/sched/pools.ts`): `pool_leases` is rebuilt with its own id (a stage granted again after a release gets a new row) and one live lease per pool and run. A grant re-counts inside its own immediate transaction and refuses rather than overfill, so live leases never exceed a cap.
- **Who holds what**: every run holds a `worker` slot from its first grant until its worker is gone (the run ends, or the reconciler finds its process dead with no resume coming). A stage holds its own pools from its start to its end: `stage done`, or the delivery for the last stage (after that the ship waits for your merge holding only its worker slot). A decline and a resume ask for them again. The migration gives every run that is open at the upgrade its worker lease.
- **The scheduler** (`src/sched/scheduler.ts`) grants in "drain before fill" order: fewest stages left first, then project priority, then how long it waited. A run it cannot grant is skipped, so work that needs a free pool is never held up by work waiting for a full one; nothing reserves a slot for the head of the queue. A pass runs after every change that frees or needs capacity (dispatch, stage done, a gate verdict, delivery, cancel, cleanup, a dead worker, a launch that failed) and every `[sched] pass_ms` (30 s). A pass runs auto-dispatch, the grants and the alerts each on its own, and each ready phase on its own: a phase that cannot start (its run cannot be created, say its worktree path is already there) gets one P1 `phase_blocked` and the pass carries on, so it never holds up a grant. A tangled primary checkout records its `dispatch.refused` event with its one P1, not again on every retry.
- **The host check** (`src/sched/host.ts`) runs before any grant that takes a new slot; a stage that needs none (build after the design) starts regardless. Available memory is free + inactive + speculative pages from `vm_stat`, because macOS keeps free memory as inactive file cache and `os.freemem()` reads a few hundred MB on a healthy machine; load is the 1-minute load average per core. `[capacity.host] probe = <command>` replaces both with a command that prints `{"free_mem_gb": n, "load_per_core": n}` (the tests' and the lab's seam). A result is reused for `host_cache_ms` (5 s); the check is recorded, with an event, only when it flips. While it fails nothing new is granted and running work carries on; work waiting longer than `[sched] wait_alert_ms` (30 min) opens one P1 `capacity_wait`, closed once nothing waits that long.
- `flowryn capacity` shows each pool's live leases over its cap, the host check, the usage-limit pause and the waiting runs in grant order with why each waits; `fleet` has a capacity line and a stage column (`qa review`, `ship waiting`); `show` adds the workflow, the gates and the leases.
- A dispatch answers after one scheduler pass: `launching`, or `waiting for capacity`.

## Docker label evidence

- The visual QA skill tells a worker to label every container `flowryn.run=$FLOWRYN_RUN`, one compose project per environment. The reconciler runs `docker ps --filter label=flowryn.run` on its steady pass (`src/reconcile/docker.ts`; `docker` joins `[tools]`) and records rank-2 evidence per run. An environment is one compose project; a container outside compose counts on its own.
- A live run running more environments than its `docker_env` leases is a divergence. Containers of a run that ended, died or holds no environment lease (a worker that left its QA containers up after `stage done`) are listed in one P1 `docker_leftover` with the `docker rm -f` line; nothing is removed automatically (section 16). Containers labelled for a run this home does not know are not judged. No Docker, or a daemon that does not answer, is skipped.

## The Claude usage limit

- The signals come from Claude Code's hooks reference (checked for this milestone): a turn that ends in `StopFailure` with `error: "rate_limit"` is a claude.ai usage limit (or an API rate limit), and `Notification` with `notification_type: "quota_auto_resume_fired"` (Claude Code 2.1.234 and later) means Claude continued after the reset. No hook input carries the reset time.
- Any Claude session, worker or leader, reporting the limit pauses every Claude launch and stage grant, and every Claude phase's auto-dispatch (`src/sched/usage.ts`), with one P1 `usage_limit`. The pause lifts on `quota_auto_resume_fired`, or on any Claude turn that later ends normally (`Stop`), which proves usage is available again; Pi work carries on throughout. Worker settings gain a `Notification` hook for the three `quota_auto_resume_*` types, and the leader's `Notification` matcher adds them to `idle_prompt`.
- Those signals need a live Claude session, and while paused none may start, so the pause also expires. With no reset time in any hook input, it backs off: `[sched] usage_backoff_ms` (15 min), doubling on each re-arm up to `usage_backoff_max_ms` (2 h). Once it expires the scheduler lets exactly one Claude start through as a probe (a waiting run's grant, or one Claude phase's auto-dispatch), recorded as `sched.usage_probe`: the probe's normal `Stop` lifts the pause, and a `rate_limit` after expiry re-arms it with the next backoff and rewrites the same P1. A probe that dies, or runs longer than the backoff, frees the slot for another.
- `flowryn capacity resume --harness claude` lifts it at once: human-only, like `approve` (a leader or worker token gets `human_only`), with a `sched.usage_resumed` event of source `cli`, resolving the P1. The P1 names that command and the expiry time; `flowryn capacity` shows the expiry or the probe, and hints the command while paused.

## The style block and the stage skills

- `[style]` (`styleBlock`): `terse = false` turns it off; `text = "…"` or `file = "<path>"` replaces the design's text (at most 2,000 characters, since it leads every prompt). The block now leads the worker contract (section 11: "the same block leads every worker's instructions") and is the leader's appended system prompt, as in M3.
- `src/skills/stages.ts` holds `flowryn-design`, `flowryn-build-test` and `flowryn-visual-qa`: descriptions of about 30 words, bodies under 2,500 characters (well inside 60 tokens and 1.5k tokens; `flowryn-visual-qa` also writes `evidence-template.html` next to its `SKILL.md`). The launcher writes them to `<state_dir>/skills/` and loads them into a Claude worker as a plugin (`--plugin-dir`); every stage start names the `SKILL.md` path, so a Pi worker reads the same file (a Pi `--skill` per skill would cost the typed launch line three long paths; M2's 960-byte limit). The design and QA pages live in `$FLOWRYN_REPORT_DIR`, outside the worktree, so a local-only delivery's clean-worktree check is not tripped by review artifacts. QA uses a `chrome-devtools-axi` session named after the run, so five browsers never share one.
- The leader's skill names `plan`, the review gates and `capacity`.

## Notifications: on in your setup, never from tests or live runs

- Found while running M5: every daemon that tests and the live runs started posted real macOS notifications, because `[notify] macos` defaults to on (M3). The default stays on, so a config written before this change (M3's init wrote `[notify]` without `macos`) keeps notifying; the protection is carried by the test and live-run isolation below instead (`src/config/leader.ts`).
- `flowryn init` asks whether to post macOS notifications (the default answer is the current value, else yes) and writes `macos` explicitly. A re-run fills in every key an existing table lacks, at any depth, and keeps every current value, so an old `[notify]` gains `macos` rather than being replaced or left as is (`withMissingDefaults` in `src/init/init.ts`). `flowryn doctor` warns when `[notify]` has no `macos` key.
- `FLOWRYN_NOTIFY=off` (or `FLOWRYN_NOTIFIER=null`) overrides the config for everything that is not your setup: the daemon still decides and records each notification (the `notifications` rows and events are unchanged, which M3's attention tests and live run read), but delivers none on any channel. The test preload, the test harness's homes, the contract suites' scratch daemons, the fixture runners, `spikes/lib/lab.sh` and every `scripts/lab/m*-live.ts` set it. `FLOWRYN_NOTIFIER=record:<path>` makes the macOS channel append to a file instead of running osascript; the harness sets it too, as a second guard.
- Every launcher of a daemon for testing refuses to start one without `FLOWRYN_NOTIFY=off` (`requireNotificationsOff` in `src/config/leader.ts`): the harness's `startDaemon`, the daemon lifecycle tests' direct spawn, the contract runner and `scripts/lab/m2-live.ts` to `m5-live.ts`. A forgotten override fails loudly instead of notifying. The fixture runners start no daemon.
- `test/helpers/no-notifications.ts` is preloaded for every test file (`bunfig.toml`): it sets `FLOWRYN_NOTIFY=off` for the test process, refuses any osascript spawn in it, and fails the run if one was attempted. `test/unit/notify-guard.test.ts` checks the default, the override (a daemon with `macos = true` records its P0 notification and delivers none), the launcher refusal, the recorder, and the in-process refusal; `test/unit/setup.test.ts` checks init's explicit `macos`, its fill-in of missing keys, and the doctor warning.

## The v1 completion pass

After M5, one pass built every v1 item [`v1-status.md`](v1-status.md) still listed as not built or partly built. This section records where the design left room and what the pass chose.

### The harness version gate (sections 5 and 16)

- `src/lifecycle/harness-gate.ts` checks the installed version (the `[tools]` binary's `--version`, cached until the binary changes) against `harness_contracts`. The daemon checks every harness in use (named by a project, an open run or a queued plan phase) at startup, before its first reconcile pass; dispatch checks it as before; so does `flowryn resume`, the reconciler before its one automatic resume and before retrying a launch that never finished, and the scheduler before any grant that launches a worker (a first launch after a capacity wait, a resume, a fresh stage worker, a relaunch).
- An untested version refuses (`contract_unverified`, the doctor command as help) and opens one P1 `harness_unverified` naming `flowryn doctor --contracts --harness <h>`, once per harness version: a dismissed one is not reopened for the same version, and a later untested version opens its own. It resolves when the installed version is verified (a startup check, or `contracts.record` for that version).
- **The automatic resume waits rather than fails.** A worker that dies on an untested version has its one resume claimed at once (so a second death is still "a failure needing you"), is marked dead, gives its slots back, and waits with `pending_launch = resume`; the scheduler launches it, into the same session, once the version passes. `flowryn capacity` says why it waits.

### Divergences (section 8)

- A divergence is a **backlog divergence** when its lower source is the backlog: a hand edit the watcher saw, or a violation the invariant pass found. Only these have an edit to accept. `flowryn divergence resolve <id> keep-run|accept-edit` (`src/lifecycle/divergences.ts`):
  - **keep-run** writes the runs' state back through the journal: a live run's task goes back In flight (`start`, or `add … --start` with the title and text it was dispatched with when you deleted it); a task with no live run gets what its last run left: `done` with its link for a cleaned run, parked (`reopen`, `hold --kind parked`) for a failed or cancelled one, `reopen` when Flowryn never ran it.
  - **accept-edit** lets your edit stand. A live run is cancelled with its worker stopped and verified gone first, its worktree kept for `flowryn cleanup`, and no backlog write at all (not the parked hold a `cancel` adds). With no live run, nothing changes, and the invariant pass does not raise the same violation again while the task reads the same.
- A divergence between evidence sources (GitHub against the worker, a process against its run, a pane label, Docker against a lease) takes only keep-run, which closes it with the run as it is; the same observation does not reopen it. accept-edit is `bad_args`. Those divergences also still close by themselves as before (a new delivery settles a GitHub one).
- The row and its P1 always close together, with a `divergence.resolved` event naming the resolution and who chose it. A backlog divergence's P1 line names the command; `flowryn show d<N>` shows one.

### The invariant pass (section 8)

- `src/reconcile/invariant.ts` runs on every full reconcile pass (startup, reconnect, the steady pass), after the backlog watcher has diffed any unseen edit and only while the snapshot's hash matches the file. It reads the snapshot inside its transaction, which is where the journal marks an intent applied, and skips every task with a pending intent, so it never judges a state that is about to change.
- A live run whose task is not In flight, or is missing, is a divergence (unless one is already open for that task); so is a task In flight with no live run. The watcher still flags a hand edit as it happens; the pass catches the rest, such as an edit to a run that already had a divergence of another kind open, or a task put In flight by hand.
- A backlog divergence whose task agrees with the runs again closes by itself (resolution `agrees`): the reconciler seeing the resolution happen elsewhere (section 9).

### Scouts land with their report (section 8)

- **A scout's workflow ends in no gate, so its verified report lands it.** Section 8's table puts a delivered report in `ready`, but `ready` is where a ship waits for its merge gate; a scout has none, and M5 already refuses a scout workflow that ends in one. So `deliver --report` records the report, links it in the backlog and moves the run to `landed`, and the delivery watcher's pass cleans it up through the cleanup guard, as after a proven merge (a clean scout worktree is `scout_clean`): the worker stops, the worktree and branch go, the run is `cleaned`, and the task is done with `--report data/<task>/report.md`.
- The `report_ready` P1 is not settled by the cleanup: it stays open until the report is read (`flowryn dismiss`, or a promotion), and `fleet` says `read` for the cleaned scout meanwhile. A scout that leaves uncommitted work is refused by the guard: it stays `landed`, its worktree kept, with a P1 ("Report delivered, but cleanup refused") naming `flowryn cleanup`.
- A scout that delivered under an earlier version and sits in `ready` is landed by the delivery watcher's next pass. The delivery watcher ignores kicks until it has started, so a report ingested from the spool at startup is cleaned only after the reconciler's startup pass has reattached the worker.

### `flowryn promote` (sections 4 and 12)

- **In place means the same task**: it keeps its id, its backlog entry and its report, and takes the project's ship policy (delivery mode, yolo, workflow, or `--workflow`); `--sensitive` marks it. Two cases (`src/lifecycle/promote.ts`):
  - **A scout at work** keeps its run, worker, worktree and branch. It cannot become a ship by a steer alone: its contract is in its system prompt and its Claude sandbox settings do not let it commit. So its run takes the ship workflow (frozen in `runs.workflow_def`), its first stage is requested with `pending_launch = relaunch`, and the scheduler stops the worker by its identity and resumes the same session (`claude --resume`, Pi's `--session-id`) under a ship's contract, sandbox settings and task file. The context it built survives; the task file carries the promotion: your words, what to keep on the branch (only the change, no scratch commits or debug output, a reproduced bug as a regression test) and the ship's delivery. A scout still waiting for its first launch simply launches as a ship.
  - **A scout whose run is over** (cleaned, cancelled or failed) becomes a ship on the same task: it goes back In flight (a parked hold is lifted) and a new run starts in a fresh worktree from the default branch, checked as a dispatch is, with a task file that names the report and quotes the scout's task.
- A landed scout still being cleaned up is `not_ready` until it is cleaned; a cancelled or failed scout whose worktree is still there is cleaned up first (`not_ready`, naming `flowryn cleanup`).

### Herdr unreachable (section 16)

- `src/reconcile/herdr-health.ts` keeps one outage episode in meta, from the first socket error (the event subscription failing to connect or closing, a dispatch's ping, a deferred launch) until Herdr answers again, so a daemon restart mid-outage continues it. Its one P1 `herdr_unreachable` opens once the episode has lasted `[herdr] unreachable_alert_ms` (60 s) and something needs Herdr: an open run, or a dispatch, launch or plan phase it held up. A Herdr that is merely not running while the fleet is idle raises nothing until you dispatch. The P1 resolves when the subscription connects again; a dismissed one is not reopened in the same episode.
- The subscription retries with its backoff (1 s to 30 s) and, when no socket was found at startup (Herdr started after the daemon), looks for the session again each time, so the daemon no longer needs a restart to find Herdr.
- Test homes without a fake Herdr set `unreachable_alert_ms` to a day: they have no Herdr by design.

### GitHub unavailable or rate-limited (section 16)

- `src/reconcile/forge-health.ts`: a failed read of the kinds that mean GitHub cannot be asked (unreachable or a 5xx, rate-limited, a refused token, nonsense answers) starts an outage; its one P1 `forge_unavailable` opens only while a merge waits on GitHub (a delivered PR at the merge gate, `ready`, or a merge waiting for its proof, `merging`), and names them. The delivery watcher's poll only runs over such ships, and a `flowryn merge` refused for the outage records it too. It resolves when GitHub answers again, or when no merge waits any more (then a merge that comes to wait in the same outage raises it again).

## Idle workers (2026-10-05 fixes)

Two live bugs, both on a Claude worker idle behind a review gate overnight.

- **The idle pointer re-fired every pass.** `worker_idle` was guarded only by "no item open", so each dismissal reopened it on the next pass or kick, with a `run.idle_alert` event every time. It now opens once per idle episode (`src/lifecycle/idle-alert.ts`): any `worker_idle` item opened since the episode began, dismissed or not, holds it until `[reconcile] idle_realert_ms` (4 h) after it opened. The episode starts at the later of the Stop, the current stage's start and the run's latest answered question, so a gate that passes after hours does not alert at once. No pointer opens while the worker waits on others (a review gate or blocking question, any open question of its own, a stage waiting for capacity), and an open one is resolved when that starts. The stale-hook pointer shares the same once-per-episode rule, keyed on the last hook.
- **A steer to an idle worker was never delivered.** The asyncRewake waiter lives at most 8 h (`WAITER_TIMEOUT_S`, the CLI's `WAITER_MAX_MS`) and only the worker's own prompt and Stop hooks arm it; the live steer arrived 8.3 h into the idle stretch, after it had expired. A waiter also exits on `protocol_mismatch`, so a daemon on a new protocol loses them all. The daemon cannot arm a Claude hook, so the reconciler now has an idle-carry fallback (`src/lifecycle/idle-carry.ts`, decided with the user, q2): an idle Claude run with a due steer, no waiter on the bus, no `blocked_prompt` item, and Herdr reading `idle`/`done` on every pass for `[reconcile] waiter_grace_ms` (20 s, at least two passes) gets the fixed `steerPointer` line typed into its pane (`pane.send_text`, then Enter, the lab's own composer pattern), after one more status read right before the keys. The ring is `path: keys`, an idle carry, so it must be seen within `seen_timeout_ms` or it rings again; the new turn's prompt hook arms a fresh waiter. A refused re-check is a `steer.idle_carry_refused` event, a failed one `steer.idle_carry_failed`. A live waiter that reconnects to a restarted daemon registers well within the grace and takes the steer instead. Remaining risk: a draft you half-typed into the worker's composer gets the pointer appended.
- Tests: `test/integration/idle-worker.test.ts`; the fake worker's `FAKE: no-waiter` never arms a waiter and wakes only on a line the fake Herdr's `pane.send_text` and Enter typed.


## Turn-end guard (autonomy spec 2, ship A)

A worker that ended its turn without an outcome sat idle until the 15 min `worker_idle` pointer and a leader turn. Now the turn end itself catches it (`src/lifecycle/turn-end-guard.ts`, called from the worker Stop hook in `src/lifecycle/hooks.ts`). Deterministic: database reads and a fixed string, no model.

- **The rule.** At a worker's turn end with no steer taken, the daemon sends `TURN_END_REMINDER` ("You ended your turn without an outcome. Finish with one of: stage done, deliver, ask --blocking, report blocked, fail.") when all hold: no steer is due (a due steer wins: Claude's Stop continuation takes it first, Pi's long poll delivers it); fewer than `MAX_CONTINUATIONS` (2) Stop continuations used on this turn, the reminder counting as one; nothing the worker waits on (the run is `running`, its stage `active`, no `pending_launch`, no open question of its own, no open `blocked_prompt`, no background job of its own still running, and the episode's instruction is not a steer sent with `--end-turn`: so a scout or stage waiting on a grant never gets one); no outcome event since its last instruction; and no reminder yet in this episode.
- **Episode and outcome.** The last instruction is the latest of the run's start, its worker start (launch or resume), its current stage's start, and the first carry of any steer to it. An outcome is a `stage.done`, `stage.requested` (stage begin), `stage.delivered`, `run.delivered`, `decision.opened` (ask), `worker.report` (any status, so `report progress` counts) or `worker.failed` event of the run since then.
- **Delivery.** Claude: the Stop hook's `hookSpecificOutput.additionalContext`, the channel steers already use (M0 c06: non-error feedback, the turn continues), not `decision: "block"`; the run stays busy. Pi: `hook stop --json` returns `context`, and the extension sends it as a `followUp` with `triggerTurn` (M0 p16); the run goes idle meanwhile and the follow-up turn reports busy itself.
- **No loop, and `stop_hook_active`.** A Stop of a turn the waiter woke reads `stop_hook_active=true` (M0 c14), so skipping those Stops would skip nearly every steer-woken turn. The flag is recorded in the reminder's payload and not used to decide; the once-per-episode record and the continuation cap bound the guard.
- **Ignored.** A second outcome-less turn end in the episode gets nothing; the `worker_idle` pointer that opens later (same timing and once-per-episode rule) reads "Worker for X got the turn-end reminder, ended its turn again, and has been idle Nm without an outcome" (it read "ignored the turn-end reminder and has been idle Nm without an outcome" until the misfire fix below), and its `run.idle_alert` payload has `ignored_reminder: true`. A new instruction starts a new episode, which can earn a new reminder.
- **Recorded.** `run.turn_end_reminder` {episode_from, harness, stop_hook_active} for each one sent; `run.turn_end_reminder_result` {reminder_seq, obeyed, outcome} at the run's next turn end: obeyed when an outcome event or a wait followed it (`outcome` names it), ignored otherwise. A reminder with no result means the run never reached another turn end (interrupted, crashed, ended). These feed the triage-runner decision (k4). Counting them:

  ```sql
  SELECT json_extract(payload, '$.obeyed') AS obeyed, COUNT(*) FROM events
   WHERE kind = 'run.turn_end_reminder_result' GROUP BY 1;
  ```
- **Contract.** The worker contract's stage line adds: "Ending a turn to wait on your own background job or agent is fine; any other turn ended with no outcome brings one reminder." (on that line: the contract stays under 30 lines). Remaining known false positive, bounded by the once-per-episode cap: a worker that answers a status steer in text gets one reminder (the leader can send such a steer with `--end-turn`).

## Gate questions

A review page used to list its open questions as prose that Flowryn never saw: you got a page to pass or send back, and your answers reached the worker only if you typed them again. Now the worker hands its questions in as data, Flowryn makes each one a decision reserved for you as the gate opens, and you answer either on the page or through the leader. The first answer counts. Nothing on this path asks a model to decide anything: a JSON file, a fixed template, a fixed pattern on the poll output, and the database. The worker's own judgement (what is truly a question) is the only model work, and the ask rule below bounds it in code.

- **The ask rule** (`src/harness/contract-text.ts`, `src/skills/stages.ts`): the worker contract says to work autonomously, decide everything you can, record each choice and why (design page or PR), and ask only when you truly cannot proceed. Code checks the shape of every question (`src/lavish/questions.ts`): it names the choice it blocks (`blocks`, 10 to 200 chars), a choice has 2 to 8 distinct short options and a recommendation among them (a multi choice: a non-empty subset), a text question carries the worker's default answer, at most 5 per gate, no two blocking the same choice. A bad file is refused whole and nothing opens. The worker lists what it decided itself under `decided`; the page shows it read-only, and a disagreement is a `gate changes`. `flowryn ask` now requires `--blocks` too, stored in `decisions.blocks` and shown on the item.
- **Hand-in** (`src/lifecycle/stages.ts`, `src/lifecycle/gate-questions.ts`): `stage done --review <url> --page <html> --questions-file <json>`, on any stage with a review gate (design and qa). `--page` must be a regular `.html` (no symlink) under `$FLOWRYN_REPORT_DIR` that, with questions, mounts the widget: `<section id="flowryn-questions"></section><script src="flowryn-questions.js"></script>`, with `data-lavish-live-reload-root` on `<html>`. In the transaction that opens the gate, each question becomes a run-scoped `q<N>` (origin `gate:<g>`, `kind` single, multi or text, `gate_id`, `note` = the worker's why), reserved "a review question for the user", with a P1 `worker_question` item that names the relay command. So the leader sees and relays them even when you cannot open localhost.
- **The widget** (`src/lavish/widget.ts`): the daemon writes `flowryn-questions.js` beside the page: a fixed renderer and the gate's state as JSON. It follows lavish-axi's `input` playbook: radios with the recommendation preselected, checkboxes for a multi choice, a text field (the default as its placeholder), an optional note each, and one Submit that queues one prompt per answered question (`queueKey flowryn:<q>`) and sends them (`sendQueuedPrompts`). Each prompt ends in `flowryn-answer v1 <base64url JSON {g, d, c, n}>`. The daemon rewrites the file whenever a question's state changes, so an answered question shows locked with who answered. A closed gate's widget is written once more, all locked.
- **The poll** (`src/lavish/poller.ts`, `src/lavish/poll-output.ts`): for each open gate with a page (at first only with an open question; see "Worker questions wake the leader"), the daemon keeps one `lavish-axi poll <page>` running (`[tools] lavish_axi`). On return it records each answer line through `lavishAnswer` (`src/lifecycle/decision-verbs.ts`, the only path beside `captainChannel` that records `answered_by = captain`, here `via lavish`). An answer counts only for an open question of that gate while the gate is open. Anything else (already answered by the leader's relay, a stale page from an earlier gate, a choice the question does not offer) becomes a `decision.lavish_ignored` event. The poll consumes everything you sent, so other prompts (annotations, chat) are appended to `lavish-notes-<gate>.txt` beside the page, and the verdict steer points the worker at that file. After recording, the next poll passes `--agent-reply` with what Flowryn did ("Flowryn recorded your answer to q1, q3. 1 question still open.", a late or invalid answer named, "Every question is answered; the review now waits for your pass in Flowryn."). Once nothing is left to poll for, one short poll (`--timeout-ms 1500`) carries the last reply. Without it Lavish's conversation spins on "Working…" for good: the visual QA found that. A failed poll backs off from 2 s, doubling to a minute. `session_ended`/`status: ended` (Send & End) stops it for good (`gates.lavish_ended`), and the leader path still works. A daemon restart rebuilds the polls from `gates`. Each running poll's pid is kept in `<state_dir>/lavish-polls/<gate>.json`. A daemon that died without its shutdown (a crash, `kill -9`) leaves its polls running, and an orphaned poll would take your answers with nothing reading them. So the next daemon first stops every recorded pid whose command line is still that page's poll. The visual QA found this through the test homes' leftover stand-ins. Killing a poll loses nothing, because Lavish puts feedback back when a poll's request closes. Without lavish-axi the decisions still open and only the poll is off.
- **Answers and verdicts**: answers are held while the gate is open (no steer wakes an idle worker that could only end its turn). Cancelling the run or promoting the scout closes them the same way, and so does the run ending for good: its cleanup, or a new run of the same task (`answered_via` says which: `gate changes`, `run cancelled`, `promoted`, `run ended`). Until then a failed run keeps them open, so a resumed run's gate still refuses until the user answers, and the daemon polls the page again once the run is live. `flowryn dismiss` refuses a review question's item: only the user answers it.

### One Send, Other, anything else, request pass

Review pages still showed questions as prose when a worker skipped the widget, and the widget sent one prompt per answer. The user: "It would make it way easier to just click instead of annotating every time." The fix is plain code again: the fixed renderer, a fixed token, the same regex on the poll output, the database. No model, since nothing here needs judgement.

- **One Send** (`src/lavish/widget.ts`): "Send answers" queues one prompt for the whole gate (`queueKey flowryn:<gate>`): a readable line per answer, then one line `flowryn-answers v2 <base64url JSON {g, a: [{d, c, n}], m, p}>`. `m` is the "anything else for the worker" box, `p` the pass request. `src/lavish/poll-output.ts` decodes v2 all or nothing (one bad answer makes the token malformed) and still decodes v1, for a page loaded before the daemon was upgraded. The token bound is 60,000 characters (5 answers, their notes, and a 4,000-char comment). The mark and its version must match (`flowryn-answer v1`, `flowryn-answers v2`).
- **Other** (`src/lavish/questions.ts`): every single or multi question also offers `other`. It counts only with the user's words: the question's note on the page, or `--words`/`--body-file` on `flowryn decide q<N> other --by captain`. The answer is stored as `other` (a multi choice: last, "a, other"), and the words verbatim as the decision's rationale. The verdict steer says `[their words: …]`. A worker option called "other" is refused, because it is reserved.
- **Anything else**: kept verbatim (control characters cleaned) in `gates.comment` (migration 12), each Send appended (4,000 characters for all Sends together), with a `gate.comment` event. A comment for a closed gate is not kept, and the reply says so.
- **Request pass**: "Send and request pass" is refused on the page until every open question has an answer, and the daemon checks again after recording the Send's answers (`requestGatePass`, `src/lifecycle/gate-questions.ts`). The item resolves with `gate_ready` (passed, changes, promoted, cancelled). Lavish has no approve API (lavish-axi 0.1.65's input playbook offers only `queuePrompt`), so the request is the most the page can do.
- **Question pages only** (the user's answer to this design's q17): the panel, comment box and pass request exist only in the widget, so only on a review that carries questions. The daemon still polls only while a question is open.
- **Skills**: the design skill says the widget is the only place a question appears (never "A (recommended): …" on the page). The QA skill carries the full recipe (`qa/questions.json`, the mount in `evidence.html`, the stage done flags) instead of pointing at the design skill. - **Tests**: `test/unit/gate-questions.test.ts` (v2 decode, a bad Send malformed whole, `other` checks, the widget's one Send, Other refused without its note, a pass refused with an empty question, the comment and Other words in the verdict, the pass request item, the poller recording a whole Send and its reply); `test/integration/gate-questions.test.ts` (a Send with a late answer, a comment and a pass request end to end; `decide other` refused without words).

## Worker questions wake the leader

A worker's non-blocking question (and a review gate's) used to be a P1 that only your next message's digest carried, so with the leader idle and you away it sat until you typed. Now every open worker question reaches the leader by itself. Plain code decides it all (SQL, a timer, fixed text); no model is involved.

- **Batching** (`questionBatch`, `src/attention/router.ts`): the questions a push may carry are the open `worker_question` and `worker_question_blocking` items never presented to any session, not shown to this one, and not leased to another push path; at most four per push, the rest in the next. A push that starts a turn waits until the oldest has waited `[leader] question_batch_ms` (30 s), so a ship's burst of asks is one wake; questions of other ships ride along.
- **Paths** (`leaderPush`, `src/leader/hooks.ts`): the P0 rules decide whether anything may be pushed (busy, or idle with you inactive, a Pi with its TUI). A P0 goes first, one at a time; a blocking question is a P0 for alerts but goes in a question batch, never the P0 path (`p0Candidate` leaves question kinds out). A busy Claude turn takes the questions at its `Stop` at once (the window only holds back a wake, and the turn is running anyway); a busy Pi gets a `followUp`. An idle Claude leader is woken by the existing asyncRewake waiter, which now also sleeps until the batch is due: its one line (`Flowryn questions [i12,i13]: 2 worker questions for the user (q7, q10). Details: flowryn decision list`, at most 200 characters; a batch holding review feedback says `N items for the user` and points at `flowryn fleet`) wakes the session, and the woken turn's `UserPromptSubmit` adds each question's full line (`questionsText`). That line counts as a wake (`isWakePrompt`), not you coming back. A Pi leader gets every line in its one `followUp`/`triggerTurn`.
- **Budgets** (`startedTurnsLastHour`): wakes are counted per started turn, not per item, and a question batch counts against `[notify] max_question_wakes_per_hour` (6), apart from the P0 budget `max_triggered_turns_per_hour` (3). Over it, your next message's digest carries the questions.
- **No double delivery**: one presentation row per question per push. A question a digest or briefing carried is never pushed, a pushed one is never in a digest, and a question presented anywhere is never pushed again. A Pi offer covers the whole batch: the extension still reports the lead item, and `acceptOffer`/`releaseOffer` act on every item offered in the same push (same `carried_at`), so neither the extension nor the CLI changed.
- **Alerts** (`src/attention/notify.ts`): a blocking question is a P0 and notifies at once, as before. A non-blocking one no longer joins the batched P1 notification: the leader is woken with it instead.
- **Choices made in the build**: the Stop path ignores the window (the design said a due batch; the brief said "deliver at its next Stop"); the woken-turn context lists only the questions that wake carried; a question carried by a turn that never ended (an interrupt) is pushed again, within the budget.
- **Tests**: `test/unit/question-wake.test.ts` (the batch window and ride-along, what is left out, the four-item limit, blocking questions off the P0 path, the wake line, wakes counted per turn on their own budget, a Pi batch accepted and released together, alerts) and `test/integration/question-wake.test.ts` (one waiter wake for two questions with both lines in the woken turn, a busy Stop, a digest-shown question never pushed, the question budget with a P0 still waking, the blocking-only alert, one Pi triggered turn for the batch). Race 2 now uses a P1 that is not a question, since a question rides the Stop.
- **Review pages are listened on by the daemon** (steer m85, added in the build): the leader used to start `lavish-axi poll` only once it noticed a page, so a page could show "Your agent is not listening". Now `stage done --page <html>` is accepted without `--questions-file` (a page with questions must still mount the widget), a `file://` review URL under the report directory counts as the page, and an https URL without `--page` gets a hint and is not polled (lavish-axi has no command that maps a session URL to its file). `gatesToPoll` keeps one poll for every open gate with a page, questions or not; the widget is written only for gates that carry questions. Each poll return opens one `review_feedback` item (`openGateFeedback`, `src/lifecycle/gate-questions.ts`): the answers recorded and the user's own words, read from the poll's TOON through `@toon-format/toon` (`PollOutput.feedback`). That kind is in `QUESTION_KINDS`, so it wakes the leader in the same batch as worker questions, and it is never OS-notified (you sent it). Feedback that opens with a pass word (`readsAsPass`: pass, approved, lgtm, looks good, ship it, go ahead) is named as possibly reading as a pass, for the leader to ask you about; feedback that goes on to ask for changes (a but/once/except/until/after clause) is relayed as changes. The gate still passes only through a human channel. A poll return whose text did not decode still opens the item, saying you left notes beside the page. The item closes when the gate passes or is sent back. Answers stay held for the verdict and notes stay beside the page, as before. The leader skill now says never to poll a review page; the design and QA skills pass `--page`.
- **Not run live**: the wake line's prefix reaching `UserPromptSubmit` as the prompt rests on M0 c01 (the fake Claude leader plays it that way); `scripts/lab/m3-live.sh` is where to confirm it.

## Away mode (autonomy spec 2, ship B)

Gates and questions sat for hours overnight because nothing reached you where you were: a P0 started a leader turn only after Claude's `idle_prompt` on the Mac, and a review gate was a P1 that waited for your next message. With remote control, the leader's chat is your phone channel; away mode routes what needs you into it. It changes delivery only: no approval, gate, merge or decision rule reads it, and there are no standing grants (k3). Plain code throughout: a meta row, a SQL wake rule and a fixed brief template; no model.

- **Posture** (`src/attention/away.ts`): `flowryn away [--until <time>] [--body-file -]` writes meta `away` = `{since, until, words, by}` with an `away.started` event; run again, it extends (`away.extended`: a new expiry and words, the start kept). `--until` takes `HH:MM` (the next time the clock reads it), `+8h`, `90m`, `2h30m` or `YYYY-MM-DD HH:MM`; at most 7 days; omitted, `[away] default_hours` (12). Your words are one sanitized line of at most 500 characters. Roles: you and the leader; the skill says the leader runs it only on your words, and nothing in code sets it (the idle suggestion below only suggests).
- **What ends it** (q26, your answer: back-or-expiry): `flowryn back`, or the expiry. Your messages never end it, since you answer from the remote chat while away. `getAway` treats a passed expiry as not away at once; the daemon's pass (`expireAway`) records `away.ended` {reason: expired} at the expiry's own time.
- **Wake rule** (`p0Candidate(…, awaySince)`, `src/attention/router.ts`; `awayWakeSql`): while away, an item opened since away began counts as a P0 for the push paths when it is `gate_ready`, `pass_requested`, `checks_red`, a `pr_ready` whose task is not yolo (a yolo task's PR is `pr_ready` only when not sensitive, and merges without you), or a `report_ready` whose scout opened a decision reserved for you that is still open. The P0 lane and the worker-question batch wake as before. The stored lane does not change, so after `back` the items read as they always did, and OS notifications (which read the lane) are unchanged: you are not at the Mac. Items opened before away began do not wake anyone.
- **Inactive while away** (`pushMode`): away counts as `user_inactive_since`, because the remote chat never fires `idle_prompt` on the Mac. A Claude waiter wakes the idle session; a Pi leader with its TUI gets a triggered turn; a busy Claude turn takes the item at its Stop, as for any P0.
- **Cap**: while away, the P0 push path's started turns per hour are `[away] max_wakes_per_hour` (6) instead of `[notify] max_triggered_turns_per_hour` (3); question batches keep their own budget. Over the cap, items wait for the next turn or your next message.
- **Return brief** (`composeReturnBrief`, `src/attention/briefing.ts`): one fixed order, built from the briefing's own sections (now `needsLines`, `reservedLines`, `decidedLines`) and the event log over the away window: waiting on you (every open actionable item, then decisions reserved for you); decided for you (decisions `answered_by = 'leader'` in the window); landed (`run.landed`); failed (`run.failed`, `run.cancelled`); spend (`run.dispatched`, `stage.started`, `leader.turn_started`, and the wakes among them: `leader.p0_pushed` and `leader.questions_pushed` by waiter or trigger). Worker turns are not counted: no event records one. `back` prints it (and reprints the last one for a day after); an expiry stores it (meta `away_last.brief_pending`) and your next own message (not a wake) carries it once (`away.brief_shown`). Expiry wakes nobody.
- **Idle suggestion** (`awaySuggestion`): your first message after at least `[away] suggest_after_min` (60) inactive, while not away, when an item the wake rule would have taken opened in that time and still waits, gets one fact line suggesting `flowryn away`; at most once a day (`away.suggested`).
- **Leader skill**: one "Away" bullet: away and back only on your word; while away, put what needs you to you in chat and publish a review page as a private claude.ai artifact (its file is now on the gate line of `flowryn show <task>` while the gate is open), recording answers as usual (`decide --by captain`, `gate pass` with Claude's prompt). `fleet` and the briefing show an "Away since … until …" line.
- **Tests**: `test/unit/away.test.ts` (`--until`, start/extend/expire/back, `[away]`, each wake-rule kind and its assumptions named in the test titles, the brief's order and window, the suggestion) and `test/integration/away.test.ts` (with the fake Claude leader: a gate opened while away wakes an idle leader whose user never went inactive, an older item does not, a chat reply keeps away on, `back` ends it with the brief and presence restores the old rule; the cap; an expiry's brief on the next message once; the leader may set away and a gate pass still prompts; refusals).

A Pi run's first model request takes 300 ms, as a live one does: the extension's prompt and tool hooks are fire-and-forget, and a first request answered at once let the tool's hook land before the turn's own. `FLOWRYN_CONTRACT_MAX_WAIT_MS` caps every step's wait (the test sets 15 s), so a broken step fails at once, naming itself. Both harnesses run in about 25 s.
- **Checked against #32**: with `workers.turn_end_guard = false` removed from the runner's scratch config, Claude fails at "idle" (timed out waiting for liveness idle) and Pi at "deliver while idle" (the reminder's follow-up turn plays the next script step early).
- **A race it found** (fixed here): after a worker's process died, the daemon's side of its last `hook wait-steer` call stayed the run's current waiter for up to `wait_poll_ms` (25 s). A steer sent to the idle resumed worker in that window was carried to the dead process, and the new process's next hook marked it seen: lost, never re-rung (6 of 10 offline runs failed at "deliver"). Now a waiter armed before the run's latest launch (its id is a ULID, `ulidTime` in `src/util/ulid.ts`) exits instead of firing (`armedBeforeLaunch`, `src/lifecycle/hooks.ts`), and a relaunch marks any steer carried but never seen lost, so it rings again to the new process (`src/lifecycle/launcher.ts`).
- **"No scratch home left" failed on the Mac** (2026-10-08, every step passing). The check listed every `fwc-*` in the shared `tmpdir()`, so any other `doctor --contracts` on the machine counted against it: another worker's `bun test` (this file runs in each), a leader's merge check, a live run. Instrumented, the runner's own home was gone right after its removal in every run (4 concurrent, 2 full suites); the one leftover a full suite caught (`fwc-GrSLq8`, pi) had vanished seconds later, which only another live run's cleanup explains. Now the test gives doctor a `TMPDIR` of its own (`fwt-*`), so the runner's scratch home lands there and the check counts that home only; a parallel run cannot fail it, and the check stays. Verified with three full `bun test` runs green, the first alongside a lab-session `doctor --contracts --verify-only --harness claude` (2.1.295 passed) while another process's live contract run had its own `fwc-*` home open in the shared tmpdir.
- **The runner's removal, hardened** against the other ways a home could stay: the scratch daemon is now awaited after a `SIGKILL` too (it was killed and not waited for); every harness process the scratch daemon recorded is terminated by identity, its group included, after the workspaces close, so a worker still exiting cannot spool hooks into the home; and `removeScratchHome` retries `rmSync` (`ENOTEMPTY` from a writer racing it), waits a 250 ms quiet spell, removes again if anything came back, and logs the reason if the home is still there after 10 s rather than skipping it in silence (`src/contracts/runner.ts`, tests in `test/unit/contracts.test.ts`).

## Automatic restarts (spec 3, phase 1)

After each Flowryn merge the leader ran `bun run build`, checked the protocol, then `flowryn daemon restart --when-idle` by hand; a build that bumped `PROTO` also made every worker and leader hook call exit 76 until the restart, so a worker could not `deliver` and release the validation slot the parked restart waited on. Now the daemon applies a new build by itself, and callers never see a protocol the running daemon refuses. Plain code throughout: a stat, a hash, git refs, the restart's existing guards; no model. Phases 2 (automatic contract checks) and 3 (the daemon builds after a Flowryn merge, and the upkeep hooks) follow from plan p7.

- **The build stamp** (`src/build-stamp.ts`, `scripts/build.sh`): `bun build --define` stamps the commit, a dirty flag (`git status --porcelain` not empty, or unreadable) and the checkout; `version --json` reports them with `schema` (the newest migration). A development command and a binary from an older `build.sh` have none. `FLOWRYN_BUILD_COMMIT`, `FLOWRYN_BUILD_DIRTY` and `FLOWRYN_BUILD_SOURCE` override the stamp, for the end-to-end test's scratch repository.
- **The watcher** (`src/daemon/build-watch.ts`): every `[daemon] build_poll_ms` (30 s) it stats the launchd target (the plist, re-read every 5 min); a changed file must hold still `build_settle_ms` (10 s: a build writes, then signs) before it is hashed. A build equal to the running one closes the watcher's items. Otherwise, once per build (`meta.build_watch`, so a restart or a dropped request never asks again): the binary check (`smokeCheck`, now returning the stamp); **refused** (`build_refused`, P1) for a failed check or a downgrade (a lower protocol, a lower version, or an older schema than the running daemon; a higher protocol is the normal upgrade); **held** (`build_held`, P1 info) for an unstamped build, a dirty tree, or a commit not on `refs/remotes/origin/<default branch>` of the stamped checkout (the branch from the project at that path, else `main`), after one `git fetch origin <branch>`; a held unmerged build is never applied by itself, even once its PR merges (PRs squash-merge, so the branch commit never reaches the default branch): rebuild from the default branch after merging, or `flowryn daemon restart` applies it now. **Apply**: the restart controller's `requestAuto` parks a `--when-idle` request `by: "auto"` with the build and commit, waiting `MAX_WAIT_MIN` (240); a request the leader or you parked is kept, an earlier automatic one replaced. A development daemon (no build of its own) is never restarted by the watcher.
- **The restart** is `tryPending`'s, unchanged but for an automatic request: `no_change` (someone restarted onto it already) or a newer installed build than the one it was parked for withdraws it quietly (`daemon.restart_withdrawn`, no P1; the watcher judges the newer build); every other refusal and the expiry are the usual `restart_dropped` P1. The briefing line reads `Daemon restarted 13:02 automatically: build 3f9a1c22d0b1→a07e55c9e1f4 (commit a1b2c3d), 0.10.0, proto 6→7.`; `daemon.started`, the snapshots and `daemon.ping` carry the commit.
- **Pinned callers** (`src/daemon/caller-binary.ts`): a compiled daemon hashes its own bytes once at startup, writes them to `<state_dir>/bin/flowryn-<build>` (unless there), and points the `<state_dir>/bin/flowryn` link at it in one rename before it opens its socket; the newest 3 copies are kept, the running one always. `workerBinary` (workers' `FLOWRYN_BIN`) and `flowryn lead` (the leader's hook wrapper) use the link, so a rebuild changes nothing for a caller until the restart, and every caller switches at the restart. If pinning fails the link goes and callers run the installed binary, as before. A development daemon replaces the link with its wrapper script (never writing through it). A leader's contract record from `$FLOWRYN_BIN` now runs the running build, which is the build the grant asks for.
- **`[daemon]`** (`src/config/daemon.ts`): `auto_restart = "merged"` (default) or `"off"`; `build_poll_ms` and `build_settle_ms` exist for tests. Validated with the other sections.
- **Choices** (the design page, approved): stat polling, not FSEvents (nothing gained at this rate); only clean merged builds apply by themselves, because relaxed contract records vouch for the running build and a branch build must not become it silently; the restart reuses `RestartController` (guards, binary check, kickstart, handoff); pinning callers removes the protocol window instead of alerting on it.
- **Tests**: `test/unit/build-watch.test.ts` (settle, judged once, running build, dirty, unstamped, unmerged stays held after its commit appears, without a second fetch or hash, a fetch that brings the commit, the project's branch, each downgrade, a higher protocol, a broken binary, a newer build replacing the line, off, a development daemon, `[daemon]`), `test/unit/restart.test.ts` (the automatic request: park, keep a leader's, replace an automatic one, quiet withdrawals, a broken binary, the stamp in `smokeCheck`, the briefing line), `test/unit/caller-binary.test.ts` (pin, repoint, keep 3, `workerBinary`, a development daemon's script), and `test/integration/binary.test.ts` with the real compiled binary: the design's assumptions (`--define` stamps a `--compile` build; a copied binary keeps its signature; `build.sh` replaces the installed file rather than rewriting it) and end to end, a compiled daemon under a script supervisor pins its build, a `build.sh` run over its installed binary with a merged commit of a scratch repository restarts it by itself (`by: auto`), and the link then points at the new build.
- **Version**: 0.10.0. `PROTO` stays 6: no envelope or verb argument changed (`daemon.ping` only answers more).
- **Not run live**: `launchctl kickstart -k` asked by the job itself (the end-to-end test uses the script supervisor, as the restart's own tests do).

## Worker reports reach the leader

`flowryn report <status>` used to append a `worker.report` event and nothing else, so no item, digest line or briefing entry followed and the leader never saw it (2026-10-08: a Pi contract failure reported as `report finding` was found only in the worker's pane). Plain code throughout: a fixed table, a lane-table kind, an exact-match duplicate check; no model.

- **The status table** (`REPORT_EFFECT`, `src/lifecycle/worker.ts`): `blocked`, `finding`, `failed`, `failing`, `error`, `broken`, `stuck`, `regression` and `risk` open an item; `progress`, `started`, `update`, `note`, `info`, `done` and `ok` are only recorded. A word outside the table opens an item: the contract tells workers to report only what a supervisor would act on, so an unknown word is far likelier a finding under another name than chatter, and a missed finding (this bug) costs more than one dismissable P1. If a word turns out to be chatter, it joins the record-only row.
- **The item**: `worker_report`, P1 actionable in the lane table, so the digest (`digestCandidates`), every briefing and `fleet` needs (`openActionable`) carry it with no router change. P1, not P0: a worker that truly cannot go on has `ask --blocking` and `fail`, which are P0. Not an away-mode wake kind: the leader can act on a report itself (steer, dismiss, relay). Its line is `Report (<status>) from <title>: "<body>"`, cut to the 200-character item line with ` (flowryn show for the full text)` when it does not fit.
- **One item per repeat**: a report with the same status and body as an open `worker_report` item on the same run adds no item (the reply names the existing one, `duplicate: true`); the event is still appended, so the record and the turn-end guard are unchanged, and a spooled report replayed after a restart opens no second item. A changed body is new information and gets its own item; a later report never closes an earlier one.
- **Closing**: `flowryn dismiss`, or the run's end: landing (a ship's `SETTLED_BY_LANDING`, a scout's `landScout`), failing (`failRun`) and cancelling (which already resolves every kind). A report from a run that has ended opens no item, since nothing would close it. An in-place promote keeps the run, so its report items stay open; a task promote follows a run that already ended.
- **Reading it**: `flowryn show <item>` for a `worker_report` item prints the report itself (status, task, run, age and the whole body, up to the 4,000 characters `report` keeps), read from the item's event, so no schema change. `flowryn show <run>` gains `report:` (the latest report of any status, one line), and the fleet's needs column says `report` while the run has an open report item.
- **Contract text**: the report line names `finding|blocked|failed`, says `progress` is only recorded, and that a finding needing a decision is a question for `ask`. The `report` verb's status help says the same; README's worker verbs too.
- **Tests**: `test/integration/worker-reports.test.ts` (a fake worker's `FAKE: report <status> [body...]` through the real CLI: one item for a repeated finding, none for progress, the line in the leader's next-message digest through the real prompt hook, `fleet` needs and the run's `report` column, `show` with the whole body plain and `--json`, an unknown word, dismiss, a scout landing closes it); `test/unit/worker-reports.test.ts` (the table, the line limit, a failed run closes it).
- **Version**: 0.11.0. `PROTO` stays 6: no verb's arguments changed; `report`'s reply only gains `item` and `duplicate`.
- **Not run live**: a real Claude or Pi worker reporting. TOON prints a multi-line body as one quoted string with `\n` escapes; `--json` gives it as is.
