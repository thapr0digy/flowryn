# M5 notes

M5 builds section 17's "M5 · Workflows, capacity, autonomy" of [`design-v3.html`](design-v3.html) on top of [M1](m1-notes.md) to [M4](m4-notes.md): workflow stages and review gates, capacity pools with the host check and Docker label evidence, plans and auto-dispatch on landing, the terse style block, and the three stage skills. This file records where the design left room, what M5 chose, and what the exit runs showed. Each item names the code that holds it. [`v1-status.md`](v1-status.md) lists every v1 item and where it landed.

## Workflows and stages

- **Workflows are data** (`src/config/workflows.ts`): `[workflows.<id>] stages = [{ id, skill, gate, pools, fresh }]`, where `gate` is `none`, `review` or `merge`. The defaults are the design's `feature`, `fix` and `scout`; a table with the same id replaces one. The checks: at least one stage, unique ids, a merge gate only on the last stage, no review gate on the last stage (it ends in a delivery), and only pools `[capacity]` defines (every run holds `worker` already, so a stage may not list it). A ship's workflow must end in the merge gate and a scout's must not.
- **A run's workflow is frozen at dispatch**: the definition goes into the `run.dispatched` event, so editing `config.toml` never reshapes a running run (`runWorkflow` in `src/lifecycle/stages.ts`). `dispatch --workflow <id>` picks one; the default is the project's (`project add|set --workflow`, which must be a ship workflow), and `scout` for scouts.
- **A stage's state** is `runs.stage_state` (migration 5): `waiting` for its capacity grant, `active`, `review` while its review gate is open, `done` once the last stage delivered. `runs.pending_launch` is the launch a grant must start (`fresh`, `resume`, or `stage` for a fresh stage worker), and `runs.stage_note` the words the stage start carries (a verdict, your changes).
- **The worker's side** (`src/harness/contract-text.ts`, `src/lifecycle/stages.ts`): the task file now starts with the current stage in one paragraph (where it sits in the workflow, the skill and its `SKILL.md` path, the pools it holds, what ends it), and the contract says: stage finished, run `$FLOWRYN_BIN stage done [--review <lavish url>]`, end your turn, and wait for a steer. `stage done` releases the stage's pools and either opens the review gate or requests the next stage; the scheduler starts it and a steer carries its instructions. A Claude worker usually gets that steer at once as its Stop continuation, a Pi worker mid-turn or as a follow-up. `stage show` prints the same instructions on demand.
- **Delivery ends the last stage, and the caps are the contract.** `deliver` from an earlier stage is accepted only when no review gate stands between (the `fix` workflow's `build` stage, say). A stage it would skip that holds pools is never finished for free. How that works depends on the delivery mode:
  - **no-mistakes**: the pipeline runs before `deliver --pr` (the PR comes from it), so the pipeline must run under the ship stage's `validation` slot. The worker starts that stage first with `flowryn stage begin <last stage>` (`beginLastStage` in `src/lifecycle/stages.ts`). It ends the current stage and requests the last one, which the scheduler grants for this run only. It returns once the stage has started, or refuses with `stage_waiting` (exit 2) while the pool is full. The worker then ends its turn, and the steer that starts the stage says so. The contract names the workflow's actual last stage and says whether it holds a slot. `deliver --pr` is refused with `stage_waiting` unless that stage was already active before the call; it is never granted at delivery time. The pipeline start itself is observed and flagged, but not blocked. When the delivery watcher sees no-mistakes go active on the run's branch while its last stage is not active and it holds no `validation` slot, it opens one P1, `validation_outside_cap` (`flagOutsideCap` in `src/reconcile/delivery.ts`). The refusal is the backstop: a pipeline run outside the cap cannot deliver until the worker holds the slot.
  - **Runs open across the upgrade** are exempt from both. Migration 5 marks the workflow it freezes for them `legacy_m4`, since their workers were given M4's contract (pipeline, then `deliver`, no `stage begin`). Such a ship's slot is granted at delivery time, as for local-only and direct-PR, and its pipeline is not flagged.
  - **local-only and direct-PR**: nothing runs under the slot before the delivery, so the skipped pooled stage is requested and granted at once for this run (`startPooledStages`), on the same pools and host check as any grant, with no steer. If it cannot be granted at once, `deliver` is refused with `stage_waiting`, and the steer that starts the stage tells the worker to deliver again. M4's flows work unchanged while the pools are free.
  - Either way, `deliver` checks its flags before changing any stage, so a malformed call changes nothing. A single-run grant (`Scheduler.grantNow`) never runs a full pass: no auto-dispatch, no other run's launch. Work nearer shipping, or older work, that needs the same pool keeps its turn. Stages without pools are still finished at once. A review gate ahead is `wrong_stage` (exit 2), and so is a delivery while the stage waits for capacity.
- **Runs open before M5** keep the contract their worker was given: migration 5 freezes `runs.workflow_def` for every open run (a ship: `build` then `ship`, the ship stage holding `validation` and ending at the merge gate; a scout: `investigate`; both marked `legacy_m4`), and `runWorkflow` reads it before the dispatch event. Without it, an M4 run of a `feature` project would sit at `build`, 2 of 4, and its delivery would be refused for the `qa` review it was never told about.
- **fresh = true** stages start a new worker: the scheduler stops the old harness by its identity, the run gets a new session id, and the launcher (mode `stage`) starts a new session in the same worktree with the stage in its task file. The reconciler leaves a run alone while `pending_launch` is set.
- **Decline** (`src/policy/verbs.ts`) now restarts the last stage through the scheduler: its pools are granted again, the merge gate row records the changes, and a worker that died meanwhile is resumed with your words as its steer.

## Review gates

- **Human-bound, like merges** (`src/policy/gates.ts`). A gate passes only with an approval record (action `gate`, bound to `gate:<id>` and the worktree's HEAD, used once) from a human channel:
  - `flowryn approve <task> --gate <stage>` in your terminal, behind the `/dev/tty` code (cli-tty), and the board's approve key, which now lists open reviews too (board). Both pass the gate as they record it: section 11 names them as the way you pass a gate.
  - The Claude leader's `flowryn gate pass <task>`: its PreToolUse hook records an attempt (action `gate`) and asks, and the ask rule `Bash(flowryn gate pass *)` M3 already wrote is the second layer (claude-ask). The attempt records the gate the prompt showed (`gate:<id>`), and the pass is refused when another gate is open by then (sent back and reopened).
  - The Pi leader's `flowryn_gate_pass` tool: it shows the stage and the review page with `ctx.ui.confirm()` and passes the gate with the approval key on stdin (pi-confirm), naming the gate it showed (`--gate-id g<n>`). `gate pass` refuses a `--gate-id` that is no longer the open gate. The extension blocks `flowryn gate pass` in the shell.
  - Nothing else: a token-less call without the code, a worker, or yolo never passes a review gate (`approval_required`).
- **Every gate prompt shows the plan it would approve** (`pendingPlanLine`): approving the design approves its plan, so `approve --gate`, the board, Claude's prompt and Pi's confirm each name the plan and its phases ("it also approves plan p1, 1 phase that start by themselves once this task lands: …") next to the review page.
- `stage done --review` needs an http(s) or file:// URL; the gate opens a P1 `gate_ready` with the link. `flowryn gate changes <task> --body-file - [--to <stage>]` sends the run back with your words: by default to the nearest earlier stage without a review gate (QA back to build), else to the gated stage itself (the design back to design). It needs no approval, since it only holds work back.
- The merge gate (section 7) is recorded as a `gates` row too: opened at the delivery, passed with the merge's approval when the run lands, sent back by a decline. The merge itself still goes through M4's merge gate.
- `gate pass`, `gate changes` and `approve --gate` wait for one scheduler pass before they answer, so the reply says whether the next stage started or waits for capacity.

## Plans and autonomy

- **A plan is a phased feature** (`src/lifecycle/plans.ts`): an optional `# title`, then one `## <phase>` section per phase, each a ship task. A section may start with `workflow: <id>`, `harness: claude|pi` and `after: <n>[, <n>]`; each phase waits for the one before it unless `after` says otherwise. At most 20 phases.
- **Approving the design approves the plan.** A design worker hands its plan in with `stage done --review <url> --plan-file <path>`; the plan waits, `pending`, on that gate, and its phases are not in the backlog. Passing the gate approves it: each phase becomes a Queued ship in tasks-axi (`add … --blocked-by`), phase 2 blocked by the design's own task. Changes on the gate discard it. `flowryn plan <project> --body-file -` files a plan the leader writes, approved as filed, like a dispatch.
- **Landed** means a run of the task is `cleaned` (merge proven, then cleanup done); a task Flowryn never ran has landed when the backlog shows it done. The blockers come from the backlog's `blocked-by:` dependencies, so a hand edit to them wins (section 8); a phase you hold or park in the backlog waits.
- **Auto-dispatch** (`Scheduler.autoDispatch` in `src/sched/scheduler.ts`): every pass, and at once when a cleanup finishes, each Queued phase of an approved plan whose blockers have all landed starts, in code, when its project's autonomy is `plan`: the run is created waiting for its first grant, the task goes In flight, and an informational P1 says "Phase 2 of 2 in "…" started by itself". A phase that is ready but cannot start (no contract record for the harness version, Herdr down, a tangled checkout) opens one P1 `phase_blocked` until it starts. The same checks as a dispatch apply; a phase never starts on an open PR.
- **Autonomy `manual`** (per project; `[autonomy] default` sets it for new projects) files the phases and starts none: `flowryn dispatch <project> --task <id>` starts one, and refuses with `blockers_not_landed` (exit 2) until its blockers landed.
- **Ad hoc tasks stay manual unless you pass `--auto`**: `dispatch --blocked-by <task> [--auto]` files a one-phase plan, Queued behind those tasks; with `--auto` it starts by itself once they land. A blocker must be a ship: a scout never lands, so a task behind one would wait forever, and dispatch refuses it (`bad_args`). `dispatch <project> --task <id> --sensitive` starting a Queued task marks it sensitive; a start never clears the mark.
- `flowryn show <plan id>` shows each phase and where it is (`queued, waits for …`, `running · build active`, `cleaned · ship done`).

## Capacity pools and the host check

- **Slots are rows** (`src/sched/pools.ts`): `pool_leases` is rebuilt with its own id (a stage granted again after a release gets a new row) and one live lease per pool and run. A grant re-counts inside its own immediate transaction and refuses rather than overfill, so live leases never exceed a cap.
- **Who holds what**: every run holds a `worker` slot from its first grant until its worker is gone (the run ends, or the reconciler finds its process dead with no resume coming). A stage holds its own pools from its start to its end: `stage done`, or the delivery for the last stage (after that the ship waits for your merge holding only its worker slot). A decline and a resume ask for them again. The migration gives every run that is open at the upgrade its worker lease.
- **The scheduler** (`src/sched/scheduler.ts`) grants in "drain before fill" order: fewest stages left first, then project priority, then how long it waited. A run it cannot grant is skipped, so work that needs a free pool is never held up by work waiting for a full one; nothing reserves a slot for the head of the queue. A pass runs after every change that frees or needs capacity (dispatch, stage done, a gate verdict, delivery, cancel, cleanup, a dead worker, a launch that failed) and every `[sched] pass_ms` (30 s). A pass runs auto-dispatch, the grants and the alerts each on its own, and each ready phase on its own: a phase that cannot start (its run cannot be created, say its worktree path is already there) gets one P1 `phase_blocked` and the pass carries on, so it never holds up a grant. A tangled primary checkout records its `dispatch.refused` event with its one P1, not again on every retry.
- **The host check** (`src/sched/host.ts`) runs before any grant that takes a new slot; a stage that needs none (build after the design) starts regardless. Available memory is free + inactive + speculative pages from `vm_stat`, because macOS keeps free memory as inactive file cache and `os.freemem()` reads a few hundred MB on a healthy machine; load is the 1-minute load average per core. `[capacity.host] probe = <command>` replaces both with a command that prints `{"free_mem_gb": n, "load_per_core": n}` (the tests' and the lab's seam). A result is reused for `host_cache_ms` (5 s); the check is recorded, with an event, only when it flips. While it fails nothing new is granted and running work carries on; work waiting longer than `[sched] wait_alert_ms` (30 min) opens one P1 `capacity_wait`, closed once nothing waits that long.
- `flowryn capacity` shows each pool's live leases over its cap, the host check, the usage-limit pause and the waiting runs in grant order with why each waits; `fleet` has a capacity line and a stage column (`qa review`, `ship waiting`); `show` adds the workflow, the gates and the leases.
- A dispatch answers after one scheduler pass: `launching`, or `waiting for capacity`.

## Docker label evidence

- The visual QA skill tells a worker to label every container `flowryn.run=$FLOWRYN_RUN`, one compose project per environment. The reconciler runs `docker ps --filter label=flowryn.run` on its steady pass (`src/reconcile/docker.ts`; `docker` joins `[tools]`) and records rank-2 evidence per run. An environment is one compose project; a container outside compose counts on its own.
- A live run running more environments than its `docker_env` leases is a divergence. Containers of a run that ended, died or holds no environment lease (a worker that left its QA containers up after `stage done`) are listed in one P1 `docker_leftover` with the `docker rm -f` line; nothing is removed automatically (section 16). Containers labelled for a run this home does not know are not judged. No Docker, or a daemon that does not answer, is skipped.

## The Claude usage limit

- The signals come from Claude Code's hooks reference (checked for this milestone): a turn that ends in `StopFailure` with `error: "rate_limit"` is a claude.ai usage limit (or an API rate limit), and `Notification` with `notification_type: "quota_auto_resume_fired"` (Claude Code 2.1.234 and later) means Claude continued after the reset. No hook input carries the reset time.
- Any Claude session, worker or leader, reporting the limit pauses every Claude launch and stage grant, and every Claude phase's auto-dispatch (`src/sched/usage.ts`), with one P1 `usage_limit`. The pause lifts on `quota_auto_resume_fired`, or on any Claude turn that later ends normally (`Stop`), which proves usage is available again; Pi work carries on throughout. Worker settings gain a `Notification` hook for the three `quota_auto_resume_*` types, and the leader's `Notification` matcher adds them to `idle_prompt`.
- Those signals need a live Claude session, and while paused none may start, so the pause also expires. With no reset time in any hook input, it backs off: `[sched] usage_backoff_ms` (15 min), doubling on each re-arm up to `usage_backoff_max_ms` (2 h). Once it expires the scheduler lets exactly one Claude start through as a probe (a waiting run's grant, or one Claude phase's auto-dispatch), recorded as `sched.usage_probe`: the probe's normal `Stop` lifts the pause, and a `rate_limit` after expiry re-arms it with the next backoff and rewrites the same P1. A probe that dies, or runs longer than the backoff, frees the slot for another.
- `flowryn capacity resume --harness claude` lifts it at once: human-only, like `approve` (a leader or worker token gets `human_only`), with a `sched.usage_resumed` event of source `cli`, resolving the P1. The P1 names that command and the expiry time; `flowryn capacity` shows the expiry or the probe, and hints the command while paused.

## The style block and the stage skills

- `[style]` (`styleBlock`): `terse = false` turns it off; `text = "…"` or `file = "<path>"` replaces the design's text (at most 2,000 characters, since it leads every prompt). The block now leads the worker contract (section 11: "the same block leads every worker's instructions") and is the leader's appended system prompt, as in M3.
- `src/skills/stages.ts` holds `flowryn-design`, `flowryn-build-test` and `flowryn-visual-qa`: descriptions of about 30 words, bodies under 2,000 characters (well inside 60 tokens and 1.5k tokens). The launcher writes them to `<state_dir>/skills/` and loads them into a Claude worker as a plugin (`--plugin-dir`); every stage start names the `SKILL.md` path, so a Pi worker reads the same file (a Pi `--skill` per skill would cost the typed launch line three long paths; M2's 960-byte limit). The design and QA pages live in `$FLOWRYN_REPORT_DIR`, outside the worktree, so a local-only delivery's clean-worktree check is not tripped by review artifacts. QA uses a `chrome-devtools-axi` session named after the run, so five browsers never share one.
- The leader's skill names `plan`, the review gates and `capacity`.

## Notifications: on in your setup, never from tests or live runs

- Found while running M5: every daemon that tests and the live runs started posted real macOS notifications, because `[notify] macos` defaults to on (M3). The default stays on, so a config written before this change (M3's init wrote `[notify]` without `macos`) keeps notifying; the protection is carried by the test and live-run isolation below instead (`src/config/leader.ts`).
- `flowryn init` asks whether to post macOS notifications (the default answer is the current value, else yes) and writes `macos` explicitly. A re-run fills in every key an existing table lacks, at any depth, and keeps every current value, so an old `[notify]` gains `macos` rather than being replaced or left as is (`withMissingDefaults` in `src/init/init.ts`). `flowryn doctor` warns when `[notify]` has no `macos` key.
- `FLOWRYN_NOTIFY=off` (or `FLOWRYN_NOTIFIER=null`) overrides the config for everything that is not your setup: the daemon still decides and records each notification (the `notifications` rows and events are unchanged, which M3's attention tests and live run read), but delivers none on any channel. The test preload, the test harness's homes, the contract suites' scratch daemons, the fixture runners, `spikes/lib/lab.sh` and every `scripts/lab/m*-live.ts` set it. `FLOWRYN_NOTIFIER=record:<path>` makes the macOS channel append to a file instead of running osascript; the harness sets it too, as a second guard.
- Every launcher of a daemon for testing refuses to start one without `FLOWRYN_NOTIFY=off` (`requireNotificationsOff` in `src/config/leader.ts`): the harness's `startDaemon`, the daemon lifecycle tests' direct spawn, the contract runner and `scripts/lab/m2-live.ts` to `m5-live.ts`. A forgotten override fails loudly instead of notifying. The fixture runners start no daemon.
- `test/helpers/no-notifications.ts` is preloaded for every test file (`bunfig.toml`): it sets `FLOWRYN_NOTIFY=off` for the test process, refuses any osascript spawn in it, and fails the run if one was attempted. `test/unit/notify-guard.test.ts` checks the default, the override (a daemon with `macos = true` records its P0 notification and delivers none), the launcher refusal, the recorder, and the in-process refusal; `test/unit/setup.test.ts` checks init's explicit `macos`, its fill-in of missing keys, and the doctor warning.

## The v1 completion pass

After M5, one pass built every v1 item [`v1-status.md`](v1-status.md) still listed as not built or partly built. This section records where the design left room and what the pass chose.

### The harness version gate (sections 5 and 16)

- `src/lifecycle/harness-gate.ts` checks the installed version (the `[tools]` binary's `--version`, cached until the binary changes) against `harness_contracts`. The daemon checks every harness in use (named by a project, an open run or a queued plan phase) at startup, before its first reconcile pass; dispatch checks it as before; so does `flowryn resume`, the reconciler before its one automatic resume and before retrying a launch that never finished, and the scheduler before any grant that launches a worker (a first launch after a capacity wait, a resume, a fresh stage worker, a relaunch).
- An untested version refuses (`contract_unverified`, the doctor command as help) and opens one P1 `harness_unverified` naming `flowryn doctor --contracts --harness <h>`, once per harness version: a dismissed one is not reopened for the same version, and a later untested version opens its own. It resolves when the installed version is verified (a startup check, or `contracts.record` for that version).
- **The automatic resume waits rather than fails.** A worker that dies on an untested version has its one resume claimed at once (so a second death is still "a failure needing you"), is marked dead, gives its slots back, and waits with `pending_launch = resume`; the scheduler launches it, into the same session, once the version passes. `flowryn capacity` says why it waits.

### Divergences (section 8)

- A divergence is a **backlog divergence** when its lower source is the backlog: a hand edit the watcher saw, or a violation the invariant pass found. Only these have an edit to accept. `flowryn divergence resolve <id> keep-run|accept-edit` (`src/lifecycle/divergences.ts`):
  - **keep-run** writes the runs' state back through the journal: a live run's task goes back In flight (`start`, or `add … --start` with the title and text it was dispatched with when you deleted it); a task with no live run gets what its last run left: `done` with its link for a cleaned run, parked (`reopen`, `hold --kind parked`) for a failed or cancelled one, `reopen` when Flowryn never ran it.
  - **accept-edit** lets your edit stand. A live run is cancelled with its worker stopped and verified gone first, its worktree kept for `flowryn cleanup`, and no backlog write at all (not the parked hold a `cancel` adds). With no live run, nothing changes, and the invariant pass does not raise the same violation again while the task reads the same.
- A divergence between evidence sources (GitHub against the worker, a process against its run, a pane label, Docker against a lease) takes only keep-run, which closes it with the run as it is; the same observation does not reopen it. accept-edit is `bad_args`. Those divergences also still close by themselves as before (a new delivery settles a GitHub one).
- The row and its P1 always close together, with a `divergence.resolved` event naming the resolution and who chose it. A backlog divergence's P1 line names the command; `flowryn show d<N>` shows one.

### The invariant pass (section 8)

- `src/reconcile/invariant.ts` runs on every full reconcile pass (startup, reconnect, the steady pass), after the backlog watcher has diffed any unseen edit and only while the snapshot's hash matches the file. It reads the snapshot inside its transaction, which is where the journal marks an intent applied, and skips every task with a pending intent, so it never judges a state that is about to change.
- A live run whose task is not In flight, or is missing, is a divergence (unless one is already open for that task); so is a task In flight with no live run. The watcher still flags a hand edit as it happens; the pass catches the rest, such as an edit to a run that already had a divergence of another kind open, or a task put In flight by hand.
- A backlog divergence whose task agrees with the runs again closes by itself (resolution `agrees`): the reconciler seeing the resolution happen elsewhere (section 9).

### Scouts land with their report (section 8)

- **A scout's workflow ends in no gate, so its verified report lands it.** Section 8's table puts a delivered report in `ready`, but `ready` is where a ship waits for its merge gate; a scout has none, and M5 already refuses a scout workflow that ends in one. So `deliver --report` records the report, links it in the backlog and moves the run to `landed`, and the delivery watcher's pass cleans it up through the cleanup guard, as after a proven merge (a clean scout worktree is `scout_clean`): the worker stops, the worktree and branch go, the run is `cleaned`, and the task is done with `--report data/<task>/report.md`.
- The `report_ready` P1 is not settled by the cleanup: it stays open until the report is read (`flowryn dismiss`, or a promotion), and `fleet` says `read` for the cleaned scout meanwhile. A scout that leaves uncommitted work is refused by the guard: it stays `landed`, its worktree kept, with a P1 ("Report delivered, but cleanup refused") naming `flowryn cleanup`.
- A scout that delivered under an earlier version and sits in `ready` is landed by the delivery watcher's next pass. The delivery watcher ignores kicks until it has started, so a report ingested from the spool at startup is cleaned only after the reconciler's startup pass has reattached the worker.

### `flowryn promote` (sections 4 and 12)

- **In place means the same task**: it keeps its id, its backlog entry and its report, and takes the project's ship policy (delivery mode, yolo, workflow, or `--workflow`); `--sensitive` marks it. Two cases (`src/lifecycle/promote.ts`):
  - **A scout at work** keeps its run, worker, worktree and branch. It cannot become a ship by a steer alone: its contract is in its system prompt and its Claude sandbox settings do not let it commit. So its run takes the ship workflow (frozen in `runs.workflow_def`), its first stage is requested with `pending_launch = relaunch`, and the scheduler stops the worker by its identity and resumes the same session (`claude --resume`, Pi's `--session-id`) under a ship's contract, sandbox settings and task file. The context it built survives; the task file carries the promotion: your words, what to keep on the branch (only the change, no scratch commits or debug output, a reproduced bug as a regression test) and the ship's delivery. A scout still waiting for its first launch simply launches as a ship.
  - **A scout whose run is over** (cleaned, cancelled or failed) becomes a ship on the same task: it goes back In flight (a parked hold is lifted) and a new run starts in a fresh worktree from the default branch, checked as a dispatch is, with a task file that names the report and quotes the scout's task.
- A landed scout still being cleaned up is `not_ready` until it is cleaned; a cancelled or failed scout whose worktree is still there is cleaned up first (`not_ready`, naming `flowryn cleanup`).

### Herdr unreachable (section 16)

- `src/reconcile/herdr-health.ts` keeps one outage episode in meta, from the first socket error (the event subscription failing to connect or closing, a dispatch's ping, a deferred launch) until Herdr answers again, so a daemon restart mid-outage continues it. Its one P1 `herdr_unreachable` opens once the episode has lasted `[herdr] unreachable_alert_ms` (60 s) and something needs Herdr: an open run, or a dispatch, launch or plan phase it held up. A Herdr that is merely not running while the fleet is idle raises nothing until you dispatch. The P1 resolves when the subscription connects again; a dismissed one is not reopened in the same episode.
- The subscription retries with its backoff (1 s to 30 s) and, when no socket was found at startup (Herdr started after the daemon), looks for the session again each time, so the daemon no longer needs a restart to find Herdr.
- Test homes without a fake Herdr set `unreachable_alert_ms` to a day: they have no Herdr by design.

### GitHub unavailable or rate-limited (section 16)

- `src/reconcile/forge-health.ts`: a failed read of the kinds that mean GitHub cannot be asked (unreachable or a 5xx, rate-limited, a refused token, nonsense answers) starts an outage; its one P1 `forge_unavailable` opens only while a merge waits on GitHub (a delivered PR at the merge gate, `ready`, or a merge waiting for its proof, `merging`), and names them. The delivery watcher's poll only runs over such ships, and a `flowryn merge` refused for the outage records it too. It resolves when GitHub answers again, or when no merge waits any more (then a merge that comes to wait in the same outage raises it again).

## Gate questions

A review page used to list its open questions as prose that Flowryn never saw: you got a page to pass or send back, and your answers reached the worker only if you typed them again. Now the worker hands its questions in as data, Flowryn makes each one a decision reserved for you as the gate opens, and you answer either on the page or through the leader. The first answer counts. Nothing on this path asks a model to decide anything: a JSON file, a fixed template, a fixed pattern on the poll output, and the database. The worker's own judgement (what is truly a question) is the only model work, and the ask rule below bounds it in code.

- **The ask rule** (`src/harness/contract-text.ts`, `src/skills/stages.ts`): the worker contract says to work autonomously, decide everything you can, record each choice and why (design page or PR), and ask only when you truly cannot proceed. Code checks the shape of every question (`src/lavish/questions.ts`): it names the choice it blocks (`blocks`, 10 to 200 chars), a choice has 2 to 8 distinct short options and a recommendation among them (a multi choice: a non-empty subset), a text question carries the worker's default answer, at most 5 per gate, no two blocking the same choice. A bad file is refused whole and nothing opens. The worker lists what it decided itself under `decided`; the page shows it read-only, and a disagreement is a `gate changes`. `flowryn ask` now requires `--blocks` too, stored in `decisions.blocks` and shown on the item.
- **Hand-in** (`src/lifecycle/stages.ts`, `src/lifecycle/gate-questions.ts`): `stage done --review <url> --page <html> --questions-file <json>`, on any stage with a review gate (design and qa). `--page` must be a regular `.html` (no symlink) under `$FLOWRYN_REPORT_DIR` that mounts the widget: `<section id="flowryn-questions"></section><script src="flowryn-questions.js"></script>`, with `data-lavish-live-reload-root` on `<html>`. In the transaction that opens the gate, each question becomes a run-scoped `q<N>` (origin `gate:<g>`, `kind` single, multi or text, `gate_id`, `note` = the worker's why), reserved "a review question for the user", with a P1 `worker_question` item that names the relay command. So the leader sees and relays them even when you cannot open localhost.
- **The widget** (`src/lavish/widget.ts`): the daemon writes `flowryn-questions.js` beside the page: a fixed renderer and the gate's state as JSON. It follows lavish-axi's `input` playbook: radios with the recommendation preselected, checkboxes for a multi choice, a text field (the default as its placeholder), an optional note each, and one Submit that queues one prompt per answered question (`queueKey flowryn:<q>`) and sends them (`sendQueuedPrompts`). Each prompt ends in `flowryn-answer v1 <base64url JSON {g, d, c, n}>`. The daemon rewrites the file whenever a question's state changes, so an answered question shows locked with who answered. A closed gate's widget is written once more, all locked.
- **The poll** (`src/lavish/poller.ts`, `src/lavish/poll-output.ts`): for each open gate with an open question, the daemon keeps one `lavish-axi poll <page>` running (`[tools] lavish_axi`). On return it records each answer line through `lavishAnswer` (`src/lifecycle/decision-verbs.ts`, the only path beside `captainChannel` that records `answered_by = captain`, here `via lavish`). An answer counts only for an open question of that gate while the gate is open. Anything else (already answered by the leader's relay, a stale page from an earlier gate, a choice the question does not offer) becomes a `decision.lavish_ignored` event. The poll consumes everything you sent, so other prompts (annotations, chat) are appended to `lavish-notes-<gate>.txt` beside the page, and the verdict steer points the worker at that file. After recording, the next poll passes `--agent-reply` with what Flowryn did ("Flowryn recorded your answer to q1, q3. 1 question still open.", a late or invalid answer named, "Every question is answered; the review now waits for your pass in Flowryn."). Once nothing is left to poll for, one short poll (`--timeout-ms 1500`) carries the last reply. Without it Lavish's conversation spins on "Working…" for good: the visual QA found that. A failed poll backs off from 2 s, doubling to a minute. `session_ended`/`status: ended` (Send & End) stops it for good (`gates.lavish_ended`), and the leader path still works. A daemon restart rebuilds the polls from `gates`. Killing a poll loses nothing, because Lavish puts feedback back when a poll's request closes. Without lavish-axi the decisions still open and only the poll is off.
- **Answers and verdicts**: answers are held while the gate is open (no steer wakes an idle worker that could only end its turn). A gate passes only once each of its questions is answered: `gate pass`, `approve --gate` and the board refuse with `questions_open`, naming them, and the approval prompts (Claude's, the Pi confirm, `/dev/tty`) list the answers the pass carries. The verdict steer carries them all: "The user's answers to your review questions: q1 (token-store) = file [their note: …]; …". Changes close the questions still open (`dismissed`), and the steer lists those as closed unanswered. The next hand-in opens fresh ones.
- **Measured on lavish-axi 0.1.65** (a scratch `LAVISH_AXI_STATE_DIR` and port, prompts posted to its API, then `poll --timeout-ms`): output is TOON, `status: feedback` with `prompts[N]` (or `prompts[N]{…}:` when every prompt has the same fields), `session_ended: true` on the last batch before Send & End and `status: ended` after it, and a poll with no session exits 1 with `code: NOT_FOUND`. A prompt's `target` is passed through as JSON, while `data` is folded into the prompt text. The samples are kept verbatim in `test/unit/gate-questions.test.ts`, and `flowryn doctor` warns when the installed lavish-axi is not 0.1.65 (`VERIFIED_LAVISH_AXI`). The visual QA proved the rest in a real browser through a real Lavish session on a scratch port and state dir. Lavish reloads the page when Flowryn rewrites the sibling `.js` (with `data-lavish-live-reload-root`). The widget's Submit reaches the daemon's poll with no extra "Send to Agent" click. A question left empty stays open. Once the last question is answered, Lavish shows "agent not listening", because Flowryn polls only while a question is open (the answer to q5 of this design was questions-only).
- **Tests**: `test/unit/gate-questions.test.ts` (the ask rule, answer checks, the poll output samples, the widget run against a DOM stand-in whose submitted tokens decode to the same answers, the decisions, the gate refusal, dismissal, the widget file, the page checks, a poller without lavish-axi and with a binary that cannot run); `test/integration/gate-questions.test.ts` (end to end: the hand-in refused without its page, reserved decisions in `decision list --reserved` and `show`, the widget and the poll, `questions_open` from your terminal and from the leader, a page answer recorded as captain via lavish with its note kept, the leader's relay through Claude's prompt held for the verdict, a late page answer ignored, the verdict steer with every answer and the notes file, the widget locked; changes dismissing the open ones, a file without `blocks` refused, fresh questions on the next hand-in, and a poll picked up again after a daemon restart). Test homes get a `lavish-axi` stand-in whose `poll` prints what a test queues in `$FLOWRYN_HOME/lavish-queue/`, and fake workers a `write` step.
