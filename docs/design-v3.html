Flowryn: one leader agent, a supervised crew, and nothing lost

You talk to one leader agent in Claude Code or Pi. It dispatches ships (which end in a PR) and scouts (which end in a report) into isolated worktrees in Herdr panes. One daemon, flowrynd, supervises them, holds all runtime state in one SQLite database, and pushes ranked, capped updates to the leader at natural pauses. Everyone, you included, drives it through one CLI.

2 · Goals and non-goals

Goals for v1

  1. One conversation. You talk to one leader. Workers, watchers and supervision stay out of its context. It sees one-line pointers and pulls detail with flowryn show.
  2. Never interrupt. Updates land at natural pauses. A P0 may start a leader turn only when the leader is idle and you are not active.
  3. Never lose what needs you. An actionable item stays open until you resolve it, and it is re-listed after every session start and compaction.
  4. Rules in code, approval from a human. Merge, cleanup and destructive actions go through the policy engine, and "your word" is a recorded human approval, not the leader's claim.
  5. Restart is a non-event. Durable state, a reconciler, an intent journal and a spool make a crash of the daemon, a worker or Herdr recoverable without chat memory.
  6. Small. Two harnesses, one runtime, one database. Target about a quarter of the previous orchestrator's surface while keeping its hard-won safeguards.
  7. Personal to-dos. Stored and shown; items due today appear in the morning briefing; overdue items are P1. No separate reminders.
  8. Autonomous within limits. Many workers at once, with hard caps on heavy stages. The next phase starts by itself when the previous one lands. You are needed only at review gates and merges (section 11).
  9. Terse. The leader and workers answer in as few words as carry the outcome.

Non-goals for v1

  • Harnesses other than Claude Code and Pi, as leader or worker. Each future harness is an adapter that must pass contract tests.
  • Runtimes other than Herdr (no tmux fallback).
  • Adversarial security. The model is confused-agent-grade (section 7).
  • A judgment tier. Anything needing judgment reaches the leader as a one-line pointer. The headless triage runner comes after v1.
  • Desks (persistent scoped workers), quota-aware scheduling and profile routing. One static profile per harness. Capacity pools are in (section 11).
  • Focus routing, score formulas, automatic "unseen becomes urgent".
  • Away and quiet modes. OS notifications cover absence.
  • Obsidian and Jira integrations; a Herdr plugin-pane board; retention compaction; the MCP wrapper; Claude Code channels and plugin monitors. Lavish needs no integration: workers host review pages and Flowryn records the link and the gate.
  • Linux and native Windows hosts. macOS is the v1 platform. The transport and service seams for the others are defined (section 12).
  • Relay (X mentions), the mail plane, multi-machine fleets.

3 · Architecture overview

Four layers. Surfaces are where you are. Bridges and the CLI are the only ways into the daemon: bridges carry push and busy/idle signals, the CLI carries every command. flowrynd holds all runtime state and makes every decision. Providers run the workers and hold the external truth. Primary-colored arrows are pushes; the green box is the human-only path; the red dashed arrow is an OS notification.

Principle 1 · One writer per fact

Only flowrynd writes flowryn.db. Only the intent journal calls tasks-axi. No fact lives in both stores.

Principle 2 · Evidence, not guesses

Reports, harness events and Herdr status are evidence of different strength. The reconciler decides, and says so when evidence conflicts.

Principle 3 · Rules in code, consent from a human

The policy engine enforces merge, cleanup and destructive gates, and accepts "your word" only as a human-channel approval record.

Stack. TypeScript on Bun 1.3, with bun:sqlite, compiled to one binary that serves as both flowryn and flowrynd (about 60 MB; 9.3 ms median startup measured, fast enough for per-prompt hooks). The build step re-signs the binary with codesign --force --sign -, because the compiled ad-hoc signature is invalid as shipped.

5 · The harness adapter interface

Supporting a harness costs lifecycle and push, not reporting. So the adapter is a typed interface covering exactly those, and v1 implements it twice: Claude Code and Pi. Each capability uses the harness's own hooks or extension API. Herdr keystroke delivery is not a v1 steer path; v1 sends the interrupt key, and one fallback: the fixed steer pointer typed into an idle Claude worker whose waiter is gone, only while Herdr reads it settled (docs/m5-notes.md, "Idle workers").

// src/harness/types.ts — one adapter per harness

    // args for Herdr agent.start; env goes on
    // workspace.create, whose params include env
  preTrust(worktree: string): Promise<Trust>;

    // never answer a dialog with keys

    // captured by the worker-start hook
  interrupt(run: RunRef): Promise<Verified>;
  exit(run: RunRef): Promise<Verified>;
  resume(run: RunRef, s: SessionId): LaunchPlan;
  // Busy truth: harness events, never screen text

Contract tests gate every harness version

Each adapter ships a contract suite: launch in a scratch Herdr session named flowryn-contract, capture the session id, observe busy and idle, deliver while busy and while idle, interrupt, exit, resume. flowryn doctor --contracts runs it and records the passing harness version. The daemon checks the installed version at startup and before each launch, and refuses to dispatch on a version with no passing record (code: contract_unverified).

Adding a harness after v1

Write the adapter and its contract suite, pinned to the installed version. A harness without native push would use Herdr agent.prompt only after proving the composer is empty, which is the costly subsystem the previous orchestrator carries (1,826 lines). The interface keeps that fallback possible without v1 building it.

6 · The reconciler and the evidence hierarchy

Herdr's agent status is itself inferred, and it is wrong in documented cases: idle while a harness waits on a long foreground tool, a Pi registration kept after Pi exited, Cursor always blocked, and working left behind by an agent killed mid-turn. Herdr's event stream has no replay, and restarting the Herdr server kills every harness process. So one component, the reconciler, owns current-state truth for each run, and it ranks its sources.

Rules

  • Higher rank wins, and a conflict is recorded, never silently resolved. Example: deliver names a PR that GitHub shows as draft or whose head is not on the remote → a divergence event (P1) and the run stays running.
  • Liveness is one of starting, busy, idle, blocked_dialog, dead, orphaned, unknown. The reconciler writes it; only the lifecycle engine changes runs.state, on the reconciler's request.
  • Reattach only when pane id, worktree path and a live harness process identity (pid plus start time plus executable) all match the runs row. Pane metadata (flowryn:<run>, written with no TTL) only finds candidates. A mismatch is orphaned; a run is never adopted by label.
  • Husks. A pane with no live harness process is dead. At startup, many husks at once mean the Herdr server restarted. The supported Herdr update path is herdr update --handoff, and flowryn doctor checks the Herdr version against the pinned minimum and protocol 17.
  • Trust wedge. Process alive but no worker-start event within 30 s of launch → blocked_dialog, reported as a P1 pointer. No keystrokes.

The only automatic actions in v1

  1. Resume a dead run once from its stored agent_session, in the same worktree. A second death is a P0 "failure needing you".
  2. Re-ring an unacknowledged steer, up to 3 times, 5 minutes apart; then a P1.
  3. Clean up after a merge the daemon itself proved. The cleanup guard still runs.
  4. Re-arm monitoring after a restart: waiters, subscription, PR polls.

Everything that needs judgment reaches the leader as one pointer line in its lane: a worker idle for 15 minutes without an outcome, busy with no hook event for 30 minutes, a divergence, an orphan. A headless triage runner (a stateless per-event claude -p or Pi print-mode call with a fixed prompt and a spend cap) is the first post-v1 addition.

7 · The approval channel and threat model

Code can enforce green checks and yolo posture, but "you said merge" has only one witness: the leader agent, which is the component the rule constrains. So a merge without yolo needs an approval record that only a human channel can create. Both channels are accepted: the harness's own confirmation prompt, and flowryn approve in your shell or on the board.

Claude leader

  1. The leader runs in --permission-mode auto. Ask rules that match a command's content still prompt in auto mode.
  2. For a flowryn merge command, the PreToolUse hook records an attempt (session, tool-use id, argument hash, permission_mode) and returns permissionDecision: "ask", which prompts in auto mode too. A routine merge (the task is yolo and not sensitive) is neither asked nor recorded, so it merges under yolo. There is no static merge ask rule: it would prompt for routine merges as well.
  3. If you approve, the command runs with the leader token. The daemon matches it to the attempt (same session and arguments, under 5 minutes old) and records channel claude-ask.
  4. If the attempt is missing or its mode was bypassPermissions, the channel is unavailable. M0 found that the ask rule and the hook's ask both still prompt under bypass, but the leader never runs in bypass, so this refusal stays as defense in depth. The merge returns approval_required.

M0 ✓ the hook input carries permission_mode (every event except SessionStart); the prompt appears in auto mode inside a Herdr pane.

Pi leader

  1. Pi has no permission system, so the extension is the gate.
  2. Its flowryn_merge tool shows PR title, URL, head SHA and checks through ctx.ui.confirm().
  3. On yes, it calls the daemon with an approval key it received over the socket at lease claim and never put in any environment. Channel pi-confirm.
  4. The extension blocks shell calls to flowryn merge and flowryn approve; without the key, a shell merge gets approval_required.

M0 ✓ the extension blocks a shell tool call (tool_call returns {block: true}, and the model gets the reason as the tool result); ctx.ui.confirm() shows a Yes/No selector in the TUI and returns false on Escape.

Your shell or the board

  1. flowryn approve T17 refuses when any FLOWRYN_* token is in the environment (an agent pane) or stdin/stdout is not a TTY.
  2. It prints the PR URL, head SHA and check summary, then reads a random 4-letter code from /dev/tty, so piped input cannot answer it.
  3. The board's approve key does the same. Channel cli-tty or board, actor $USER.
  4. --allow-red <check> names one failing check to waive. Only a human channel can create it; every other check must be green.
Sensitive work. A task is sensitive when you or the leader mark it at dispatch (--sensitive) or the worker's deliver --sensitive flags security impact. Destructive actions (cleanup --discard, project removal, a forced worktree removal) are always sensitive. Sensitive actions need a human-channel record even under yolo.

Threat model: confused-agent-grade

Flowryn protects against agents that are wrong, confused or prompt-injected into ordinary misuse. It does not protect against a deliberate attacker running as your user: Herdr exports HERDR_SOCKET_PATH into every pane, so any worker process can read or type into any pane, the leader's included. That residual risk is accepted and stated.

8 · tasks-axi vs SQLite, and the intent journal

Intent journal protocol

  1. In one SQLite transaction: the runtime change (for example a run row in launching), an intents row in pending, and an event.
  2. Run <tasks-axi absolute path> <verb> … --file <path> --json with a 10 s timeout. One intent at a time, which matches tasks-axi's single-supervisor lock (2.5 s advisory timeout).
  3. On success: mark it applied and store the resulting file hash in backlog_snapshot, in one transaction.
  4. On failure: stay pending, retry at 1 s, 5 s, 30 s, 2 min, 10 min, then a P1 "backlog out of sync" item.
  5. At startup: replay pending intents in order. start and hold are idempotent by their help text; add is made replay-safe because flowrynd mints the task id and checks tasks-axi show <id> first. done, unhold and update are idempotent too (a repeat returns already: true and leaves the file unchanged), and so is add with the same id. mv is not (a repeat returns NOT_FOUND), and it moves a task to another backlog file, so the journal never issues it M0 revised.

When you edit the backlog by hand

  • A file watch plus a 60 s hash check notices any change whose hash is not the last applied one.
  • The journal re-reads tasks-axi list --fields … and diffs it against the snapshot. Read verbs print TOON; tasks-axi 0.2.5 has --json only on mutations.
  • Your edit wins for title, body, priority, dependencies, holds, to-do done state and due date.
  • A contradiction with a live run (an In flight task moved or deleted, or its id changed) becomes a divergence (P1). The run is untouched until you run flowryn divergence resolve <id> keep-run|accept-edit.
  • An editor holding a stale buffer can overwrite a CLI write; the hash check catches it as an edit, and the journal re-applies any intent the overwrite erased.

9 · Delivery semantics and the lane table

No harness can observe that the leader "saw" something. A timed-out UserPromptSubmit hook's context is discarded; Stop does not fire on an interrupt; hook context is invisible to you in the transcript. So "never lose" is defined by two delivery classes rather than by read receipts, and the leader never has to call an acknowledgement command.

Actionable items: never closed by delivery

Open decisions, ready PRs and reports, failures, blockers, divergences, overdue to-dos. Each stays open until something resolves it: your answer, a merge or decline, flowryn dismiss, a to-do marked done, or the reconciler seeing the resolution happen elsewhere (a PR merged on GitHub). Every briefing, including the one after compaction, and every flowryn fleet lists them. That is the "never lose" guarantee.

Informational items: at least once

Outcomes you should know but need not act on, like a yolo merge or an automatic resume. Stable ids. An item is carried when a hook returns it and presented only when the same session's next turn end follows (Claude Stop, Pi agent_settled). A turn with no turn end (interrupt, hook timeout, API error) means the item is carried again next turn, deduplicated by id. After 3 attempts it drops to the board.

Ordering, aging, limits

  • Within a lane: project priority, then due date, then age. An item never changes lane on its own.
  • Only actionable items age: one open over 24 h moves to the top of its lane and joins the next batched notification, once a day.
  • A P0 is leased to one delivery path at a time (continuation, waiter or trigger), so it is never delivered twice. After presentation it stays open and listed; an unresolved P0 re-notifies after 4 h.
  • Started turns are capped at 3 per hour; beyond that, notification only.
  • OS notifications: P0 immediately, coalesced within 60 s; at most one batched non-P0 notification per 30 min; none for P2.

Races and their resolution

  1. Interrupt leaves busy stuck → busy lease expiry (no hook and no idle_prompt follow an interrupt).

  3. P0 through both continuation and waiter → per-item delivery lease.
  4. Composer race with your draft → no keystroke delivery; waiter only when you are inactive.
  5. P0 arrives while Stop is deciding → Stop asks once; anything later goes to the waiter.
  6. Two leaders → the lease (section 10).
  7. Compaction drops digests → the compact briefing re-lists actionable items.
  8. Pi nextTurn while idle never delivers → P0 uses triggerTurn; P1 waits by design.
  9. Stale Herdr status → the harness's own idle signal decides.

10 · The leader lease and handover

Claude Code and Pi are both first-class leaders, but only one session leads at a time. Without that, both would mark busy and idle, and deliveries would split or duplicate. The lease decides which session receives pushes and may run leader mutations. It grants no approval authority.

Claim and handover

  1. A new leader session's start hook asks the daemon for the lease. Vacant or stale → claimed (epoch + 1). Held → this session becomes read-only.
  2. You move leadership by asking the new session to run flowryn leader claim, or by running it in your shell with --session <id>.
  3. On claim: epoch + 1; a new leader token and approval key are issued; the old waiter is told to exit 0 silently; informational items carried but not presented in the old session are re-queued; actionable items need nothing, because the new briefing lists them.
  4. The old session's next hook or extension event shows one banner line: "leadership moved to pi in pane w3:p1".

11 · Workflows, capacity and autonomy

You work in a particular way. You review a design in Lavish, the crew builds and writes tests on its own, visual QA collects evidence you review in Lavish, you ask for changes until it looks right, and then it ships. You want the next phase to start as soon as the previous one lands. And you want many workers running at once, while heavy stages such as Docker environments, visual QA and no-mistakes stay under hard caps. Flowryn splits this into two parts. It owns when and whether: stages, human review gates, capacity and auto-dispatch, because those need durable state, supervision and human-bound approval. Skills own how: how to test a stack with a front end, back end and database, how to walk an app with chrome-devtools-axi and capture evidence, and how to build the Lavish evidence page.

Stages and gates

  • A run moves through its workflow's stages in order. The lifecycle engine owns runs.stage. By default one worker and one worktree carry the whole run, so context survives. A stage with fresh = true gets a new worker, for example for an independent QA pass.
  • The worker finishes a stage with flowryn stage done [--review <url>]. It hosts the Lavish page itself, as the previous orchestrator's workers did.
  • A review gate opens a P1 item: "design ready for review" with the link. You iterate with the worker inside Lavish. You pass the gate with a human channel: flowryn approve <task> --gate design or the board. The leader can also ask through its confirmation prompt with flowryn gate pass, which carries an ask rule. flowryn gate changes <task> --body-file - sends the run back to the named stage with your words.
  • Gates are human-bound like merges (section 7). A worker saying "you approved it in Lavish" is not a pass.

Capacity pools

  • Each stage names the pools it needs. The scheduler starts a stage only when every pool has a free slot and the host check passes. Slots are rows in pool_leases, tied to run and stage.
  • Slots are released at stage end or run end. The reconciler also releases them when a run dies. A leak is impossible because no process holds a slot, only a row.
  • A waiting worker is never held in a blocking call. It ends its turn, and the daemon wakes it with a steer when the slot is granted.
  • Grant order is "drain before fill": stages closer to shipping first, then project priority, then age. With the caps above, about 15 workers build while 5 validate, and QA never exceeds 5 Docker environments.
  • Docker evidence: the worker labels containers flowryn.run=<id>. The reconciler counts them with docker ps --filter label=…. Running more than the lease allows is a divergence.

Autonomy: phases continue by themselves

  • A phased feature is a plan, filed as tasks chained with blocked-by (flowryn plan <project> --body-file plan.md). A plan is usually the output of a design stage, so approving the design approves the plan.
  • When a task lands (merge proven and cleanup done), the scheduler re-evaluates immediately, in code, with no leader turn. Every queued task from an approved plan whose blockers have all landed starts as soon as capacity allows. You get one informational line: "phase 2 of checkout started".
  • A phase starts only after its blockers have landed, never on an open PR, so no phase builds on unreviewed code (decided in review). Stacking on an open PR may become a per-plan option after v1.
  • Tasks you dispatch ad hoc stay manual unless you pass --auto.
  • Autonomy never skips a gate, never merges without the merge rules, and pauses while a Claude usage limit is active.

Terse by default: output tokens are spent on outcomes

Flowryn already keeps input small with pointers, capped digests and show on demand. For output, flowryn lead appends a short style block to the leader's system prompt. Identity and transport

  • At launch, the daemon sets FLOWRYN_RUN, FLOWRYN_TOKEN (a per-run capability), FLOWRYN_BIN (absolute path, so workers never depend on PATH), FLOWRYN_SOCK and FLOWRYN_PROTO on the Herdr workspace.create call.
  • The leader token comes from the lease (section 5). Tokens are stored only as hashes.
  • Commands never infer a task from the working directory.
  • JSON over a local socket. On macOS: a Unix socket at ~/.flowryn/run/flowrynd.sock in a mode-0700 directory; the path is fixed and short because macOS limits socket paths to 104 bytes. All socket code sits behind src/transport/ (see Portability below).
  • Envelope {proto, ulid, verb, token, args}; reply {ok, data | error{code, message, help}, hints}. Every call starts with a protocol check.
  • Every mutation carries a client-generated ULID. The daemon keeps replies for 7 days, so a retry returns the original result.

When the daemon is down

  • Worker verbs (report, ask, deliver, fail) try the socket with a 300 ms connect and 2 s reply timeout, then write <data>/spool/<run>/<ulid>.json atomically, print spooled: <ulid>, and exit 75. One writer per file. The daemon ingests at startup and on every pass, deduplicated by ULID.
  • ask never holds a call open. It returns a decision id (or spooled); the worker ends its turn; the answer arrives as a steer.
  • Hooks use a 300 ms connect timeout and step aside silently: exit 0, no output. A slow daemon never stalls your prompt.
  • Reads (fleet, show, board) open SQLite read-only (WAL allows concurrent readers) with a "daemon down" banner.
  • Leader mutations exit 69 with help: flowryn daemon status.
Portability. A Unix socket does not suit native Windows, so transport is an interface, not a path. macOS (v1): Unix socket, launchd. Linux (after v1): the same Unix socket, with a systemd user unit instead of launchd. Windows: the supported path is WSL2, where Unix sockets, git and the terminal runtime behave as on Linux. A native Windows build would use a named pipe (\\.\pipe\flowryn-<user>) restricted to your account, a scheduled task instead of launchd, and the console device instead of /dev/tty for the approval code. It would also need a runtime, because Herdr on native Windows is unverified. Every surface calls the same verbs, so none of this reaches the command registry.

15 · Setup and init

flowryn init is interactive and runs only in your own terminal. It detects first, asks, and writes nothing until you confirm. It can be re-run to change any answer.

  • Preflight. macOS; Herdr at or above the pinned minimum with protocol 17; Claude Code and/or Pi versions; git; gh authenticated; tasks-axi at the pinned version; no-mistakes (optional). Missing tools are listed with their install command; nothing is installed without your yes.
  • Data (artifacts) directory. Where reports, spool and large artifacts go. Default ~/.flowryn/data. Any path is allowed; a path under Documents, Desktop or iCloud gets a warning about macOS privacy prompts for a background binary.
  • State directory. Holds flowryn.db, its lock and logs. Default ~/.flowryn/state. Refused under iCloud, Dropbox, Documents or other synced folders, because SQLite WAL on a synced folder risks corruption. The socket always lives in ~/.flowryn/run/.
  • tasks-axi location. Paths for backlog.md and todos.md (default in the data directory; an existing backlog may be adopted). init runs tasks-axi list --file … on each (read verbs print TOON; there is no --json for them) to prove it can read and write them.
  • Tool paths. Records absolute paths for tasks-axi, node, git, gh, herdr, claude, pi and no-mistakes, resolving symlinks. tasks-axi under an nvm directory is flagged, because it breaks on the next Node upgrade. The daemon checks every path at startup.
  • Leaders. Claude Code, Pi, or both. Writes the leader settings file and the Pi extension into ~/.flowryn/leader/, and installs the flowryn skill there. You start a leader with flowryn lead or flowryn lead --pi; your global harness settings are never edited.
  • Workers. One static profile per harness (model, effort, permission mode). Capacity pools and the host check (defaults: 20 workers, 5 validation, 5 Docker environments, 5 browsers). Workflows (feature, fix, scout) and the default autonomy. The terse style block. Morning-briefing hour (default 05:00).
  • Projects. flowryn project add <repo> for each, with default delivery mode and yolo posture (default no-mistakes, yolo off).
  • Service. Writes a launchd agent with absolute paths, an explicit PATH, KeepAlive and log paths (Flowryn rotates its own logs), starts the daemon, then runs flowryn doctor --contracts.
