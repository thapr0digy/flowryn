# Cutover notes

> **Frozen on 2026-10-09.** New work goes in its own file under [`docs/notes/`](notes/README.md). Fix this file in place; never add a section to it.

The work that let Flowryn replace the previous orchestrator: decisions (C1), prompt wedges (C2), the one-time import (C3, since removed). Spec: the cutover spec in the superpowers vault. Each section records the choices made where the spec left room, and live results.

## C1 · Decisions

- A run-scoped question is `q<N>` (`flowryn ask`); a standalone decision is `k<N>` with its own backlog task (`--kind decision`), held for the user. Content lives in `decisions`; the task, hold and blocked-by edges in the backlog. A decision task has no `task_policy` row, so it counts as landed once Done (`hasLanded`).
- Reserved classes (`[decisions] reserved_classes`): merge, destructive, irreversible, security, credential, outward. Matching is keyword-based in `src/attention/decisions-policy.ts` and errs toward reserved; a source's own `Reserved:` reason wins. A decision becomes `merge` (only if it has no reason yet; a reason is never cleared or replaced) when a task that merges only with a human record (its project not yolo, or `--sensitive`) waits on it, whether through `decision add --blocks` or a later `dispatch --blocked-by`.
- Run-scoped and standalone decisions share one `(origin, key)` index but never fold into each other: `decision add` or a report entry whose key is already the run's own `ask --key` question is refused (a report records it as a warning in `report.decisions`), and `ask --key` refuses a key a standalone decision from its task holds.
- A captain answer is accepted from Claude's prompt (an `ask` rule plus the PreToolUse attempt bound to `decision:<id>`), the Pi `flowryn_decide` confirm (the lease's approval key), your own shell (`human`), your answer to the Claude leader's binding AskUserQuestion question (`via claude-chat`, a chat-answer grant used through `flowryn grant use`; docs/notes/2026-10-10-chat-answers-authorise-5g.md) or, for a review gate's own questions only, your submit on the review page that the daemon's lavish-axi poll returns (`via lavish`, `lavishAnswer`; docs/m5-notes.md, "Gate questions"). Nothing else.
- Dependent work starts by itself only as the scheduler already allows: a plan phase or a `--blocked-by … --auto` ship in an `autonomy = plan` project.
- A leader's rationale is `--rationale <why>`, or `--rationale -` to read it from stdin like `--body-file -`. Any flag whose spec sets `stdin` reads a lone `-` from stdin (other values stay literal); one command reads stdin for at most one flag, else `bad_args`.
- Scout reports: an `## Open decisions` section, one `### <key>: <question>` entry each; a malformed entry becomes a decision with its raw text.
- A Claude leader's gate (`src/leader/hooks.ts`) matches any shell line containing `flowryn … decide … captain`, whatever its spelling (quoted, reordered flags, `--by=captain`, a backslash-newline continuation); the prompt it raises shows the literal command. A line with more than one captain answer gates and prompts but records no attempt for any of them, so none of the `decide` calls it runs can ever match one — it refuses by construction. Every one of a Claude leader session's unmatched approval attempts — merge, discard, gate and decide alike — is voided fail-closed on every tool call, at Stop and at the next prompt (`voidPendingAttempts` in `src/policy/approvals.ts`), so a declined or abandoned prompt can never be reused later in its five-minute window.
- Known, deliberately parked limits, outside the design's confused-agent threat model (design section 7), left open as follow-ups:
  (a) an attempt binds to (action, task), not the exact command text, so a background process the leader started earlier could still race a pending prompt and consume it;
  (b) a leader shell can itself fake a "human" caller — run with no token and a pty (for example `script`) — and answer as captain, since the human path has no approve-style code challenge of its own;
  (c) the Pi shell gate can be dodged by mid-word quoting (for example `fl''owryn hook approval-key`), so the approval key's secrecy, not the shell gate, is the real protection on Pi.
  (d) a review page's answer is accepted as your word when the daemon's lavish-axi poll returns it, and anything local that can reach Lavish's port (a worker included, since it opened the page) can post one with a same-origin header. Two things bound the damage. It reaches only an open question of an open review gate, and the first answer counts, so an answer you already gave is never replaced. Passing the gate still needs a human channel.
  (e) a chat-answer grant is checked against a transcript in Claude's project folder for the leader's own directory, with a tool use that carried no answers, but the leader's hook token can repoint its session's transcript (a forged `hook session-start`): another Claude session in that same directory, run outside a Flowryn leader, that asked the canonical question with prefilled answers (where its transcript does not show them in the tool use) or that the user answered there could still be replayed by a leader that forges the pre- and post-tool hook calls, since nothing ties the transcript to the process `flowryn lead` launched. `flowryn leader repin` (your terminal, a code read from /dev/tty; docs/notes/2026-10-11-flowryn-leader-repin-xv.md) can move the leader's directory to its transcript's folder: it shows the transcript and the Claude process's cwd first, and refuses every grant, question and answer from before it, so a repin moves this limit to a directory you confirmed rather than widening it.

## Approval channels · routine merges

- The Claude leader's settings no longer carry the static ask rule `Bash(flowryn merge *)` (`src/bridges/claude/settings.ts`); the other three ask rules (`gate pass`, `cleanup --discard`, `decide *captain*`) are unchanged. The PreToolUse hook (`src/leader/hooks.ts`) is now the only merge prompt, and its own `ask` prompts in auto mode as well (M0 c08).
- The hook skips a routine merge, one whose task policy is yolo and not `--sensitive` (`isRoutineMerge` in `src/policy/approvals.ts`): no prompt and no attempt recorded, so the merge gate takes the yolo posture and records channel `yolo`. It can never record `claude-ask` for it, since there is no attempt to match.
- Every other merge (a project that is not yolo, a `--sensitive` task, or an unknown task) still gets the hook's prompt and attempt, exactly as before. Sensitive work is refused under yolo by the gate itself (`checkGate` in `src/policy/merge.ts`), so a sensitive merge run without a prompt is refused `approval_required` until you answer a Claude prompt, a Pi confirm, `flowryn approve` or the board.
- The Pi leader is unchanged: `flowryn_merge` still confirms every merge.

## Approval channels · red-check waivers from the leader

- `flowryn merge <task> --allow-red <check>` (`src/policy/verbs.ts`, refused when given twice or empty) waives the one failing check through the leader's own channels, so the user no longer has to switch to a shell for `flowryn approve --allow-red`. Every rule stays in `checkGate` (`src/policy/merge.ts`): the named check must be the only one failing when the gate reads GitHub (on green, two red, or local-only work it refuses `red_checks`), the approval is bound to the head, used once, and only a human channel's record waives (`waiverOf`; a waiver with none is refused `approval_required`); yolo never does, so a waiver merge on a yolo project is not routine and the hook asks.
- **Claude.** `mergeWaiver` (`src/leader/hooks.ts`) reads the check with a strict shell-word reader (`src/util/shell-word.ts`) over that merge's own simple command: bare words of `[A-Za-z0-9._:/@+=,%-]`, `'…'`, `"…"` whose only escapes are a backslash before `"`, `\`, `$` or a backtick, and `--allow-red=<check>`. An expansion, glob, a bare-word backslash, a leading `=` (zsh), an unclosed quote, a repeat, an empty name, a control character or a value starting with `-` (the CLI strips a bare `--json`/`--help` before flags) is unreadable: the prompt says it will be refused and no attempt is recorded. The prompt names the check JSON-quoted beside the PR URL and head, and warns when the checks flowrynd last read disagree. The attempt stores the check (`approval_attempts.allow_red_check`, migration 13) and it is part of `argsHash`, so a plain-merge prompt never matches a waiver, nor the reverse. The claude-ask approval row records `allow_red_check`.
- **Fail-open.** The hook CLI exits 0 on any daemon error, so Claude falls back to its rules. No attempt then means a refusal; the remaining case is a reply lost after the daemon recorded the attempt, where `Bash(flowryn merge *allow-red*)` (`src/bridges/claude/settings.ts`) still makes Claude prompt (test: `hookDecisionsLost` in `test/helpers/fake-claude-leader.ts`). Plain merges keep no static rule, so that case is still open for them (routine yolo merges must stay unprompted). Unverified live: that Claude's matcher applies the mid-command `*allow-red*` wildcard to each part of a compound command (`cd x && flowryn merge …`); the fake anchors rules on the whole line.
- **Pi.** `flowryn_merge` takes an optional `allow_red`; it refuses before asking unless that check is the only failing one in the summary, shows `WAIVE red check: "<check>"` in the confirm, and passes `--allow-red=<check>` as one argument. The key choice carries it, and the row is `pi-confirm` with the waiver.
- The `red_checks` hint now names both ways, shell-quoted (`shellWord`): `flowryn merge <task> --allow-red '<check>'` through the leader, or `flowryn approve <task> --allow-red '<check>'`.

## Approval channels · contract records from the leader

A harness contract record (`harness_contracts`) is what lets dispatch and resume run on a new Claude or Pi version (design section 5), so recording one was human-only: `flowryn doctor` refused any caller with `FLOWRYN_TOKEN` or `FLOWRYN_RUN`. This loosens that boundary in two places, approved 2026-10-06, and adds `[policy] mode` to choose how far.

- **`doctor --contracts --verify-only`** is open to every caller, the leader and workers included. It runs the full suite and writes a report marked `"mode": "verify-only"` (file name `…-verify-only.json`), and never calls the daemon: no `harness_contracts` row, no P1 settled. The leader runs it on a PR's own build (`bun <worktree>/src/main.ts doctor …`) before merging a worker-path PR (`src/lifecycle/`, `src/harness/`, `src/contracts/`, `src/reconcile/`).
- **`[policy] mode = "strict"`** (the default, and what a missing key means): only your own terminal records. The leader's `doctor --contracts` is refused `human_only` before the suite starts, and the skill tells it to ask you.
- **`[policy] mode = "relaxed"`**: the leader may also record, only from the installed build (`recordGrant`, `src/contracts/grant.ts`). The build id is the first 12 hex digits of the compiled binary's sha256 (`buildIdOf`, as `daemon status` and the restart lines show it). The CLI sends its own; the daemon compares it with the one it hashed at start. A PR build, a development command (no build id), or a `dist/flowryn` rebuilt since the daemon started is refused `not_installed_build`, before the suite runs (`contracts.may_record`) and again at the record. The daemon also reads the leader's report: it must be in `<data_dir>/contracts/` (symlinks resolved), a passing recording run of that harness, version and build. Each leader record appends `contract.passed` with `by: leader`, the build and the session, opens a P1 info item `contract_recorded` (your next message's digest: "claude 2.1.300 passed, recorded by the leader (build ab12cd34ef56)"), and adds a line to the next briefing.
- **The daemon's automatic check** (spec 3, phase 2, docs/m5-notes.md "Automatic contract checks"): in relaxed mode the daemon also runs the recording check itself when the harness gate finds a new version, from the pinned copy of its own running build, and records it `by: daemon` after the same report check. The build rule holds by construction (the binary that ran the suite is the one running), you see each record as a `contract_recorded` line and in the briefing, and a failure is one P1 with the report. Strict mode, and a development daemon, never run it.
- **Never**: a worker records (`worker_token`, by role, before any check), nor a read-only leader session (`not_leader`). Your own terminal records exactly as before, in both modes, with no build or report check. Merges, gate approvals and discards are unchanged in both modes.
- **Why the installed build bounds it.** A record vouches for the code that ran the suite: the suite's scratch daemon is the binary that ran `doctor` (`selfCommand()`), so its hooks, prompts and launcher are what was tested. With a PR build the leader would choose the code under test, so a green run of unreviewed code could open dispatch for everyone. Tying a record to the build the daemon runs means a leader record says only "the code you installed works with the harness on disk", which is what you would have checked by hand. A new build applies by itself only when it is a clean build of a merged commit (docs/m5-notes.md, "Automatic restarts"); any other build still needs `flowryn daemon restart`, on your word.
- **Threat, and the parked limit.** The build id and the report come from the caller. A leader shell that writes its own envelope to the socket, with a forged build id and a forged report file, could record without a run: the daemon cannot see which process is on its socket. That is outside the confused-agent threat model (design section 7), parked with C1's limits (a)–(e) above; strict mode closes it, and every leader record is shown to you. Separately, verify-only on a PR build runs worker-written code as you, outside any sandbox (the harness in Herdr, its hooks), as running it by hand did; it records nothing.
- **The sandbox.** A Claude leader's Bash sandbox allows only the daemon socket, and a contract run needs the Herdr socket, binds its scratch daemon's socket and writes under `$TMPDIR`. The leader settings are not widened (that would hand every leader command Herdr); the skill says to run contract checks outside the sandbox, which Claude's permission engine decides (auto mode's classifier may ask you). Unverified live: whether auto mode lets it run without a prompt.

## C2 · Prompt wedges

- Spike `c12-permission-prompt` (`docs/m0-verdicts.md`): Claude's `Notification` `permission_prompt` fires about 6 s after a `PreToolUse` hook raises a confirmation dialog, in both `bypassPermissions` and default mode; Herdr's `agent_status` reads `blocked` for the whole dialog and `working` for a long tool call, with no overlap — one signal tells the two apart, no screen-marker fallback needed.
- The notify path (`hook notify`, `src/lifecycle/hooks.ts`): a `permission_prompt` on a busy run opens one P1 `blocked_prompt` item (`src/lifecycle/prompt-wedge.ts`) carrying the prompt's own line. The screen is read off the pane with Herdr's `recent_unwrapped` source (a secret split across a soft-wrapped line is caught whole only then), capped at 1.5 s so the hook still answers fast. `redactSecrets` (`src/util/redact.ts`, linear in the input) strips private keys, PEM or an armored `PGP PRIVATE KEY BLOCK` (whole, or from a lone `BEGIN`/`END` to the cut end when the pair is split by a tail), known token shapes (`ghp_`/`gho_`/etc, `github_pat_`, `sk-`, `AKIA`, `xox`, `glpat-`) and `Bearer` values; redacts `scheme://user:pass@` URL userinfo to `scheme://[redacted]@`; and for a `--password`/`--token`/`--secret`/`--api-key`-style flag or a `password`/`token`/`secret`/`api_key` label (with or without a surrounding prefix, suffix or quote, such as `AWS_SECRET_ACCESS_KEY=` or `"password":`) redacts to the end of the line rather than just the value, since a passphrase can run several words.
- The hold: while the item is open, liveness stays `blocked_dialog` and the idle/stale pointers are suppressed (`liveChecks`'s `prompted` branch in `src/reconcile/reconciler.ts`). The release: any hook activity (`markBusy`/`markIdle`) resolves it on both harnesses. For Claude the reconciler also clears it from Herdr's `agent_status` (an Esc decline fires no hook afterwards, so hook activity alone would hold it forever): it holds on `null` (Herdr unreachable) and `"unknown"`; releases at once on `"working"` (a dialog and a running tool never overlap); and releases on `"idle"`/`"done"` only once the *previous* pass's recorded status was also settled (`"idle"`/`"done"`) — two consecutive passes, so one flickered read right after the Esc can't release a dialog that is still actually up. Either path, it is also resolved when the run dies or resumes.
- The backstop (same spike, no hook signal at all): for Claude, `agent_status === "blocked"` with no hook for `prompt_suspect_ms` (`[reconcile] prompt_suspect_ms`, default 120 s) opens the same item, marked suspected. Pi has no dialog status to read, so it only ever reports the worker "may be stalled" once a known status is neither `"working"` nor `"unknown"` for that long — a possible stall, never a confirmed dialog.
- Flowryn never sends keys to answer a dialog: the item tells you what the screen shows and nothing more; a human (or the leader's approved channel) decides.

## C3 · Import (removed)

C3 shipped a one-time import from the previous orchestrator's home: its projects (cloned from each old clone's own `origin`), its Queued work, its open decisions and the user's preferences, recorded through an internal `import.apply` verb. The cutover is done, so the import command, its parser, the `import.apply` verb and their tests were removed. What C3 added that stays:

- `dispatch --mode <mode> --mode-reason <why>`: a dispatch may override its project's delivery mode for one task, with the reason kept beside it (`task_policy.mode_reason`).
- Queued tasks outside any plan (`src/lifecycle/queued.ts`): `dispatch --task <id>` starts one once its blockers have landed, and a task whose earlier run failed or was cancelled may be started again.
- `import_source` on projects, tasks and decisions: migration 9 rewrote every stored value to `legacy:<id>`. Nothing writes it any more.
- The import triage line: if `meta.import_triage` is still set, the leader's next briefing says once "Imported earlier: N open decision(s). Decide each one you may with `flowryn decide <id> <choice> --rationale <why>`; leave reserved ones for the user." (`src/attention/briefing.ts`), counting open, non-reserved decisions that carry an `import_source`.
- `~/.flowryn/leader/preferences.md`, which the import wrote once, is still folded into the leader's appended system prompt on every `flowryn lead` (`writeLeaderFiles`).
- Relinking a new build: the launchd plist stores the resolved binary path, so relinking `~/.local/bin/flowryn` alone leaves the daemon on the old build until `flowryn daemon uninstall && flowryn daemon install`. `bootout` is asynchronous, so `loadAgent` (`src/service/launchd.ts`) waits up to 5 s for `launchctl print` to stop finding the old agent, then retries `bootstrap` after 250, 500, 1000 and 2000 ms before failing with the last launchctl output; back-to-back uninstall and install no longer fail with `5: Input/output error`.
- Queued work is visible (`src/lifecycle/queue-view.ts`): `queuedWork` is the one definition fleet, show, the board and the briefing share — a backlog task in Queued, not a standalone decision's task, with no open run (a run that started before the snapshot caught up counts as in flight, never twice). Hand-added backlog tasks with no Flowryn policy count too, with `auto -` and `next -`, since `dispatch --task` cannot start them. Each gets a status: `held` (a backlog hold; it wins over blockers), `waiting` (blockers that have not landed, by `waitingOn`, the rule dispatch and the scheduler use) or `ready`; and `next`: the `dispatch --task` command, `starts by itself` (the scheduler's own rule: an approved plan's phase with auto on and no earlier run in a project whose autonomy is plan; `cannot start (<item>)` while a `phase_blocked` item is open), `starts when unblocked` / `dispatch when unblocked`, or `unhold`. `flowryn fleet` adds a `queued` table (ready, then waiting, then held; by priority, then age; at most 10 rows), `flowryn show <task>` describes a Queued task (an imported scout returned `not_found` before), a task Queued again after its run failed keeps the run view plus a `queued: <status> · <next>` line, the board has a QUEUED section (6 rows), and the briefing reads `Queued: N (r ready, w waiting, h held)`.

## Steers · latency (Tier 0 and Tier 1)

From the steer latency investigation (the 2026-10-04 spec in the superpowers vault). Flowryn's own delivery path was already about 1 ms; these close the gaps it found. Tier 2 (`flowryn steer --urgent`) is the next section.

- **The interrupt key never answers a dialog** (`interruptKeyRefusal` in `src/lifecycle/control.ts`). Escape on a permission dialog declines it, so the Claude interrupt sends the key only while Herdr reads the agent `working` (a dialog reads `blocked`, and the two never overlap, spike c12), and never while the run is `blocked_dialog` or has an open `blocked_prompt`. Herdr unreachable, unsure (`unknown`, null) or reading `idle`/`done` refuses too. A refusal is the error `interrupt_refused` (exit 2, a policy refusal) and a `run.interrupt_refused` event; nothing reaches the pane. The status is read just before the key, so a dialog that opens in the milliseconds between is the remaining window. Pi's interrupt is the extension's abort, not a key, and is unchanged.
- **After an interrupt the idle path wakes at once.** A verified interrupt (either harness) marks every steer it carried but nobody saw `lost` and notifies the bus; before, nothing woke the waiter, so an idle steer waited up to `wait_poll_ms` or a reconcile pass. A Claude worker's waiter is now armed at every `UserPromptSubmit` as well as every `Stop` (`workerSettings` in `src/harness/claude/adapter.ts`): Claude fires no hook on an interrupt (M0 c04), so a turn a waiter woke and Flowryn then interrupted used to leave no waiter at all. The newest waiter supersedes the older ones as before, and the daemon fires one only while the worker is idle, so a turn-start waiter stays parked until the turn ends or is interrupted. asyncRewake from `UserPromptSubmit` was not covered by spike c01 (Stop and SessionStart were); the contract suite's interrupt step now checks it on every harness version (below).
- **Seen** (`messages.seen_at`, migration 8, and a `steer.seen` event) is delivery; the ack stays compliance. Claude: the next `PreToolUse`, `PostToolUse` or `Stop` after a carry, since the model read the attachment (or the woken turn's prompt) at its inference in between; a parallel sibling tool's hook can mark it a moment early. `UserPromptSubmit` is not evidence: it fires before the model reads anything, so a woken turn that ends in `StopFailure` or is interrupted before its first inference leaves the steer carried, and `markLost` rings it again at once. A woken turn's first inference can take longer than `seen_timeout_ms`; that causes no duplicate, because the waiter fires only while the worker is idle and the turn's next hook marks the steer seen before a `PostToolUse` or `Stop` could carry it again. Pi: the worker extension's `context` event, which fires before every model request, shows the steer's message (`hook steer-seen`). An ack also counts as seen when no hook said so first.
- **A lost carry rings again within seconds**, not after `ring_interval_ms` (5 min). Each message keeps its latest ring's state (`ring_state`: carried, seen or lost) and whether it went to an idle worker (`ring_idle`). A steer is due again at once when lost (a verified interrupt, a Claude `StopFailure` or a relaunch of the worker, before it was seen; `seen_via` keeps what marked a ring seen), after `seen_timeout_ms` (`[reconcile]`, default 5 s) when an idle carry was not seen (a Claude waiter wake, or a Pi `followUp`), and after `ring_interval_ms` otherwise. A busy carry has no short clock: it is seen only at the next boundary, which can be a long tool call away. The waiter's long poll wakes for the next of these times as well as for the bus, so no daemon timer is needed. Fast re-rings count toward `max_rings` like any other. `steer.rung` says why a ring is a re-ring (`again`: lost, unseen or interval) and whether the worker was idle.
- **The Pi extension** says how it delivered each steer (`hook steer-carried`, mode `followUp` or `steer`): only a `followUp` to an idle agent starts a turn at once, so only it gets the 5 s clock. The daemon's own idle guess stands until the report arrives. The extension now re-polls 50 ms after an empty reply instead of 1 s.
- **What you see.** `flowryn show` lists the run's latest steers (every open one and the last few acknowledged) with `delivery`: `carried +2ms, seen +2.7s, acked +8.8s` after creation, or `queued 4s`, `not seen for 12s`, `lost, ringing again`. `flowryn fleet` has a `steer` column: the oldest open steer as `m3 queued 2s`, `m3 unseen 12s`, `m3 seen, not acked` or `m3 lost, ringing`.
- **The contract suite measures steers** (`src/contracts/suite.ts`): the busy steer is sent once the worker's first tool call has started (its `PreToolUse`; hook evidence now names the hook), each steer step reports that steer's carried, seen and acked times beside the step's seconds, the runner re-reads the scratch database every 100 ms (was 500 ms) and reports step seconds to a tenth, and the scratch daemon keeps the default `wait_poll_ms`. The interrupt step's long command is acknowledged before it runs, and after the interrupt a second steer ("do not run it again") must reach the idle worker and be acknowledged; so every steer is acknowledged before exit, and the resumed worker no longer re-runs a 120 s sleep before the last deliver (the 131 s the investigation traced).
- **Live, 2026-10-05** (`scripts/lab/m2-live.sh --claude-project <this checkout> contracts`, lab `fm-lab-flowryn-steers-31224-17191`, Herdr lab session, scratch home removed, no contract branch left): **22/22**. Times after each steer's creation:

## Steers · urgent (Tier 2)

`flowryn steer <task> --urgent --body-file -` makes a steer cut in. The approved design (2026-10-05, every recommendation taken) is in the run's report directory; this is what was built.

- **The row and the carriers.** An urgent steer is an ordinary `messages` row with `urgent = 1` (migration 10, with `preempted_at`). The waiter, `PostToolUse`, the `Stop` continuation and the Pi extension still carry it, ring it again, mark it seen and take its ack. Urgency only moves the boundary earlier, in one of two ways: it **blocks** the next tool call, or it **cuts** the running one.
- **Block, Claude.** The next main-agent `PreToolUse` with a due urgent steer answers `permissionDecision: "deny"`, and the reason is the steer line plus "This tool call was blocked so you read this first; redo it if it still applies." (`urgentBlockLine`). It is `steer.rung` with path `pre-tool`, and the hook after the model's next inference marks it seen (the Tier 1 rule). A known limit (accepted): in a parallel batch, a sibling's `PreToolUse` after the deny marks the steer seen, though the model has not read the deny reason yet, so a long sibling is not cut and runs to its end before the steer is read. A subagent's tool hooks (input with `agent_id`) never deny and are not timed: the main agent's `Agent` (Task) call is the running tool, and cutting it cuts the subagent. A hook reply is not a keystroke, so blocking is allowed even with a dialog about.
- **Block, Pi.** An urgent steer delivered into a busy turn is queued as `deliverAs: "steer"` as before, and the extension's `tool_call` handler blocks every call (`{block: true, reason}`, M0 p08) until a `context` event shows the steer, so the batch ends and the queued steer goes into the next request (p13).
- **Cut, when a tool has run `steer_preempt_after_ms`** (`[reconcile]`, default 3 000). The clock is the oldest running main-agent tool. A tool younger than that is cut when it reaches it, and a tool that ends first is not cut at all: its end carries the steer. Each urgent steer cuts at most once (`preempted_at`, `steer.preempted` with `via`, `tool_ms`, `verified`).
  - Claude: `UrgentPreempter` (`src/lifecycle/urgent.ts`) times it from the `pre-tool`/`post-tool` hooks, plus `tool-failed` on `PostToolUseFailure`, which Claude fires instead of `PostToolUse` for a tool that failed (a command exiting non-zero), so a failed tool does not leave a stale clock that would cut a later, younger one (an in-memory tracker keyed by `tool_use_id`, cleared at every turn start, `Stop`, `StopFailure`, `SessionEnd` and verified interrupt; a daemon restart forgets it, so nothing is cut until the next tool starts). At the threshold it calls the verified interrupt, the interrupt key behind `interruptKeyRefusal`. Escape interrupts the whole turn, parallel tools and subagents included (no Claude primitive cancels one tool; accepted). The interrupt clears busy, marks unseen carries lost and wakes the waiter, which fires the steer into the idle session. A key that went but was not verified still counts as the one cut. One attempt runs per run at a time, so a hook's kick while an attempt reads Herdr cannot send a second key.
  - Pi: the extension keeps the clock (it sees every `tool_execution_start`/`end`, so Pi's `pre-tool` stays throttled to once a minute) and asks the daemon `hook preempt {steer, tool_ms}` before it acts: `go` (marked preempted), `defer` (a dialog may be open; it asks again every second) or `go: false` (seen, already cut, the tool too young, not urgent). On `go` it calls `ctx.abort()` (p14). The abort drops the queued copy, so the `stop` the following `agent_settled` sends loses every urgent steer that was queued into the busy turn and never seen (`loseUnseenUrgent`, `steer.lost` reason `turn settled unseen`). The waiter then rings it again at once, now as a `followUp` that starts a turn. The same rule covers an urgent steer queued while the model wrote its final, tool-free message. The bash override that would keep the turn alive is a later option, only if p15's A6 check fails.
- **Never through a dialog.** `interruptKeyRefusal` now reads Herdr's status twice, 500 ms apart, and reads the screen in between for Claude's `Do you want to proceed?`. It refuses on `blocked_dialog`, an open `blocked_prompt`, any read other than `working`, a dialog question on screen, or a screen it cannot read. This applies to `flowryn interrupt` too. A refused cut is `steer.preempt_deferred` (once per steer and reason) and is tried again every second; the preempter's retries do not also append `run.interrupt_refused`, which stays for `flowryn interrupt`. While a `blocked_prompt` is open, each retry applies the reconciler's rule: Herdr reading `working` means the dialog is gone. The retry clears the item (`run.prompt_cleared`) and returns the run to busy, and the approved tool's clock restarts, so it gets its own threshold. Pi aborts send no keys, but the same known-dialog checks gate `hook preempt`. The remaining window is the milliseconds between the last read and the key, as for the manual interrupt.
- **Targets (agreed).** For Claude, the urgent steer is *carried* within 3 s when the tool has already run past the threshold. It is *seen* one inference later, because the Tier 1 rule counts only the first hook after an inference. For Pi, it is *seen* within 3 s (the `context` event fires before the request). Both are reported. Worst case, a steer that lands just as a tool starts is cut at the tool's 3 s mark.
- **What you see.** `show` adds `urgent` and `cut a tool +0.1s` to a steer's delivery line, and `fleet`'s steer column reads `m7 urgent unseen 2s`. The worker contract gains one line: "A tool call may be blocked or cut short to deliver an urgent steer: act on it, then redo the call if it still applies."
- **Contract suite.** A new step, "urgent while busy", sends a normal steer that asks for `perl -e 'sleep 60'` and then an urgent steer a second into it. It requires the tool to be cut (`preempted_at`), the worker to stay alive, and the steer to be acknowledged, and it reports the steer's carried, seen and acked times. The scripted Pi worker's script gained the two acks (m3, m4), so the interrupt step's steers are now m5 and m6.
- **The design's assumptions, live** (2026-10-05, Herdr lab sessions, `docs/m0-verdicts.md` c13 and p15, both **confirmed**). On Claude Code 2.1.289 with Sonnet, a `deny` under `bypassPermissions` stopped the tool and the model read its reason (A1). Herdr already read `blocked` 395 ms after a hook's `ask` (A2), well inside the gate's 3 s threshold and second read. A subagent's Bash hook carried `agent_id` while the main agent's `Agent` call did not (A3). On Pi 0.87.1 (scripted model), a steer queued at a blocked `tool_call` was in the very next request (A4). One queued at a tool-free turn end was delivered before `agent_settled` (A5), so the settle re-ring is only a backstop. `ctx.abort()` killed a bash command's backgrounded child too (A6), so the bash override is not needed. The Pi probe gained a `block_tools` control for p15.
- **Live, 2026-10-05** (`scripts/lab/m2-live.sh --claude-project <this checkout> contracts`, lab `fm-lab-flowryn-m2-76545-14944`, scratch home removed): **24/24**. In the urgent step, the steer is sent about a second into `perl -e 'sleep 60'`, so the tool reaches its 3 s mark about 2 s later.

  |---|---|

- **Determinism.** Nothing here asks a model to decide. The block, the cut, the threshold, the dialog gate and the re-ring are plain rules and timers. The only model in the loop is the worker reading the steer, which is the point of a steer.

## Worker workspaces

- **One pane per worker workspace.** The launcher used to open a workspace and split its root shell to set the run's environment, which left a useless shell beside every worker. `workspace.create` takes `env` too (protocol 17 schema, confirmed live by spike `h06-workspace-env`: the root pane's shell saw the env, a blanked variable as set-but-empty, and the cwd), so the worker now runs in the root pane and nothing splits. `pane.split` left `ALLOWED_METHODS`. Liveness, resume (the same pane, reused while its shell is idle) and cleanup (`workspace.close` by `runs.workspace_id`) are unchanged.
- **The workspace label is the task id alone** (`show-queued-work-m6`, the branch without `flowryn/`), not `flowryn <task>`, which Herdr's sidebar truncated to `flowryn show-…`. The pane's metadata title stays `flowryn <task>`.

## Leader-safe daemon restart

`flowryn daemon restart` lets the leader (or you) apply a new build without your terminal. `daemon stop`, `start`, `install` and `uninstall` stay yours. Every rule is plain code in `src/daemon/restart.ts`:

- **Who.** The daemon checks the caller's token: the lease holder or your own terminal (channel `tty`). A worker gets `worker_token` (exit 77), from its pane before the call and by its token alone at the daemon; a read-only session gets `not_leader`; a script with no token, `role_refused`.
- **The guards** (`restartGuards`), each a query or a look at the daemon's memory, in this order: a merge `requested` or being asked of GitHub (a restart turns it `unproven`); a run held at `blocked_dialog` or with an open `blocked_prompt` item; a live `validation` lease (no-mistakes running before `deliver --pr`; kept as a blocker by the user's choice, though its state is in the database), unless its pipeline only waits on external CI (every active step `ci` with no local agent, from a no-mistakes status read at most 2 min old and read afresh before the decision; docs/m5-notes.md "Leader Stop items and restarts past CI"); a cleanup running; a launch in progress; an `approve` challenge waiting for its code; the daemon's automatic contract check running (`contract_check`, docs/m5-notes.md "Automatic contract checks"). Pending intents are not a guard: they replay at startup, and shutdown already waits for the journal. Plain `restart` refuses `restart_blocked` (exit 2) naming every one. `--when-idle` parks the request in `meta.restart_pending` (who asked, the deadline: `--wait-min`, default 30, at most 240; a second request keeps the first deadline and start, and its reply says so in `kept`, adding that `--wait-min` was ignored when one was given) and returns at once (it parks too when the guards clear between the check and the decision, so `--when-idle` never gets `restart_blocked`); the daemon re-reads the guards every 5 s and restarts once they clear. `--cancel` drops it. An expired request appends `daemon.restart_expired` and opens a `restart_dropped` P1 naming what it waited on.
- **The binary check** (`smokeCheck`): the target is the installed plist's `ProgramArguments` read through `plutil`. A plist that differs from what `daemon install` would write now (program, environment, working directory) is refused `plist_drift`: re-installing stays yours, since a daemon cannot boot itself out and bootstrap afterwards. The target must answer `version --json` (10 s limit, no agent identity in its environment) with a version and a protocol, and a compiled binary must pass `codesign --verify --strict`; otherwise `binary_broken` and the running daemon stays.
- **Builds.** The version string does not change between builds, so each daemon hashes its own compiled binary at startup (`build`, 12 hex digits, in `daemon status`). A target with the running build is refused `no_change` unless `--force`. A development command (bun plus a script) has no build and is never `no_change`.
- **The restart.** The daemon, not the CLI, asks launchd: a detached `launchctl kickstart -k gui/<uid>/<label>` in its own process group. The leader's Bash runs in Claude's sandbox, which allows only the daemon socket, and the daemon runs under launchd with no sandbox. The daemon must be the agent's running pid (`launchctl print`; it and the plist read through `plutil` each have a 10 s limit, a hang counting as not supervised or an unreadable plist); a daemon started in the background is refused `not_supervised`. kickstart sends SIGTERM, the existing clean shutdown runs, and launchd starts the program again. If the helper fails, or cannot be asked at all, while the daemon is still up, the handoff is withdrawn, a `restart_dropped` P1 opens, and the waiting CLI sees the old daemon answer with no handoff and reports `restart_dropped` with the reason at once. The verb is ephemeral: it is never taken from the spool or replayed from the idempotency table, so no stored reply can kick a later daemon. A second restart within 60 s of the last is refused (`restart_cooldown`).
- **The record.** The old daemon writes `daemon.restart_requested` (who, the old pid, version, protocol and build, the target's) and `meta.restart_handoff`. The new daemon, in its `daemon.started` transaction, turns the handoff into `daemon.restarted` (who asked, both builds, the downtime) and closes any `restart_dropped` item. The next briefing shows one line per restart since the last briefing: `Daemon restarted 13:02 by the leader (L3): build 3f9a1c22d0b1→a07e55c9e1f4, 0.5.0, proto 4.` The CLI waits up to 30 s for a daemon with a new pid and prints the old and new pid, version, protocol, build and uptime.
- **Protocol bumps.** The gateway serves `daemon.ping` and `daemon.restart` whatever protocol the caller speaks (`PROTO_EXEMPT_VERBS`), so after a build that bumps `PROTO` the new CLI can still ask the old daemon to restart and recognize the new one. Their arguments are frozen; `test/unit/gateway.test.ts` pins them. Every other verb still refuses a mismatch. This helps from the first daemon that has it onwards.
- **Steers after a restart.** A steer queued to an idle worker just before the restart is delivered by the new daemon through idle-alert-spam-cj's idle-carry fallback (`src/lifecycle/idle-carry.ts`), not a second copy; `test/integration/idle-worker.test.ts` runs it through `flowryn daemon restart`.
- **Test seam.** `FLOWRYN_SUPERVISOR` names a JSON file `{program, restart}` that stands in for launchd, the way `FLOWRYN_NOTIFIER` stands in for the macOS channel: `program` is the target the binary check runs, `restart` a command run detached with `FLOWRYN_DAEMON_PID` set. `superviseWithScript` (`test/helpers/harness.ts`, and `makeFleetEnv({ supervised: true })`) writes one.
- **Tests.** `test/unit/restart.test.ts` (each guard, the binary check's refusals, the controller's request, park, cancel, cooldown, expiry and refusal paths, the new daemon's record, the briefing line once, the launchd pid and plist drift, and the design's assumptions: the real binary answers `version --json`, `launchctl print` shows `pid = N`, a detached helper outlives a SIGTERM to its parent's process group), `test/unit/gateway.test.ts` (roles, the protocol exemption, frozen arguments), `test/integration/daemon-restart.test.ts` (a leader restart end to end, a worker refused, a validation that blocks and then a parked restart, `--cancel`, a broken build, a daemon not under launchd).
- **Not checked live:** `kickstart -k` asked by the job itself, against the real launchd agent; doing it here would restart the fleet's daemon. It belongs to a lab pass with its own `FLOWRYN_HOME` and label.

## Live runs

### The cutover live run

`scripts/lab/cutover-live.sh [--keep] [phase ...]` (phases `decisions`, `prompt`) runs in a Herdr lab session (`spikes/lib/herdr-lab.sh`) against a real Claude Code worker. The Claude project is a linked worktree of the checkout the run itself executes in (one more level of worktree-of-a-worktree on top of the usual worktree-of-a-primary-checkout M2 proved live; `trust.ts`'s canonical-project resolution walks through every level to the one true primary checkout), with `[workers.claude] pretrust = "check"`, so nothing is ever written to `~/.claude.json`. The "prompt" phase's extra `PreToolUse` hook lives in a `.claude/settings.json` committed to that worktree's own disposable branch, not in Flowryn's per-run `--settings` file, so every task worktree Flowryn later checks out from that branch inherits it on top of Flowryn's own hooks (the merge spike c11 proved). Every branch is `flowryn/contract-<runid>-…`, and the run removes exactly the branches and worktrees it made from the checkout by exact name on exit, through `src/contracts/cleanup.ts`'s guard — the same one the other live scripts use.

A first attempt pointed `[workers.claude] config_dir` at a scratch, empty `CLAUDE_CONFIG_DIR` instead (to keep the extra hook, and workspace trust, fully out of `~/.claude`). That is **not** safe: `CLAUDE_CONFIG_DIR` isolates Claude Code's stored credentials along with its settings, so a brand-new directory has none, and the very first real launch hit Claude's own first-run wizard (a theme-style picker, then a login-method prompt) before any hook or task ever ran — the "decisions" phase's scout sat at that dialog until its own 480 s wait timed out. This is a lab/environment limitation of that approach, not a Flowryn bug, and the live script was redesigned around it (the linked-worktree-plus-committed-hook shape above) rather than working around it by typing through the wizard.

Latest full run, 2026-10-04, Herdr 0.7.5, Claude Code 2.1.289 (haiku for both phases' workers), lab session `fm-lab-flowryn-cutover-55982-11565`: **9/9 passed**.
