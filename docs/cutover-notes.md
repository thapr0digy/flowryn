# Cutover notes

The work that lets Flowryn replace Firstmate: decisions (C1), prompt wedges (C2), the Firstmate import (C3). Spec: the cutover spec in the superpowers vault. Each section records the choices made where the spec left room, and live results.

## C1 · Decisions

- A run-scoped question is `q<N>` (`flowryn ask`); a standalone decision is `k<N>` with its own backlog task (`--kind decision`), held for the user. Content lives in `decisions`; the task, hold and blocked-by edges in the backlog. A decision task has no `task_policy` row, so it counts as landed once Done (`hasLanded`).
- Reserved classes (`[decisions] reserved_classes`): merge, destructive, irreversible, security, credential, outward. Matching is keyword-based in `src/attention/decisions-policy.ts` and errs toward reserved; a source's own `Reserved:` reason wins. A decision becomes `merge` (only if it has no reason yet; a reason is never cleared or replaced) when a task that merges only with a human record (its project not yolo, or `--sensitive`) waits on it, whether through `decision add --blocks` or a later `dispatch --blocked-by`.
- Run-scoped and standalone decisions share one `(origin, key)` index but never fold into each other: `decision add` or a report entry whose key is already the run's own `ask --key` question is refused (a report records it as a warning in `report.decisions`), and `ask --key` refuses a key a standalone decision from its task holds.
- A captain answer is accepted from Claude's prompt (an `ask` rule plus the PreToolUse attempt bound to `decision:<id>`), the Pi `flowryn_decide` confirm (the lease's approval key), your own shell (`human`) or, for a review gate's own questions only, your submit on the review page that the daemon's lavish-axi poll returns (`via lavish`, `lavishAnswer`; docs/m5-notes.md, "Gate questions"). Nothing else.
- Dependent work starts by itself only as the scheduler already allows: a plan phase or a `--blocked-by … --auto` ship in an `autonomy = plan` project.
- Scout reports: an `## Open decisions` section, one `### <key>: <question>` entry each; a malformed entry becomes a decision with its raw text.
- A Claude leader's gate (`src/leader/hooks.ts`) matches any shell line containing `flowryn … decide … captain`, whatever its spelling (quoted, reordered flags, `--by=captain`, a backslash-newline continuation); the prompt it raises shows the literal command. A line with more than one captain answer gates and prompts but records no attempt for any of them, so none of the `decide` calls it runs can ever match one — it refuses by construction. Every one of a Claude leader session's unmatched approval attempts — merge, discard, gate and decide alike — is voided fail-closed on every tool call, at Stop and at the next prompt (`voidPendingAttempts` in `src/policy/approvals.ts`), so a declined or abandoned prompt can never be reused later in its five-minute window.
- Known, deliberately parked limits, outside the design's confused-agent threat model (design section 7), left open as follow-ups:
  (a) an attempt binds to (action, task), not the exact command text, so a background process the leader started earlier could still race a pending prompt and consume it;
  (b) a leader shell can itself fake a "human" caller — run with no token and a pty (for example `script`) — and answer as captain, since the human path has no approve-style code challenge of its own;
  (c) the Pi shell gate can be dodged by mid-word quoting (for example `fl''owryn hook approval-key`), so the approval key's secrecy, not the shell gate, is the real protection on Pi.
  (d) a review page's answer is accepted as your word when the daemon's lavish-axi poll returns it, and anything local that can reach Lavish's port (a worker included, since it opened the page) can post one with a same-origin header. Two things bound the damage. It reaches only an open question of an open review gate, and the first answer counts, so an answer you already gave is never replaced. Passing the gate still needs a human channel.

## C2 · Prompt wedges

- Spike `c12-permission-prompt` (`docs/m0-verdicts.md`): Claude's `Notification` `permission_prompt` fires about 6 s after a `PreToolUse` hook raises a confirmation dialog, in both `bypassPermissions` and default mode; Herdr's `agent_status` reads `blocked` for the whole dialog and `working` for a long tool call, with no overlap — one signal tells the two apart, no screen-marker fallback needed.
- The notify path (`hook notify`, `src/lifecycle/hooks.ts`): a `permission_prompt` on a busy run opens one P1 `blocked_prompt` item (`src/lifecycle/prompt-wedge.ts`) carrying the prompt's own line. The screen is read off the pane with Herdr's `recent_unwrapped` source (a secret split across a soft-wrapped line is caught whole only then), capped at 1.5 s so the hook still answers fast. `redactSecrets` (`src/util/redact.ts`, linear in the input) strips private keys, PEM or an armored `PGP PRIVATE KEY BLOCK` (whole, or from a lone `BEGIN`/`END` to the cut end when the pair is split by a tail), known token shapes (`ghp_`/`gho_`/etc, `github_pat_`, `sk-`, `AKIA`, `xox`, `glpat-`) and `Bearer` values; redacts `scheme://user:pass@` URL userinfo to `scheme://[redacted]@`; and for a `--password`/`--token`/`--secret`/`--api-key`-style flag or a `password`/`token`/`secret`/`api_key` label (with or without a surrounding prefix, suffix or quote, such as `AWS_SECRET_ACCESS_KEY=` or `"password":`) redacts to the end of the line rather than just the value, since a passphrase can run several words.
- The hold: while the item is open, liveness stays `blocked_dialog` and the idle/stale pointers are suppressed (`liveChecks`'s `prompted` branch in `src/reconcile/reconciler.ts`). The release: any hook activity (`markBusy`/`markIdle`) resolves it on both harnesses. For Claude the reconciler also clears it from Herdr's `agent_status` (an Esc decline fires no hook afterwards, so hook activity alone would hold it forever): it holds on `null` (Herdr unreachable) and `"unknown"`; releases at once on `"working"` (a dialog and a running tool never overlap); and releases on `"idle"`/`"done"` only once the *previous* pass's recorded status was also settled (`"idle"`/`"done"`) — two consecutive passes, so one flickered read right after the Esc can't release a dialog that is still actually up. Either path, it is also resolved when the run dies or resumes.
- The backstop (same spike, no hook signal at all): for Claude, `agent_status === "blocked"` with no hook for `prompt_suspect_ms` (`[reconcile] prompt_suspect_ms`, default 120 s) opens the same item, marked suspected. Pi has no dialog status to read, so it only ever reports the worker "may be stalled" once a known status is neither `"working"` nor `"unknown"` for that long — a possible stall, never a confirmed dialog.
- Flowryn never sends keys to answer a dialog: the item tells you what the screen shows and nothing more; a human (or the leader's approved channel) decides.

## C3 · Import

- `flowryn import firstmate <home>` is read-only on the Firstmate home: the command (`src/cli/commands/import.ts`) reads `data/projects.md`, `backlog.md`, `note-archive.md`, `done-archive.md`, `captain.md`, `learnings.md`, `captain-shared.md` and each old clone's `origin`; nothing in the command or `import.apply` ever writes there. `src/import/firstmate.ts` is a pure parser with no filesystem access of its own — it only turns the text the command reads into projects, items and decisions. Everything the import records (a project, a queued task, a decision) carries `import_source = firstmate:<id>`, so a re-run finds its own prior work and reports `exists` instead of redoing it. `--only <project>` (repeatable) limits the import to the named project(s): every other project and its tasks are left out of the plan entirely, while a decision belonging to one still shows as its own `skip` row (`repo … is not imported`).
- The clone rule (`src/cli/commands/import.ts`): for each non-`local-only` project, the command reads the *old* clone's own `origin` (`git -C <old> remote get-url origin`) and clones exactly that URL into `--clone-root/<name>` (`git clone -- <origin> <target>`; the `--` and an outright refusal of an origin beginning with `-` mean a hostile old clone can never be read as a git option). If `--clone-root/<name>` already exists, it is **adopted** when its own `origin` matches the old clone's (no second clone; the plan still names it) and **refused** when it does not — this is what lets `--apply` be re-run after a partial failure without redoing the clones it already finished. The old clone itself is read-only throughout.
- The mode mapping (`mapMode` in `src/import/firstmate.ts`): Firstmate's `no-mistakes-prod-only` becomes Flowryn's `no-mistakes`; `direct-PR` and `local-only` pass through unchanged. A `local-only` Firstmate project is skipped outright (`skip: "local-only, not migrated"`) — Firstmate's own local-only work was never meant to travel.
- The decision rules (`selectDecisions` in `src/import/firstmate.ts`): a candidate is a `(kind: captain)` backlog or archive item carrying a `Decision key:` body line, **keyed by `(project, key)`**, not by its own item id — Firstmate reuses a key across report revisions on purpose, so the same question can be re-raised and re-answered more than once (a real instance is traced below, in the row-count note). A key is **resolved** the moment any `[x]`-checked `(kind: captain)` item anywhere (the live backlog, `note-archive.md` or `done-archive.md`) shares that `(project, key)`; every other still-open candidate with the same key then imports as `skip (resolved <that item> is done)`, whatever its own id or archive date — one answer settles every instance of the question, by design. Among candidates that remain unresolved for the same key, the **live backlog copy wins, else the newest `## Archived <date>`**; every other one is `skip (superseded by <winner>)`. A `(kind: captain)` item with no `Decision key:` line, or a held item of another kind sitting in the archive, is never silently dropped: it comes back as `review`, for a human to read by hand.
- The preferences file (`import.ts`): `captain.md` and `learnings.md` (and `captain-shared.md`, when present) are read line by line; a `-`-prefixed line naming Firstmate's own machinery (`FIRSTMATE_MACHINERY`: captain, `fm-*.sh`, `bin/fm-`, firstmate, secondmate, crewmate) is held out rather than kept. `--apply` writes `~/.flowryn/leader/preferences.md` (0600) once: the kept lines first, then a `## Review` section holding the flagged ones verbatim, so nothing is silently discarded — keep, reword or delete each reviewed line by hand. Once that file exists, every later run (dry or `--apply`) leaves it alone and reports each of its source files `exists ("preferences.md already exists; edit it in place")`, so the leader's own hand edits are never clobbered by a re-run. A file that is absent (most homes have no `captain-shared.md`) imports as `skip absent`, never an error. `writeLeaderFiles` (Task 18) folds `preferences.md` into the leader's appended system prompt (`leader/system-prompt.md`, style block then preferences) on every `flowryn lead` launch.
- Nothing from the backlog is dropped without a row: a Queued item whose repo is unknown, local-only, or left out by `--only` is `skip ("repo <repo> is not imported")`; a Queued item still held in Firstmate is imported Queued anyway, plus a `warn` row naming the hold reason, truncated to 80 characters (`held in Firstmate (<reason>); not held here`) — the reason is the user's own data and the row only ever reaches their own terminal. A task's `blocked-by` edge that cannot be kept — the blocker's repo is not imported, the blocker was itself refused (an id collision, its own project not imported), or the blocker simply does not exist — becomes a `warn` row on the dependent (`blocked-by <id> dropped: <why>`) and the task still imports without that edge; a blocker that has already landed (a decision resolved elsewhere) is dropped silently, since nothing is actually missing. A `blocked-by` edge that names a Firstmate captain/decision item this import is itself about to create as a decision is kept and remapped, inside `import.apply`, to that decision's real new task id; an edge naming a superseded copy follows its winner, and one naming a captain/decision item this import does not create is a `warn` row (`a Firstmate decision this import does not create`) (decisions are created before tasks for exactly this reason, though their rows still print after the task rows, in the plan's own order). `import.apply` creates a plan's tasks in dependency order over blockers that are themselves plan tasks, not file order, so a dependent listed before its blocker in Firstmate's own backlog still creates both (tasks-axi's `add --blocked-by X` fails if X is not yet in the backlog); a genuine cycle refuses only its actual members (`blocked-by cycle`), and a task merely downstream of one — blocked by a cycle member but not itself part of the cycle — still creates, with that one edge dropped and a `warn` row naming it (`blocked-by <id> dropped: blocked-by cycle`).
- The `links` row: the printed relink commands end with `flowryn daemon uninstall && flowryn daemon install`. The launchd plist stores `process.execPath`, the resolved binary path, so relinking `~/.local/bin/flowryn` alone leaves the daemon running the old build until the agent is reinstalled. `bootout` is asynchronous, so `loadAgent` (`src/service/launchd.ts`) waits up to 5 s for `launchctl print` to stop finding the old agent, then retries `bootstrap` after 250, 500, 1000 and 2000 ms before failing with the last launchctl output and whether the old agent is still loaded; back-to-back uninstall and install no longer fail with `5: Input/output error`.
- The import triage: the moment any decision is actually created (not merely previewed), `import.apply` sets `meta.import_triage = 1`. The leader's very next briefing then carries one extra line — "Imported from Firstmate: N open decision(s). Decide each one you may with `flowryn decide <id> <choice> --rationale <why>`; leave reserved ones for the user." — counting only open, non-reserved, `import_source`-carrying decisions, and flips the flag off once shown, so it appears exactly once (`src/attention/briefing.ts`).

## Steers · latency (Tier 0 and Tier 1)

From the steer latency investigation (the 2026-10-04 spec in the superpowers vault). Flowryn's own delivery path was already about 1 ms; these close the gaps it found. Tier 2 (`flowryn steer --urgent`: blocking the next tool call, preempting a long one) is not built and needs your approval.

- **The interrupt key never answers a dialog** (`interruptKeyRefusal` in `src/lifecycle/control.ts`). Escape on a permission dialog declines it, so the Claude interrupt sends the key only while Herdr reads the agent `working` (a dialog reads `blocked`, and the two never overlap, spike c12), and never while the run is `blocked_dialog` or has an open `blocked_prompt`. Herdr unreachable, unsure (`unknown`, null) or reading `idle`/`done` refuses too. A refusal is the error `interrupt_refused` (exit 2, a policy refusal) and a `run.interrupt_refused` event; nothing reaches the pane. The status is read just before the key, so a dialog that opens in the milliseconds between is the remaining window. Pi's interrupt is the extension's abort, not a key, and is unchanged.
- **After an interrupt the idle path wakes at once.** A verified interrupt (either harness) marks every steer it carried but nobody saw `lost` and notifies the bus; before, nothing woke the waiter, so an idle steer waited up to `wait_poll_ms` or a reconcile pass. A Claude worker's waiter is now armed at every `UserPromptSubmit` as well as every `Stop` (`workerSettings` in `src/harness/claude/adapter.ts`): Claude fires no hook on an interrupt (M0 c04), so a turn a waiter woke and Flowryn then interrupted used to leave no waiter at all. The newest waiter supersedes the older ones as before, and the daemon fires one only while the worker is idle, so a turn-start waiter stays parked until the turn ends or is interrupted. asyncRewake from `UserPromptSubmit` was not covered by spike c01 (Stop and SessionStart were); the contract suite's interrupt step now checks it on every harness version (below).
- **Seen** (`messages.seen_at`, migration 8, and a `steer.seen` event) is delivery; the ack stays compliance. Claude: the next `PreToolUse`, `PostToolUse` or `Stop` after a carry, since the model read the attachment (or the woken turn's prompt) at its inference in between; a parallel sibling tool's hook can mark it a moment early. `UserPromptSubmit` is not evidence: it fires before the model reads anything, so a woken turn that ends in `StopFailure` or is interrupted before its first inference leaves the steer carried, and `markLost` rings it again at once. A woken turn's first inference can take longer than `seen_timeout_ms`; that causes no duplicate, because the waiter fires only while the worker is idle and the turn's next hook marks the steer seen before a `PostToolUse` or `Stop` could carry it again. Pi: the worker extension's `context` event, which fires before every model request, shows the steer's message (`hook steer-seen`). An ack also counts as seen when no hook said so first.
- **A lost carry rings again within seconds**, not after `ring_interval_ms` (5 min). Each message keeps its latest ring's state (`ring_state`: carried, seen or lost) and whether it went to an idle worker (`ring_idle`). A steer is due again at once when lost (a verified interrupt, or a Claude `StopFailure`, before it was seen; `seen_via` keeps what marked a ring seen), after `seen_timeout_ms` (`[reconcile]`, default 5 s) when an idle carry was not seen (a Claude waiter wake, or a Pi `followUp`), and after `ring_interval_ms` otherwise. A busy carry has no short clock: it is seen only at the next boundary, which can be a long tool call away. The waiter's long poll wakes for the next of these times as well as for the bus, so no daemon timer is needed. Fast re-rings count toward `max_rings` like any other. `steer.rung` says why a ring is a re-ring (`again`: lost, unseen or interval) and whether the worker was idle.
- **The Pi extension** says how it delivered each steer (`hook steer-carried`, mode `followUp` or `steer`): only a `followUp` to an idle agent starts a turn at once, so only it gets the 5 s clock. The daemon's own idle guess stands until the report arrives. The extension now re-polls 50 ms after an empty reply instead of 1 s.
- **What you see.** `flowryn show` lists the run's latest steers (every open one and the last few acknowledged) with `delivery`: `carried +2ms, seen +2.7s, acked +8.8s` after creation, or `queued 4s`, `not seen for 12s`, `lost, ringing again`. `flowryn fleet` has a `steer` column: the oldest open steer as `m3 queued 2s`, `m3 unseen 12s`, `m3 seen, not acked` or `m3 lost, ringing`.
- **The contract suite measures steers** (`src/contracts/suite.ts`): the busy steer is sent once the worker's first tool call has started (its `PreToolUse`; hook evidence now names the hook), each steer step reports that steer's carried, seen and acked times beside the step's seconds, the runner re-reads the scratch database every 100 ms (was 500 ms) and reports step seconds to a tenth, and the scratch daemon keeps the default `wait_poll_ms`. The interrupt step's long command is acknowledged before it runs, and after the interrupt a second steer ("do not run it again") must reach the idle worker and be acknowledged; so every steer is acknowledged before exit, and the resumed worker no longer re-runs a 120 s sleep before the last deliver (the 131 s the investigation traced).
- **Live, 2026-10-05** (`scripts/lab/m2-live.sh --claude-project <this checkout> contracts`, lab `fm-lab-flowryn-steers-31224-17191`, Herdr lab session, scratch home removed, no contract branch left): **22/22**. Times after each steer's creation:

## Live runs

### The cutover live run

`scripts/lab/cutover-live.sh [--keep] [phase ...]` (phases `decisions`, `prompt`) runs in a Firstmate lab session (`fm-herdr-lab.sh`) against a real Claude Code worker. The Claude project is a linked worktree of the checkout the run itself executes in (one more level of worktree-of-a-worktree on top of the usual worktree-of-a-primary-checkout M2 proved live; `trust.ts`'s canonical-project resolution walks through every level to the one true primary checkout), with `[workers.claude] pretrust = "check"`, so nothing is ever written to `~/.claude.json`. The "prompt" phase's extra `PreToolUse` hook lives in a `.claude/settings.json` committed to that worktree's own disposable branch, not in Flowryn's per-run `--settings` file, so every task worktree Flowryn later checks out from that branch inherits it on top of Flowryn's own hooks (the merge spike c11 proved). Every branch is `flowryn/contract-<runid>-…`, and the run removes exactly the branches and worktrees it made from the checkout by exact name on exit, through `src/contracts/cleanup.ts`'s guard — the same one the other live scripts use.

A first attempt pointed `[workers.claude] config_dir` at a scratch, empty `CLAUDE_CONFIG_DIR` instead (to keep the extra hook, and workspace trust, fully out of `~/.claude`). That is **not** safe: `CLAUDE_CONFIG_DIR` isolates Claude Code's stored credentials along with its settings, so a brand-new directory has none, and the very first real launch hit Claude's own first-run wizard (a theme-style picker, then a login-method prompt) before any hook or task ever ran — the "decisions" phase's scout sat at that dialog until its own 480 s wait timed out. This is a lab/environment limitation of that approach, not a Flowryn bug, and the live script was redesigned around it (the linked-worktree-plus-committed-hook shape above) rather than working around it by typing through the wizard.

Latest full run, 2026-10-04, Herdr 0.7.5, Claude Code 2.1.289 (haiku for both phases' workers), lab session `fm-lab-flowryn-cutover-55982-11565`: **9/9 passed**.

A `--blocked-by <task> --auto` ship was filed, Queued, before any answer. **Row-count difference from the original planning estimate**: that estimate expected 20 decisions `create` and 2 items of one shared decision key `skip (resolved …)`; the run above shows 0 `create` and 22 `skip (resolved …)`. **The estimate was itself stale, not the live data** — traced by hand against the real `data/backlog.md`, `note-archive.md` and `done-archive.md`:
- The estimate's "20 create" counted each item's "awaiting captain decision" copy in `note-archive.md`. But 21 of the 22 `skip (resolved …)` rows above resolve against a **different, `[x]`-checked copy of that exact same item, already sitting in `done-archive.md`** — each one recorded there with "Resolution mode: answered" and a done date of 2026-09-20 through 2026-09-23, **before** the estimate was made. Reading `done-archive.md`, alongside `note-archive.md` and the live backlog, is what catches exactly this shape of record — an answer for an item that would otherwise still look open — and turns these candidates into `skip (resolved …)` instead of the predicted `create`.
- The remaining 1 of the 22 is the one decision key called out above: it was asked three times for the same project, re-using the same `Decision key:` across report revisions (by design — see the rule above). Two of its three copies resolve the ordinary way just described (their own `[x]` copy in `done-archive.md`, before the estimate was made); the third resolves by the `(project, key)` rule itself, against one of those other two rather than its own copy — also already answered before the estimate was made.
- The `review` count (2: a held ship that is not a decision, and a captain item with no `Decision key:`) matches the original estimate exactly.
- Idempotency still holds for every row, resolved ones included: a second `--apply` against a fresh copy of the same home (below) reproduces every `skip`/`review` row byte-for-byte, and turns every `create` into `exists`.

No committed file carries the private text of any decision, preference or task title; the table above is counts and row shapes only, by design — never the content of a real decision or preference.
