# Versioned harness contract compatibility

- Status: done
- Open: not run live (a real `doctor --contracts` against Claude and Pi in a lab session); no test forces a revision decision when adapter code changes (bumping stays a reviewer's call)

`docs/next_steps.md` package 4, first slice: a harness contract pass names the adapter and contract behaviour it proved, not only the harness version, so a behaviour change makes older evidence visibly stale while a docs-only or unrelated commit keeps reusing it. Plain code throughout, no model.

## Design

### The boundary

A pass is identified by `(harness, version)` alone. `recordPass` (`src/contracts/verbs.ts`) upserts `harness_contracts` on that key, and the gate (`checkHarness`, `unverifiedVersion` in `src/lifecycle/harness-gate.ts`) asks only `WHERE harness = ? AND version = ?`. The report and the `contract.passed` event carry the build, but nothing reads it back. So:

- A change to what the suite proves (how the Claude adapter launches, resumes or wires hooks; the Pi extension bridge; a contract step) keeps every old pass of the installed harness version valid. The gate lets dispatch through on evidence about behaviour that no longer exists.
- Using the build id to fix that would go the other way: every commit, a docs-only one too, would demand a new contract run (a paid one for Claude).
- The P1 and the automatic check dedupe on the harness version alone (`harness_flagged:<h>` holds the version, `unverifiedItemOpened` matches `$.version`, `settled()` compares the attempt's version), so even with a stale pass recognised, a version whose P1 was dismissed or whose automatic check already failed would never be flagged or checked again.

Repro (test first): a pass for the installed version at revision 1, and a build whose revision for that harness is bumped to 2 (`checkHarness` and `gateHarness` take the revision map, so a test bumps it without editing the constant). Before this change nothing could tell the two apart; after it the gate says `unverified` with revision 1 named as stale.

### The rule

- **A compatibility revision per harness.** `CONTRACT_REVISIONS` in `src/contracts/revision.ts`: a hand-bumped integer per harness, starting at `1` for both. It is bumped in the same PR as a change to behaviour that harness's contract suite proves (its adapter and launch, the hook or extension bridge the worker path uses, a step in `src/contracts/suite.ts` for it); a docs, test or unrelated change never touches it. Revision `1` is the *baseline*: the adapter behaviour when revisions were introduced, which is what every pass recorded before them proved (this change proves no new behaviour), so anything stored without a revision (a pass, a report, an automatic attempt, a flag, a P1's event) reads as revision 1. The revision is a source constant, never derived from the build id, so two builds of the same revision reuse each other's evidence.
- **Identity of a pass: `(harness, version, revision)`.** `harness_contracts` gets `revision` in its primary key, so a pass at one revision never overwrites another (a human recording from an older CLI cannot replace a current pass with a stale one).
- **The gate requires the daemon's own revision.** `checkHarness` verifies only a pass at `(harness, installed version, CONTRACT_REVISIONS[harness])`. A version that has passes only at other revisions is `unverified` with `stale: [revisions]`, and every place that says why names it: the `contract_unverified` refusal ("passed only at contract revision 1, not revision 2"), the `harness_unverified` P1 line, the `harness.unverified` event (`revision`, `stale`), `flowryn doctor`'s contract check.
- **What the recording carries.** The suite's report records `revision` (the revision of the binary that ran it) and `context`: `platform` (`<os>-<arch> <release>`), `herdr` (`herdr --version` of the configured Herdr binary, null when it cannot be read) and `launch_profile` (the worker launch settings the suite ran with: Claude's model, effort, permission mode, pretrust and extra args; `scripted` for the Pi gate). `recordPass` writes them as columns and into `contract.passed`. Context is recorded and shown, not compared: making the Herdr version or the platform part of the identity would re-run paid suites on every Herdr update, which is a separate decision.
- **Where each recorder's revision comes from.** The verb's arguments do not change (no `PROTO` bump): the revision comes from the run's report.
  - The daemon's automatic check and the leader: the report must already pass `reportProblem` (passing, recording, this harness and version, the daemon's own build); it now must also carry the daemon's revision, else it is refused ("proves contract revision N, not this daemon's M"). Their records are therefore always at the current revision.
  - Your own terminal: authority unchanged (recordGrant is untouched; no report check). The record takes the report's `revision` when the report is readable and names this harness and version, and the baseline otherwise (an older CLI wrote no revision, and its code is the baseline's or older). After a bump, such a record is stale like any other. A record that is not at the daemon's revision is still written, and the reply says `current: false` with the revision the gate needs, which `doctor --contracts` prints as a warning: recorded, but dispatch still refuses it.
- **Alert dedup and automatic attempts carry the revision.**
  - `harness_flagged:<h>` holds `{"version","revision"}` JSON; a plain version string (written before this) reads as the baseline, so the upgrade itself re-flags nothing.
  - `unverifiedItemOpened` matches `$.version` and `$.revision` (missing reads as the baseline), so one P1 opens per `(version, revision)`: a P1 dismissed for a version at revision 1 does not hide the same version going stale at revision 2, and the upgrade opens no second P1 for a version already flagged.
  - `noteContractPassed` settles the flag and P1 when a pass for the flagged version is at the daemon's current revision, whatever revision the flag recorded (a plain-version flag from before revisions included); a pass at any other revision, such as a stale human record, settles nothing.
  - `AutoAttempt.revision` (missing reads as the baseline): `settled()`, `noteWaiting`, `activeAutoAttempt` and the refusal's "check queued/running" help compare version and revision, so a check that failed at an older revision runs again at the new one, once, while one that failed before revisions stays final for that version. Events `contract.auto_*` carry `revision`.
- **Strict vs relaxed recording authority is unchanged**: the same callers record in the same modes; only what a record says it proved changes.

### Migration (23, `contract-revision`)

`harness_contracts` is rebuilt with `revision INTEGER NOT NULL DEFAULT 1 CHECK (revision >= 1)` in the primary key and nullable `platform`, `herdr_version`, `launch_profile`. Existing rows keep `passed_at` and `report_path` and carry over at revision 1, the baseline.

The first design marked them legacy (revision 0), needing a re-run. The leader's review (2026-10-12) changed that, for upgrade safety: legacy refused every Claude dispatch, resume and new stage, in-flight runs included, until a Claude automatic check of up to 2 h passed, and one failure was final until a manual doctor run, so a deploy blocked the fleet. Revision 1 is defined as the adapter behaviour when revisions were introduced, and that is exactly what the existing passes proved, since this change alters no proven behaviour. So an upgrade refuses nothing; only a later bump of `CONTRACT_REVISIONS` makes these passes stale, and then the automatic check (relaxed) or the P1 naming the stale revision and `flowryn doctor --contracts --harness <h>` (strict) asks for the re-run, as for any untested version.

Automatic attempts in `meta.contract_auto:<h>`, flags left as plain versions and the events of P1s opened before this have no revision either, and read as the baseline the same way.

### Files

`src/contracts/revision.ts` (new: the constants, labels), `src/contracts/context.ts` (new: platform, Herdr version, launch profile), `src/db/schema.ts` (migration 23), `src/contracts/verbs.ts` (record identity and context, reply), `src/contracts/grant.ts` (`reportProblem` checks the revision), `src/contracts/report.ts` (the report carries revision and context; `reportFacts` reads them for a record), `src/contracts/runner.ts` (result carries revision and context; the scratch seed records at the current revision), `src/lifecycle/harness-gate.ts` (gate, flag, P1 dedup, refusal), `src/contracts/auto.ts` (attempt revision), `src/doctor/doctor.ts` (contract check), `src/cli/commands/setup.ts` (stale record warning), `test/helpers/harness.ts` (a stand-in `herdr` that answers a version), `test/helpers/fleet-env.ts` (seeds at the current revision, or `contractsAt`), `src/reconcile/reconciler.ts` (its unchecked stand-in carries the revision), `src/lifecycle/auto-resume.ts` and `src/sched/wait-reasons.ts` (a resume or launch waiting on a stale pass names the stale revision, through `harnessWaitReason`, as `harnessFacts` does), `scripts/lab/*-live.ts` (`--seed-contracts` seeds, and the recorded-pass checks look, at the current revision).

### Out of scope

Verification-policy identity and native acceptance (package 4's other slices). A check that forces a revision decision whenever adapter files change (a fingerprint test would conflict across parallel PRs touching those files); the bump stays a reviewed edit. Herdr version or platform as part of the identity.

## Build

- **Version** 0.24.0. `PROTO` stays 6: no verb argument changed (the revision travels in the report), and `contracts.record`'s reply only gains fields (`revision`, `current`, `required_revision`); a CLI that does not read them treats the record as before.
- **Wording.** A stale pass reads "claude 2.1.300 passed only at contract revision 1, not revision 2" in the refusal, the P1 and doctor; the P1 line stays inside the 200-character digest, so the doctor command at its end is never cut.
- **Tests.** `test/unit/contract-record.test.ts` (revision and context on a record; a leader's report at another revision is refused; a report from before revisions is at the baseline; a record at another revision never overwrites a current one; doctor's check and `doctor --contracts`' warning; Herdr version parsing and launch profiles), `test/unit/auto-contract.test.ts` (a pass from another build at the current revision runs no check; a bump, through an injected revision map, makes the pass at the old revision stale and opens one P1; a pass at another revision is re-recorded by the daemon; an attempt failed at another revision runs once more, one failed before revisions stays final; a report at another revision is not recorded; strict: a flag and P1 from before revisions open no second P1, only a pass at the current revision settles the P1, a plain-version flag included), `test/unit/db.test.ts` (migration 23 on a database in use: the passes stay verified at revision 1 and go stale at a bump to 2), `test/integration/harness-gate.test.ts` (startup and dispatch name the stale revision; a current pass lets dispatch through; a pass recorded before revisions refuses nothing), `test/integration/auto-contract.test.ts` (a compiled daemon re-runs a pass at another revision and records it at its own, with the context).
