# Verify results bound to their policy

- Status: not built
- Open: design only; the build follows

`docs/next_steps.md` package 4, its second slice: a local verification counts only for the verify policy it ran under, not just for the head it ran at. Plain code throughout (a normalizer, a hash, a column, a comparison); no model. The contract-revision work (#73) is a separate PR and not touched here.

## Design

**Boundary.** A `verifications` row records the PR and head, but not which commands checked it. `finishedAtHead` (`src/verify/store.ts`) selects by PR and head alone, and `localGreenOf` (`src/policy/merge.ts`) accepts any passing row it finds. So after you strengthen `[projects.<id>] verify` (add `npx oxlint`, say) or change `verify_binary`, an old pass at the same head still stands in for checks GitHub never started, though it never ran today's steps. `verify.start` (`src/verify/verbs.ts`) attaches a caller to the running job for the same PR and head even when that job runs yesterday's steps. Repro tests: a pass recorded under one step list still yields local green after the config gains a step; a running job under the old steps is attached to after the config changed.

**Rule.**

1. **A canonical policy identity.** `verifyPolicyId` (`src/verify/policy.ts`) hashes, with SHA-256, the canonical JSON array `["flowryn-verify-policy", 1, <steps>, <binary or null>]` and returns `vp1:<64 hex>`.
   - Steps keep their order: a step list run in another order is another check (an install after the tests is not the same run), so reordering changes the identity.
   - Each step is normalized so formatting noise does not count: leading and trailing whitespace trimmed, and each run of spaces and tabs outside quotes collapsed to one space. Whitespace inside single or double quotes, or after a backslash, is kept, since there it is part of an argument (`echo "a  b"` differs from `echo "a b"`). Newlines are kept (in `/bin/sh` a newline separates commands).
   - The artifact is `verify_binary` as `verifyConfig` already normalizes it (`./dist/flowryn` and `dist/flowryn` are one path); no artifact is `null`.
   - The encoding is a fixed-order array, so object key order or TOML layout never reaches the hash; the leading tag and version let a later encoding change the identity on purpose.
   - Not part of it: `verify_timeout_min` (a longer or shorter limit does not change what a pass proved) and the project id (a result already belongs to one PR, so to one project).
2. **Snapshotted at start, stored with the result.** Migration 23 adds `verifications.policy_id TEXT` (nullable: rows from before it are legacy and keep `NULL`). `verify.start` computes the identity in `prepare` from the same `verifyConfig` it runs, and `insertVerification` writes it with the row; `pr.verify_started` and `pr.verified` carry it as `policy`, and `verify show` prints it (`-` for a legacy row). The steps a job runs and the identity it records come from one config read, so they cannot disagree.
3. **Attachment needs the same identity.** A running job for the same PR and head attaches only when its `policy_id` equals today's. Otherwise the start is **refused** with `verify_busy`, naming the job and saying it checks a different verify policy (the config changed since it started) and so would not cover today's steps; the hint is to wait for it (`flowryn verify show <id>`) and run `flowryn verify` again. Refusing, not starting a second job, keeps package 7's rule of one verify per daemon and one validation slot (docs/notes/2026-10-12-next-steps-md-64.md); the refusal writes nothing and takes no slot. Same-policy attachment and every lease behaviour are unchanged.
4. **Merge-time reuse needs the same identity.** `MergeContext` gains `verifyPolicy(projectId)`: today's identity from the loaded config, or `null` when the project has no verify steps (a malformed table throws `config_invalid`, refusing the merge loudly; it is read only when every red check is one GitHub never started, so other merges never read it). `LocalEvidence` gains `policy` (today's identity), and its `atHead` becomes the newest finished verify at this head **under today's identity** (`finishedAtHead` now takes the identity and matches `policy_id` exactly, so a legacy `NULL` never matches), plus `otherPolicyAtHead`: the newest finished verify at this head under any other identity or none, read only for the message. `localGreenOf`, in order:
   - a same-policy pass at this head: local green, as before;
   - a same-policy failure or error at this head: `red_checks`, as before;
   - otherwise a result at this head under another policy, or a legacy one: the new code **`verify_stale`** (exit 2, a policy refusal): "CI never started at h2; the local verify v4 at this head ran under another verify policy (the `[projects.web]` verify steps or `verify_binary` changed since) and does not cover today's", or "...ran before Flowryn recorded its verify policy", or "...and project web has no verify steps now"; help `re-verify this head under today's steps: flowryn verify <task>`;
   - otherwise a pass at an older head: `head_moved`, as before; else `red_checks` with `flowryn verify <task>`, as before.
5. **The narrow exception stays narrow.** Nothing about which checks local green may cover changes: only red github-actions runs GitHub never started, every red one of them, and still no pending check and still an approval (sensitive work still a human one). A stale or legacy result covers nothing and can only add a refusal.

**Kept.** Package 7's job lease, admission, release and recovery; `--detach` and following; `lastPassed` (any policy, only for the `head_moved` message); `show`'s verification line.

**Files.** `src/verify/policy.ts` (new), `src/verify/store.ts`, `src/verify/verbs.ts`, `src/db/schema.ts` (migration 23), `src/policy/merge.ts`, `src/policy/verbs.ts` (`mergeContext`), `src/api/errors.ts` (`verify_stale`).

**Tests planned.** Unit: normalization (whitespace noise equal; quoted whitespace, a changed command, a reordered list, a changed or added binary differ; timeout ignored); the gate (an unchanged policy reuses the pass; a strengthened policy at the same head is `verify_stale` naming re-verification; a legacy result is `verify_stale`; a same-policy failure still `red_checks`; a stale pass never lifts a ran-and-failed or pending check or a missing approval); `finishedAtHead` never returns a legacy or other-policy row; migration 23 on a database with a verification keeps it with `NULL`. Integration: `flowryn verify` records the identity; a second `flowryn verify` after the config gained a step, while the first job runs, is refused `verify_busy` and takes no slot; with the same config it attaches; the merge gate end to end refuses an old pass after the steps change, merges on it with them unchanged, and asks for re-verification of a legacy row.
