# Local verify

- Status: done
- Open: a real `flowryn verify` of a Flowryn PR under the launchd daemon not yet run live (the bun suite inside the daemon, the GitHub fetch over ssh from launchd's environment)
- Config: `[projects.<id>] verify`, `[projects.<id>] verify_binary`, `[projects.<id>] verify_timeout_min`

GitHub Actions minutes ran out, so every PR was tested by hand: a detached worktree at the head, install, typecheck, lint, the full suite, the build, then a check that the head had not moved before merging. `flowryn verify <task|pr-number|pr-url>` does it as one command, and the merge gate reads its result. Plain code throughout (a config table, shell steps, a regex over bun's summary, a SQL lookup at the gate); no model.

- **Steps** (`src/verify/config.ts`): `[projects.<id>] verify = [...]` in config.toml, run in order through `/bin/sh -c` in the worktree; `verify_binary` (a file the steps build, relative to the worktree) is copied to `<state_dir>/verify/v<n>/bin/` with any symlink beside it that names it (`flowrynd`), and kept for `doctor --contracts --verify-only`; `verify_timeout_min` (30) bounds the whole run. The steps live in your config, never in the repository, so a PR cannot change the check that lets it through the gate; a `project set` flag was not used for the same reason (a leader could rewrite it). A project without steps is refused (`not_configured`) with the bun list to paste. No list is built in: a guessed one fails confusingly on other stacks. A known limit: the commands are fixed, but what they run is the PR's own (its package.json scripts, its tests), so local green trusts the PR's test code as CI would.
- **Where it runs** (`src/verify/runner.ts`): in the daemon, outside every sandbox, so it can write the worktree and run a `bun test` that needs sockets. The CLI verb (`src/cli/commands/verify.ts`, local, like `approve`) starts it with the internal `verify.start` and follows `verify show` once a second, one line per step; Ctrl-C stops following, never the job; `--detach` returns the id. The same PR at the same head under the same verify policy attaches to the running job (docs/notes/2026-10-13-next-steps-md-y4.md). A new job takes a `validation` slot under the scheduler's host check (docs/notes/2026-10-12-next-steps-md-64.md); without one it is queued, never refused (docs/notes/2026-10-22-daemon-run-verify-y3.md). A leader-safe restart waits for it (guard `verifying`); a daemon that stops mid-run kills the step's process group, and the next daemon records the row as an error and removes its worktree.
- **The head** (`ensureHead`): already in the project's object store (a worker's commit, since worktrees share it), else `git fetch --refmap= origin refs/pull/<n>/head`, else the head branch; the empty refmap keeps the fetch from moving origin's remote-tracking branches, and `--no-write-fetch-head` keeps it off FETCH_HEAD, so it writes objects only (two jobs in one repository can fetch at once). Then `git worktree add --detach <state_dir>/verify/v<n>/wt <sha>`, removed with `git worktree remove --force` (or, for a verification's own path only, rm and prune). Fork PRs are refused (`fork_pr`): the daemon runs the PR's code unsandboxed.
- **Environment** (`stepEnv`): the daemon's, minus `FLOWRYN_*`, `CLAUDECODE`, `CLAUDE_CODE_*`, `GH_TOKEN` and `GITHUB_TOKEN`, with `NO_COLOR=1`. PATH is the caller's (the CLI sends it), absolute entries only: launchd's PATH has the [tools] directories and the system ones, not `~/.bun/bin`, so `bun` would not be found otherwise (found while building; the design had assumed the daemon's PATH).
- **Recorded** (migration 16, `src/verify/store.ts`): a `verifications` row (id, project, PR URL, task, head, state running/passed/failed/error, steps with each one's state, exit, duration, log and counts, the test counts, detail, binary, directories, times) with `pr.verify_started`, `pr.verify_step` (each start and end) and `pr.verified` (head, each step's pass/fail, exit and duration, the counts, the total duration, the binary). Counts come from bun's closing summary (`parseBunSummary`: the last `N pass`/`fail`/`skip`/`todo` lines and `Ran N tests across M files`). Each step's output is a log beside the row; the CLI prints the last 30 lines of a failed one. The newest three finished directories per project are kept; rows stay, and `verify show` marks a pruned binary `(removed)`. `flowryn show <task>` gains `verified: v4 passed at fc2f76d7 (1843 pass, 0 fail)`.
- **Local green at the merge gate** (`src/policy/merge.ts`): when GitHub never starts a job (billing, a spending limit), the check run still fails, with a failure annotation reading "The job was not started because …" (read from PR #37's real check run on 2026-10-06). `Check` now carries the run's id, app and annotation count, and `Forge.annotations` reads them; the gate asks only when every red check is a failed github-actions run with annotations. If every red check is not-started and the newest finished verify at exactly the PR head, under today's verify policy, passed, step 3 passes and the merge records `local_green: v<n>` (`merge.requested`, the merges row). One at this head under another verify policy, or from before policies were recorded, is `verify_stale` (docs/notes/2026-10-13-next-steps-md-y4.md). A verify that passed only at an older head is `head_moved`; one that failed at this head is `verify_failed`, and none is `verify_required`, each with `flowryn verify <task>` as the help (`red_checks` only for a project with no verify steps). Since 2026-10-15 a project with verify steps needs this pass on every merge, whatever GitHub's checks say, and the merges row keeps its id in `local_green` (docs/notes/2026-10-15-merge-gate-require-bf.md). A check that ran and failed is never covered; pending checks, the approval and the sensitive rule are unchanged; `--allow-red` is unchanged. Local green is evidence, not a waiver, so a yolo merge may use it. Not-started is matched per check run (by id), so a second run with the same name that ran and failed rules local green out. If GitHub changes the wording, or the annotations cannot be read (the outage is noted as for any GitHub read), the gate falls back to `red_checks` or the `--allow-red` waiver (fails closed).
- **Choices made in the build**: the caller's PATH (above); `not_found` for a PR GitHub does not have; `verify show` reads the failed step's log file beside the database (also offline).
- **Tests**: `test/unit/verify.test.ts` (the summary parser, the config, the scrubbed environment and PATH, a real job in a real repository: pass with the binary and its symlink kept, a failing step, a timeout that kills what the step started, an unfetchable head, a fetch that writes no ref, a missing binary, pruning, startup recovery and the restart guard, a copied ad-hoc-signed bun binary still verifying on macOS; the gate's local-green rows; which red checks count as not started) and `test/integration/verify.test.ts` (with a real daemon and the fake GitHub: merge refuses, `flowryn verify` passes and keeps the binary, `show` and `verify show`, the merge lands on local green; a PR number, a PR URL and `--detach`; one job at a time (the same PR and head attaches, another PR is `verify_busy`); a fork, an unknown PR and an unconfigured project refused).
- **Version**: 0.18.0. `PROTO` stays 6: new verbs, no changed argument.

## Configuration

`[projects.<id>]` in `~/.flowryn/config.toml`: `verify`, the steps in order; `verify_binary`, a built file to keep; `verify_timeout_min`, default 30. For this repository:

```toml
[projects.flowryn]
verify = ["bun install --frozen-lockfile", "bun run typecheck", "npx oxlint", "bun test", "bun run build"]
verify_binary = "dist/flowryn"
```
