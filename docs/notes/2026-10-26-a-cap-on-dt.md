# A worker limit per project

- Status: done
- Config: `[projects.<id>] max_workers`

Scout finding 15 (scout-efficiency-and-fz): the only worker limit was the shared `[capacity] worker` pool, so a project with a heavy test suite, or one bound to a single device (a phone simulator), could not say "at most two of mine at once" without slowing every other project. The predecessor had a per-project cap (ac0811c4); this follows the scout's summary of it, not its code.

## Config

```toml
[projects.ios]
max_workers = 2
```

A positive integer. Left out, the project has no limit of its own and only `[capacity] worker` binds. Zero, a negative, a fraction or a string is `config_invalid` when the config loads (startup and SIGHUP keep the last good config). A value above `[capacity] worker` is allowed; it never binds. `flowryn config` shows it under the project.

## Behaviour

- **What counts:** the project's live `worker` pool leases (`pool_leases` joined to `task_policy.project_id`): ships and scouts alike, since a scout's worker runs on the same machine. A verify's job lease is not a worker and never counts; verifies keep the `validation` pool as their limit.
- **When it is checked:** only by a grant that takes a worker slot (a first launch, a resume or relaunch of a run whose worker slot was released). A live worker moving to its next stage keeps its slot and is never held. In `tryGrant` (`src/sched/scheduler.ts`) the check runs after the shared pools; `grantLeases` (`src/sched/pools.ts`) counts again inside the grant's transaction and throws `ProjectAtLimit` (an `OverCapacity`), so two grants at once cannot overfill it.
- **A held run:** the scheduler records explanation `capacity.project_full`, "project web is at its worker limit (1/1)", with its holders as a fact and the unblock "raise `[projects.web] max_workers`". The grant moves on to the next candidate, so a project at its limit never holds up another project. The 30-minute capacity wait alert covers it like any capacity wait.
- **A lowered limit** stops nothing: running workers carry on, and new starts wait until the count is under the limit.
- **`flowryn capacity`** adds `projects` rows (`project`, `workers`, `max`) for each project with a limit, filtered by a scoped leader's lens, and a waiting run's `why` reads "project web at its worker limit (1/1)".

## Choices

- No migration: the count derives from the lease rows, which are already released at stage end, run end or a dead worker, so a separate counter could only drift.
- Zero is refused rather than meaning "paused": parking a project is a different feature, and "at its worker limit (0)" would mislead.
- No `PROTO` bump: `flowryn capacity` only gains an output field. No contract revision: the worker contract is unchanged.

## Tests

- `test/unit/project-worker-limit.test.ts`: parsing and load-time refusal; what counts (scouts, released slots, other projects, job slots); the in-transaction re-count; the scheduler holding a fresh start and a resume at the limit, granting another project's run past it and a live worker's next stage, and starting the held run once a slot frees.
- `test/integration/capacity.test.ts` "max_workers = 1": through the daemon and CLI with fake workers, a second web task waits with the project reason in `flowryn capacity` while an api task starts, and starts once the first is cancelled.
