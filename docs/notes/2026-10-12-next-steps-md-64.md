- Status: done

`docs/next_steps.md` package 7: give `flowryn verify` a durable job lease in the same `validation` pool and host check as a ship's no-mistakes pipeline, so local verification is no longer heavy work outside admission control. Plain code throughout (a table, a count inside a transaction, the existing host check); no model.

## Design

**Boundary.** `verify.start` (`src/verify/verbs.ts`) checks only its own one-at-a-time guard (`runningVerifications`) and its `settle` starts `runVerification` at once. Nothing counts it in `liveCounts` (`src/sched/pools.ts`), so with `validation = 1` a ship can hold the validation slot while a verify runs `bun install`, the type check and the full suite beside it, and the scheduler can grant the slot to a ship while a verify runs. The host check is never read: a verify starts with 1 GB free or a load of 4 per core. A daemon killed mid-verify leaves the step's process group running (it is spawned `detached`), and the next daemon marks the row an error and removes its worktree under the still-running step. Repro tests: a verify refused nothing with the validation pool full or the host check failing, and a ship granted the last slot while a verify runs.

**Rule.**

1. **A job lease, not a fake run.** Migration 21 adds `job_leases` (`id, pool, kind, job_id, task_id, granted_at, released_at, released_by, proc_pid, proc_start, proc_exe`), `kind` checked to `'verify'`, one live row per (`pool`, `kind`, `job_id`). `pool_leases` stays run-only (its `run_id` is `NOT NULL REFERENCES runs`, and the validation guard, CI wait and stuck-slot reads join it to runs), so no run is fabricated and no run query sees a job. `liveCounts` sums both tables, so `fullPools`, the scheduler's grants, `grantLeases`' re-count and `flowryn capacity` all see a verify's slot (its `jobs` rows list each one). `grantJobLease` re-counts inside the caller's transaction and throws `OverCapacity` exactly like `grantLeases`; `releaseJobLeases` updates only a live row and appends `pool.released` only when it changed one, so a second release is a no-op. Grant and release append `pool.granted` / `pool.released` with `{ job, kind, pools }`.
2. **Admission at start.** `verify.start` order in `apply` (one immediate transaction, the single writer): the same PR at the same head running attaches (no host or pool check: it takes nothing new); another verify running is still `verify_busy` (kept: one verify per daemon, the pool is the shared budget on top); the host verdict, read in `prepare` through `ctx.sched.host()` (the scheduler's own cached check, recorded on a flip as today), refuses with `no_capacity` and its reason; then the row is inserted and `grantJobLease(validation)` taken in the same transaction, `OverCapacity` becoming `no_capacity` naming who holds the slots (`t3 (ship), v2 (verify)`) and the hint `flowryn capacity`. A refused start writes nothing (the transaction rolls back). No queue: the caller runs it again. A verify does not yield to runs already waiting for validation (it is the leader's explicit request, and the run waits at most one verify); recorded here as a conservative non-change.
3. **Release after cleanup.** `runVerification`'s `finally` releases the lease after the step's process group is killed (`runStep` resolves only after SIGKILL to the group) and after `removeWorktree` and `pruneDirs` ran; a cleanup that fails is logged and the lease still released (holding it would shrink the budget until a restart for work that is not running). Then the scheduler is kicked (`VerifyDeps.released`), so a waiting ship gets the slot.
4. **The step's identity.** Each step's `/bin/sh` (the group leader) is read from `ps` after spawn and written to the lease (`proc_pid/start/exe`, with a `pool.job_process` event), only while the lease is live. A read taken while the leader is still being exec'd (macOS `ps` names it in parentheses, `(sh)`) is re-read until the name settles (up to 2 s, else logged and not recorded), since that transient name would never match the running step and recovery would take it for absent.
5. **Startup recovery.** `recoverVerifications` walks every live job lease (all belong to a dead daemon at startup) and every running row: it ends a recorded step by identity, its whole group (`terminate`, `src/runtime/proc.ts`; a reused pid is never signalled; once the leader it signalled is gone, any member of the group still alive, one that ignored SIGTERM, is SIGKILLed, but a group whose leader was already gone is never signalled), records a running row as an error, removes the worktree, then releases the lease (`released_by` "recovered at startup"). A step that does not exit keeps its lease (logged; the next startup tries again) rather than freeing a slot that is still in use. A running row from before migration 21 has no lease and is recovered as before. Each job is recovered on its own: one that throws (a failed `ps` read) is logged as `verify <id>: recovery failed: ...`, has a running row recorded as an error (so `verify_busy` and the `verifying` restart guard stop waiting on it) but keeps its slot and worktree for the next startup to retry through the lease, and the rest are still recovered.

**Kept.** Same-job attachment, `--detach` and following (the CLI is unchanged), the restart guard `verifying`, exact-head detached worktrees, fork refusal, the merge gate's local green.

**Files.** `src/db/schema.ts` (migration 21), `src/sched/pools.ts`, `src/sched/scheduler.ts` (a public `hostCheck`), `src/sched/services.ts` (`host()`), `src/daemon/daemon.ts` (wiring), `src/sched/verbs.ts` (`capacity` lists job leases), `src/verify/verbs.ts`, `src/verify/runner.ts`, `src/api/errors.ts` (`no_capacity`).

**Out of scope.** Policy identity for verify results (package 4); upkeep builds adopting job leases; a job queue; changing default caps (no measurement under the fake fleet was made for that).

## Built

- **Choices made in the build.** `task_id` on the lease, so `pool.*` events and `flowryn capacity` name the task a verified PR belongs to. A `ps` read that fails (a sandbox, a quick step already gone) is logged and the step runs on without a recorded identity: its group is still killed when it exits, and only a crash in that window leaves it to the old behaviour. The refusal is `no_capacity` (exit 2, like `verify_busy`). The scheduler is kicked only when a release changed a row.
- **Tests.** `test/unit/workflows.test.ts` (a job's and a run's slots against one cap, neither grant overfilling the other; release exactly once; a step's identity only on a live lease), `test/unit/db.test.ts` (migration 21 on a database in use, a verification running before it holding no slot, one live lease per job, only `verify`), `test/unit/verify.test.ts` (pass and fail each release once, after the step's group and the worktree are gone; startup recovery ends a real detached step group by identity before removing the worktree and freeing the slot, once; a group member that ignores SIGTERM is ended too; one job's failed recovery records its row as an error, keeps its slot until a later startup frees it once, and does not stop the next; a step that will not exit keeps its slot until a later startup; a slot whose row already finished is freed), `test/integration/verify.test.ts` (host pressure refuses and writes nothing, an attach with the pool full and the host failing takes nothing, the slot freed once with its event) and `test/integration/capacity.test.ts` (a verify and a ship with `validation = 1`: the ship waits `full: validation`, gets the freed slot, then a new verify is refused naming it; a sampler over both tables never sees 2; the 24-ship run's sampler now counts job leases too).
