# CI-wait watchdog

- Status: partial
- Open: phase 2 (policy follow-through: a policy change on main steers in-flight ships to merge it) follows from plan p10; a real pipeline's `axi abort` of a CI wait and `no-mistakes rerun` after the merge not yet run live
- Config: `[validation] ci_wait_alert`

A ship's no-mistakes pipeline whose PR has no checks (Actions is off) waits in its `ci` step for no-mistakes' `ci_timeout` (168 h here) unless its branch has main's `no_ci: true`, and nothing said so: the run read `validating`, the worker waited and the validation slot stayed leased. Phase 1 of task pipeline-watchdog-and-pt; phase 2 (policy follow-through) is plan p10. Plain code throughout: the status flowrynd already reads, one GitHub read, git, fixed text; no model.

- **The rule** (`src/lifecycle/ci-wait.ts`, run from the delivery watcher's poll after each status read, never from the restart guard's read): the pipeline waits only on CI (`waitsOnlyOnCi`: every active step `ci`, no `agent_pid`), on the run's own branch, for at least `[validation] ci_wait_alert` minutes, and the PR no-mistakes names has no checks at its head (`forge.pull`, then `forge.checks`; a PR not open, not on this GitHub, or a failed read skips the pass; no PR named counts as no checks). The clock is the `ci` step's `active_for` (no-mistakes' own, so a flowrynd restart does not reset it); when that is unreadable, `ci_since` in the run's `nomistakes` evidence, the first read of this pipeline run waiting (`applyNmObservation` keeps it across reads of the same run id).
- **GitHub reads share the watcher's backoff**: the CI-wait read is skipped while the PR watcher is backing off, and its own failure backs off the same way (an outage or rate limit opens the same GitHub P1, a rate limit's `retryAt` is honoured); a successful read ends that outage, so a CI-wait read is never a tight retry loop.
- **The branch's facts** (`readBranchFacts`): `git fetch origin <default>` in the worktree, then `.no-mistakes.yaml` at `origin/<default>` and at `HEAD` (a top-level `no_ci: true` line; an unreadable file counts as absent) and `merge-base --is-ancestor origin/<default> HEAD`. The question says when the branch lacks main's `no_ci: true`; when the branch already has main's tip it says merging changes nothing and recommends `keep-waiting` instead of `merge-main` (it never recommends skipping CI).
- **The decision**: a run-scoped `q<N>`, origin `ci-wait`, key `<no-mistakes run id>-<n>`, non-blocking, reserved for you (`the user's call: a ship waiting on CI`), options `merge-main | accept-without-ci | keep-waiting`, with a `worker_question` item (`CI wait q12 on <title>: no checks for 90 min; branch lacks main's no_ci: true [...] recommends merge-main; relay: flowryn decide q12 <choice> --by captain`), so the leader's question wake, its Stop, away mode and the Pi confirm carry it unchanged. One per stall: an open one waits; `merge-main` or `accept-without-ci` settles that pipeline run for good (the run after the merge is a new stall); `keep-waiting`, or a question closed unanswered, is asked again (`-2`, `-3`, ...) once another alert period has passed since.
- **Carrying it out** (`answerDecision` in `src/lifecycle/decision-verbs.ts` asks `ciWaitSteer` for the text instead of the generic "Answer to your question"): `merge-main` steers the worker to merge origin/main with a new commit (never rebase or force-push), run the tests, then `no-mistakes rerun`, which cancels the stale CI monitor and validates the branch again (the no-mistakes skill's recovery for a monitor that is no longer useful; `axi run` would only reattach to it); `accept-without-ci` steers it to end the CI wait (`no-mistakes axi abort`), change nothing, `git pull --ff-only` and deliver. The merge gate already passes a PR with no checks (`none`), and the leader's merge prompt line adds `the user accepted it without CI (q12)`. `keep-waiting` sends nothing. flowrynd itself still never drives the pipeline: the worker ends its own run's wait.
- **Closing unanswered**: a wait that ends first (the pipeline moves past CI, ends, or names another run; no run) closes the open question (`decision.dismissed`, `answered_via = watchdog`, its item resolved) with no steer, and so does the run leaving `running`/`validating` (each poll's `strandedCiWaits`). `flowryn dismiss` of its item tells the worker nothing either (the worker never asked).
- **`[validation]`** (`src/config/validation.ts`): `ci_wait_alert`, whole minutes, default 60, 0 off; unknown keys refused, validated with the other sections.
- **Choices** (the design page, approved): the worker ends the wait, since flowrynd only reads no-mistakes and aborts only parked runs at cleanup; zero check runs is the test, since pending checks mean CI runs, just slowly; a `worker_question` item so every relay path works with no router change; a normal steer, since an urgent one may cut a running tool.
- **Tests**: `test/unit/ci-wait.test.ts` (the delivery watcher's poll on a scratch database, real git and a status stand-in: one decision past the alert naming the missing `no_ci`, one per stall, under the alert, pending checks, GitHub down and its backoff, off, a CI fix round, a branch that already has main, each answer's steer, merge-main settling the run and a new run asking again, keep-waiting asking again after the period, a wait that ends, a cancelled run, the `ci_since` fallback; `no_ci` parsing; `[validation]`); `test/integration/ci-wait.test.ts` (the real daemon, fake worker and fake GitHub with no checks: the decision opens, the Claude leader cannot answer it alone, relays accept-without-ci, the worker gets the steer, delivers, and the merge prompt names the answer; a dismissed question steers nothing).
