# Build after merge and upkeep hooks (spec 3, phase 3)

- Status: done
- Open: a build by the launchd daemon of a real Flowryn merge not yet run live (launchd's PATH and environment)
- Config: `[upkeep] build_after_merge`, `[upkeep] sync_primary`, `[upkeep] clean_ended_hours`, `[upkeep] nudge_conflicts`, `[upkeep] interval_ms`, `[tools] bun`

After each Flowryn merge the leader still ran `bun run build`; it also ran `flowryn cleanup` on failed and cancelled runs by hand, and nothing moved a primary checkout forward, so dispatch (which branches from the local default branch) started runs on stale code. The spec 3 review chose "the daemon builds it" (question `build-after-merge`) and three of four upkeep hooks (question `extra-hooks`: sync, clean, nudge; pruning Done items was not chosen and is not built). Plain code throughout: git, `bun install`, `scripts/build.sh`, a rename, the cleanup guard, GitHub's `mergeable`; no model.

- **The loop** (`src/upkeep/upkeep.ts`): a pass every `[upkeep] interval_ms` (10 min), and one second after a landed run is cleaned (the `delivery.cleanup` wrapper in `src/daemon/daemon.ts` kicks it). In order: sync each project's primary checkout, build the Flowryn merge, then sweep ended worktrees. One pass at a time; a pass waits (does nothing until the next kick or tick) while a restart is asked for or under way, or a cleanup runs, since sync and cleanup both work in the primary checkout.
- **Build after merge** (`src/upkeep/build.ts`, `[upkeep] build_after_merge`): the Flowryn checkout is the project whose path is the running build's stamped source (the build watcher's own match); a development daemon never builds. It fetches `origin/<default branch>`; when the tip is neither the running build's commit nor the last attempt (`meta.upkeep_build`), it checks the tip out detached in `<data_dir>/build/<project>` (a linked worktree of the primary checkout, reused: `checkout --detach --force`, `clean -ffdx -e node_modules`, then HEAD and a clean `git status` are verified), runs `bun install --frozen-lockfile` when there is a `package.json`, then `scripts/build.sh <dir of the installed binary>/.flowryn-build/<name>` with `FLOWRYN_BUILD_SOURCE` set to the primary checkout (build.sh stamps the commit and the clean tree itself), and renames the result over the installed binary (the supervisor's target, read as the watcher reads it). The staging directory sits beside the binary, so the rename is atomic, and build.sh's `flowrynd` link lands there, not beside the real binary; it is removed either way. The watcher then sees a clean build of a merged commit and restarts onto it through the guards (phase 1). The tip, not the one merge commit: two quick merges build once, and a merge made on GitHub outside Flowryn is caught by the timer. Each step has 15 min; the output of every step goes to `<state_dir>/logs/build-<commit>.log`. A failure is one `build_failed` P1 (`Build after merge failed for flowryn at 1a2b3c4d (tell the user), binary unchanged; log ~/.flowryn/state/logs/build-1a2b3c4d5e6f.log: scripts/build.sh exited 1`: the log before the detail, so the 200-character line keeps it; the event keeps the whole detail), not retried for that commit; the next merge tries again and a success closes it. With no `bun` (`[tools] bun`, PATH, then `~/.bun/bin/bun`, where Bun's installer puts it and launchd's PATH does not reach) a `build_failed` P1 says so. While a build runs the restart has a new `build` guard, since launchd's restart kills the job's process group; no build starts while a restart is asked for.
- **Sync** (`src/upkeep/sync.ts`, `sync_primary`): `git fetch origin <branch>`, then `git merge --ff-only origin/<branch>` only when the checkout is on its default branch, has no tracked changes (untracked files alone do not stop it) and its branch is an ancestor of origin's. Git's own refusal (an untracked file the merge would overwrite, a lock) is a skip too. Uncommitted changes, local commits (ahead or diverged) or a refused merge open one `checkout_unsynced` P1 info line per project, replaced when the reason changes and closed once the checkout is in step; off its default branch is left to dispatch's `checkout_tangle`; no origin or a failed fetch is only logged. A fast-forward is an `upkeep.synced` event.
- **Clean ended worktrees** (`src/upkeep/sweep.ts`, `clean_ended_hours`, 24; 0 turns it off): a `failed` or `cancelled` run whose worktree exists, whose cleanup is not done and that has not been updated for that long goes through `cleanupRun` with no discard, marked `sweep: true` in its `cleanup.done`/`cleanup.refused` event. The guard decides: one with unlanded work is refused and kept, and the refusal opens no item (a cancel with unlanded work is a task you parked; `flowryn cleanup --discard` remains the way to drop it). A refusal updates the run, so it is asked again only after another full wait. A worktree an open run uses is never swept.
- **Nudge a conflicting PR** (`nudge_conflicts`; `src/reconcile/delivery.ts`, `src/lifecycle/send-back.ts`): the forge's `PullRequest` gains `mergeable` (GitHub's PR read, which the delivery watcher already makes; null while GitHub computes it). A delivered ship (state `ready`) whose PR reads `mergeable: false` at the delivered head is sent back the way `decline` sends it (both now call `sendBack`: the run is running again, approvals void, the merge gate closes, the last stage starts again through the scheduler, resuming a worker that is gone) with the steer "Your PR … conflicts with main … Merge origin/main into your branch with a new commit (git fetch origin, then git merge origin/main), resolve the conflicts, run the tests, then ship it again and deliver. Never rebase or force-push.", a `run.conflict_nudged` event and a `conflict_nudged` P1 info line. Once per delivered head, at most 3 per run (`MAX_CONFLICT_NUDGES`): a head nudged before (delivered again unchanged) or a fourth conflict opens one `pr_conflict` P1 instead, closed when the PR reads mergeable or the run lands. The fake GitHub computes `mergeable` with a trial merge on its bare origin (a knob forces it).
- **`[upkeep]`** (`src/config/upkeep.ts`): `build_after_merge`, `sync_primary`, `nudge_conflicts` (all `true`), `clean_ended_hours = 24`, `interval_ms` (for tests); unknown keys refused, validated with the other sections. `[tools] bun` is a new optional tool (init's hint, doctor's optional line).
- **Choices** (the design page, approved): a daemon-owned worktree rather than the primary checkout, so a build never sees your edits or moves your branch; no tests in the build (merged code passed validation, and the watcher's binary check refuses a broken one); the nudge reuses decline's send-back so it goes through the scheduler like any stage start; one item kind per hook, so each is dismissable on its own.
- **Tests**: `test/unit/upkeep-sync.test.ts` (real git: a fast-forward and its event, in step, tracked changes, an untracked file alone, an untracked file in the way, ahead then diverged, off the branch, no origin and a failed fetch, the item closing; `[upkeep]` defaults, switches and refusals), `test/unit/upkeep-build.test.ts` (real git with a stand-in `build.sh` that stamps as the real one does: the tip built and renamed with a new inode, staging and link gone; the design's assumption that the real build watcher applies what the builder installs; the running commit and a tried commit; a failure's P1 and the next merge; no bun; a hung step; a development daemon and no project; the `build` guard while it runs; the worktree reused and cleaned, node_modules kept), `test/unit/upkeep.test.ts` (the sweep's selection, the nudge-or-ask rule, the pass's order, switches, waits and timer), and `test/integration/upkeep.test.ts` through the real daemon with the fake Herdr and the fake GitHub (a conflicting PR nudged with the steer and its item, the same head delivered again asking you with `pr_conflict`; the switch off; a merged PR landing and the primary checkout fast-forwarded; a cancelled run cleaned by the sweep, its workspace closed, while one with unlanded work is kept with no item). The real `build.sh` compiling a stamped binary is phase 1's `test/integration/binary.test.ts`.
