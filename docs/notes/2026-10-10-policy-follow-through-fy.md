# Policy follow-through

- Status: done
- Open: a real worker's merge and `no-mistakes rerun` after a follow-through steer not yet run live
- Config: `[validation] follow_paths`, `[validation] follow_interval_ms`

A ship whose branch forked before main changed its validation policy validates under the old policy. Its pipeline might wait on CI because the branch lacks main's `no_ci: true`, or its CI might run old workflows, and nobody told it to merge main. Phase 2 of task pipeline-watchdog-and-pt; phase 1 (the CI-wait watchdog) is `2026-10-09-pipeline-watchdog-and-pt.md`. Plain code throughout: git, a timer and fixed text; no model.

- **The policy files** (`[validation] follow_paths`): `.no-mistakes.yaml` and `.github/workflows/` by default (the design review's q41: "no-mistakes.yaml and workflows"). They are git pathspecs, so a directory needs its trailing slash. Only plain relative paths are accepted (no `:` pathspec magic, no leading `-` or `/`, no `..`). An empty list turns the follow-through off.
- **The pass** (`src/upkeep/policy-follow.ts`, `PolicyFollower`): runs every `[validation] follow_interval_ms` (5 min), and one second after each cleanup attempt, whatever its outcome, since a landing moved main even when its cleanup was refused. One pass runs at a time. Per project with candidates, it fetches `origin/<default>` once from the first candidate's worktree; linked worktrees share refs, so every run sees it. A failed fetch reads the last fetched tip and is logged once per change of error. The policy hash is the sha256 of `git ls-tree -r origin/<default> -- <paths>`: paths and blob ids, with no file reads.
- **Candidates**: no-mistakes ships (`kind = ship`, `delivery_mode = no-mistakes`) at their ship stage, meaning the last stage `active` while `running` or `validating`, or delivered (`ready`). An earlier stage or a stage still waiting for its grant is left alone; the next pass after it reaches its ship stage still sees it behind and acts then. A `merging` run is left alone.
- **Behind**: `git diff --name-only $(git merge-base HEAD origin/<default>) origin/<default> -- <paths>` in the run's worktree is not empty. Only main's changes count, never the branch's own edit of a policy file. A git read that fails skips the run for this pass.
- **Once per (run, policy hash)**: each action appends `run.policy_steered` with `{hash, main, files, via}`. Before acting, the pass looks for that event with this hash. An unrelated merge leaves the hash unchanged and steers nobody again; a further policy change is a new hash and acts again. The state lives in events, so a restart loses nothing, and a merge made on GitHub counts the same as one Flowryn made.
- **A live ship** (last stage active): one normal steer: "main changed its validation policy since your branch forked (<files>; origin/main at <sha>). Merge origin/main into your branch with a new commit (git fetch origin, then git merge origin/main; never rebase or force-push), run the tests, then no-mistakes rerun if your pipeline is running for this branch (it validates the merged branch again), else start it as usual. Then deliver as usual." An open CI-wait decision on the run is dismissed as superseded (`answered_via = policy`, a `decision.dismissed` event whose `why` says so). The steer opens no item; it shows in the fleet and the worker's inbox.
- **A delivered ship** (`ready`): sent back through `sendBack`, as `decline` and the conflict nudge send it. The run is running again, approvals are void, the merge gate closes, and the last stage starts again through the scheduler with "Your delivered PR is behind: … then ship it again and deliver." A `policy_sent_back` P1 info line says so, and the scheduler is kicked.
- **Delivered again still behind** a hash it was already steered or sent back for: no second send-back. One `policy_behind` P1 info line ("merge as is, steer it, or flowryn decline <task>"), closed once the branch has main's policy or the run lands.
- **Items**: `policy_sent_back` and `policy_behind` are P1 info. A landing settles both, and the leader skill names them.
- **Choices** (the design page, approved): an own loop rather than an upkeep hook, because the task asks for 5 min while upkeep runs every 10 and waits on cleanups and restarts (this pass only reads git and writes steers). The trigger is a state-based diff, not merge events. `sendBack` handles delivered ships because it landed with spec 3 phase 3 (#52); `policy_behind` covers only the case of a ship delivered again behind the same hash. No-mistakes ships only, because a local ship runs neither no-mistakes nor CI. The steer is normal, because an urgent one may cut a running tool.
- **Tests**: `test/unit/policy-follow.test.ts` (real git: the directory pathspec in `ls-tree` and `diff`; the branch's own edit is not main's; an unrelated file keeps the hash; an unreadable commit is null; a validating ship steered once per hash, an unrelated merge, a further change; a branch that merged main; one fetch serving two worktrees; earlier stage, waiting stage, local ship, merging run, then the earlier stage reaching its ship stage; the CI-wait dismissal; the send-back and its line; `policy_behind` once and its close; a landing settling the lines; the switch off; a failed fetch; kick and stop; `[validation]` defaults and refusals). `test/integration/policy-follow.test.ts` runs through the real daemon, fake Herdr and worker, and fake GitHub on the bare origin: a policy merge steers a validating ship once, an unrelated merge does not, a further policy change does, and a delivered ship is sent back with its line and steer.
