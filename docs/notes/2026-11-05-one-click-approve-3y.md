# One-click approve on every review page

- Status: done
- Open: not yet run live in a real browser beyond the probe below (Chrome only; Safari and Firefox are untested), nor with the browser-folder deny on a real QA run of chrome-devtools-axi.

Approve on a review page passes its gate in one click: no code to type, no confirmation in chat, no `flowryn approve`. Every review page carries the widget, so pages without questions get the button too. A worker still cannot pass its own gate: the page the user's tab shows is the daemon's checked copy of the worker's page, on which no script but Flowryn's widget runs. Plain code (a random key, a hash, fixed checks, an HTML check); no model.

## How it works

0. **The snapshot.** The key reaches the page's frame, so a script the worker put on its page could read it as the widget does and press Approve itself. So the user never sees the worker's file. At `stage done` the daemon checks the page (`reviewPageProblems`, `src/lavish/snapshot.ts`): any `<script>` other than exactly `<script src="flowryn-questions.js"></script>`, an `on*=` handler, a `javascript:`/`vbscript:`/`data:text/html`-style URL (character references and blanks decoded), an `<iframe>`, `<frame>`, `<object>`, `<embed>`, `<base>`, `<meta http-equiv>`, `<link rel="import">`, an SVG `<foreignObject>` or script, a form or button posting elsewhere, and markup a browser could split differently from the check (a CDATA section, a `<style>` or `<title>` holding `<`, a `<textarea>`/`<noscript>`-style raw-text element, a cut-off tag) refuse it with the list. A page that passes is copied, with its images (`.png .jpg .jpeg .gif .webp`), CSS and Markdown (the design spec link) under its folder (no symlinks, at most 200 files, never `.js`, `.svg`, other pages or the worker's own `flowryn-questions.js`), to `<state_dir>/review-pages/<run>/<its path in the report directory>`, which no Claude worker can write. The gate's `page_path` is the copy and `source_page` (migration 53) the worker's file; the review URL is the copy's Lavish session on the worker's host and port. The daemon writes the widget only beside the copy, hosts it (`lavish-axi <copy> --no-open`, checking the printed session key, before its first poll and after a failed one), polls it, replies on it and opens it. While the gate is open the poller looks at the worker's page every 2 s (and a `review reply` copies first, and re-pins a design only when the copy took, so a refused revision leaves the old pin and a changed spec cannot pass): a revision that passes replaces the copy (`gate.page_copied`; Lavish live-reloads your tab), one that fails keeps the last good copy, records `gate.page_refused` with the problems and steers the worker with them. Design pins and draft checks read the copy, so you approve what you saw. A gate from before this change (no `source_page`) gets no key.
1. **The key.** When the opener claims a gate's page (`src/lavish/opener.ts`), it mints a pass key (32 random bytes, base64url, `mintPassKey` in `src/policy/pass-key.ts`), stores its SHA-256 on the gate (`gates.pass_key_hash`, migration 53 `page-pass-key`) in the claim's transaction, and hands `open` the review URL with `?flowryn_pass=<key>`. Only that argument carries the key: the gate's `review_url`, the `gate.browser_*` events (`one_click: true|false`), the gate_ready item and the log keep the URL without it, and a failed open's message is redacted. A file:// page gets no key.
2. **One key per tab.** A page resubmitted after changes is `skipped` (Lavish live-reloads the tab you have), and its gate takes the tab's live hash from the latest earlier gate of the run with that URL.
3. **The page reads it.** lavish-axi 0.1.96 ignores the query (`/session/:key` reads only its layout-gate flag) and loads the page in a sandboxed frame whose `document.referrer` is the full top-level address, query included, across live reloads (measured 2026-11-05 with a probe page in Chrome). The fragment never reaches the frame, which is why the c6 design parked one click. The widget (`src/lavish/widget.ts`) reads `flowryn_pass` from the referrer when its state says the gate has a live key (`oneClick`), and puts it in the Send's token as `t` on Approve only, never in the prompt's words.
4. **The check.** `passFromPage` (`src/policy/page-pass.ts`) runs every check it ran for a code (run live, gate open and the run's own, every question answered, the draft page unchanged), then the key against the hash (constant time), then the HEAD now against `gates.pass_head`, the HEAD `stage done` read when the review opened. Right: `recordGatePass` on channel `page` (actor `<you> (review page, one click)`), bound to that HEAD and used once; the next stage is requested and the page hears "Approved: the review passed; the <stage> stage starts now."
5. **Spent on arrival.** The Send that carries the key sits in lavish's files, which a worker can read, so a right key that arrives is spent whatever the outcome (`spendPassKey` clears the hash on every gate of the tab, event `gate.pass_key_spent` with the gate and why). A wrong key spends nothing: it reveals nothing, and spending it would let a worker spoil your button.
6. **Fallback.** No live key (spent, the page opened by hand from a copied link, a browser that hides the referrer): the widget shows the c6 pass code field and Approve works as "Send and pass" did. A refusal for a spent key (`no_key`) or moved work (`key_moved`) opens the leader's request and sends you a code at once; a wrong key (`wrong_key`) opens the leader's request only.

## What the guard stops, and what it doesn't

- **Stops:** a Claude worker's script reading the key from your tab (the tab shows the checked copy, which a Claude worker cannot write and which carries no script but the widget), a worker posting Approve to Lavish (no key, or a guessed one: 256 bits), a worker's CLI (`gate pass` is a leader verb), a replay of your click (the gate is closed and the key spent), an approval of work that moved since the review opened. The one-click design refuses a gate change (`design_changed`) as the typed code does: no leader request and no code.
- **Does not stop:** anything that reads your browser's history or session files on disk, where the address with the key is kept. Claude workers are denied reading browser profile folders (`browserProfileReads`, `src/policy/static.ts`: Chrome, Chromium, Brave, Edge, Arc, Vivaldi, Firefox under `~/Library/Application Support`, and `~/Library/Safari`), which Claude applies to its Bash sandbox too; a Pi worker has no such fence, nor a write sandbox, so it could also rewrite the copy. `/usr/bin/open`'s command line shows the address to process listings for a moment while the worker is idle (the c6 notification's class). A program that drives your own browser can click the button. These are listed with limit (d) in docs/cutover-notes.md "C1 · Decisions".

## Where the key never goes

The database (only the hash), events, the daemon log, items, notifications, Lavish replies, the widget, and the notes beside the page: a poll's raw output kept there now has each answer token replaced with `(recorded)` (`withoutAnswerTokens`, `src/lavish/poll-output.ts`), for codes as well as keys. The integration test scans every file under the test home's state and data directories and its logs after a pass (the open recorder, which stands in for your browser, aside).

## Choices

- **The query, not the fragment:** the only daemon-to-browser path a worker cannot read that reaches the frame.
- **The hash in the database, not the key in memory:** a daemon restart during a review would otherwise drop you back to typing; the hash is useless to a reader.
- **Keep the typed code** as the fallback above, rather than leaving only chat.
- **A checked copy, not a policy on the worker's page:** a Content-Security-Policy would need Lavish to serve the page with a header it does not set, and moving the key out of the frame's reach loses the only path that reaches it. The check is an allow-list of plain HTML and CSS, deliberately stricter than browsers need (prose and code samples are text and pass; markup inside a `<style>` does not).
- **Every review page mounts the widget:** `stage done` refuses a page given with `--page`, or a Lavish page found from `--review`, that does not mount it; the design and QA templates mount it, and the draft page always did.
- **The leader skill** (`src/bridges/skill.ts`) says an Approve on the page is the user's pass and is never confirmed again in chat.
- **No `PROTO` bump** (the token is the page's format, not the wire) and **no `CONTRACT_REVISIONS` bump**: the contract suite never runs `stage done` or a review page.
